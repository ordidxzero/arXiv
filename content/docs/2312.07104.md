## Abstract

대규모 언어 모델(LLM)은 점점 더 복잡한 작업에 쓰이고 있다. 이런 작업에는 여러 번의 생성 호출, 고급 프롬프팅 기법, 제어 흐름(control flow), 구조화된 입력·출력이 필요하다. 그런데 이런 애플리케이션을 작성하고 효율적으로 실행할 시스템이 아직 부족하다. 본 논문은 복잡한 언어 모델 프로그램을 효율적으로 실행하는 시스템인 SGLang을 소개한다. SGLang은 프런트엔드 언어와 런타임으로 이루어진다. 프런트엔드는 생성과 병렬 처리를 제어하는 프리미티브(primitive, 언어가 기본으로 제공하는 연산)를 제공해 프로그래밍을 쉽게 한다. 런타임은 새로운 최적화로 실행을 가속한다. 대표적으로, KV 캐시를 재사용하는 RadixAttention과, 구조화된 출력을 더 빠르게 디코딩하는 압축 유한 상태 기계(compressed finite state machine)가 있다. 실험 결과, SGLang은 다양한 대규모 언어 모델과 멀티모달 모델에서 당시 최고 수준의 추론 시스템보다 최대 {{< katex >}}6.4\times{{< /katex >}} 높은 처리량을 달성했다. 실험 작업에는 에이전트 제어, 논리 추론, 퓨샷 학습 벤치마크, JSON 디코딩, 검색 증강 생성(retrieval-augmented generation) 파이프라인, 멀티턴 채팅이 포함된다. 코드는 <https://github.com/sgl-project/sglang>에 공개되어 있다.

> **역주.** KV 캐시는 트랜스포머가 이미 처리한 토큰들의 key·value 텐서를 저장해 두고 다음 토큰을 계산할 때 다시 쓰는 메모리다. 유한 상태 기계(FSM)는 상태와 상태 사이 전이로 이루어진 그래프로, 여기서는 출력이 정해진 형식(예: JSON)을 벗어나지 않도록 디코딩을 안내하는 데 쓰인다. 두 개념은 각각 3절·부록 A와 4절·부록 B에서 자세히 다룬다.

## 1 Introduction

최근 LLM의 능력이 커지면서 활용 범위도 넓어졌다. 이제 LLM은 더 다양한 일반 작업을 처리하고, 자율 에이전트로도 동작한다 [35, 6, 36, 52, 46]. 이런 애플리케이션에서 LLM은 여러 라운드에 걸쳐 계획하고 추론하며 외부 환경과 상호작용한다. 이를 가능하게 하는 수단은 도구 사용 [41, 38], 여러 입력 모달리티 [47, 2], 그리고 다양한 프롬프팅 기법 [30]이다. 프롬프팅 기법에는 퓨샷 학습(few-shot learning) [5], 자기 일관성(self-consistency) [53], skeleton-of-thought [33], tree-of-thought [56] 등이 있다. 이 새로운 사용 사례들은 모두 LLM 생성 호출을 여러 번 실행해야 하며, 뒤 호출이 앞 호출의 결과에 의존하는 경우가 많다. 즉, 복잡한 작업을 여러 호출로 이루어진 구조로 해결하는 추세가 나타나고 있다 [57, 21].

> **역주.** 자기 일관성은 같은 질문에 답을 여러 번 샘플링한 뒤 가장 많이 나온 답을 고르는 기법이다. Tree-of-thought는 추론 과정을 트리처럼 여러 갈래로 펼쳐 탐색하는 기법이고, Skeleton-of-thought는 답의 뼈대(목차)를 먼저 생성한 뒤 각 항목을 병렬로 채우는 기법이다.

이런 패턴이 등장했다는 것은 LLM을 다루는 방식이 바뀌고 있다는 뜻이다. 단순한 채팅에서 벗어나, 프로그램으로 LLM을 쓰는 더 정교한 방식으로 옮겨 가고 있다. 즉, 프로그램이 LLM의 생성 과정을 스케줄링하고 제어한다. 본 논문은 이런 프로그램을 "언어 모델 프로그램(Language Model Program, LM 프로그램)"이라 부른다 [4, 20]. 앞에서 말한 고급 프롬프팅 기법과 에이전트 워크플로는 모두 LM 프로그램에 속한다. LM 프로그램에는 흔히 두 가지 공통 특성이 있다. (1) LM 프로그램에는 보통 여러 번의 LLM 호출이 있고, 그 사이사이에 제어 흐름이 끼어 있다. 복잡한 작업을 완수하고 전체 품질을 높이려면 이런 구조가 필요하다. (2) LM 프로그램은 구조화된 입력을 받아 구조화된 출력을 낸다. 그래야 LM 프로그램끼리 조합할 수 있고, 기존 소프트웨어 시스템에 LM 프로그램을 통합할 수 있다.

LM 프로그램이 널리 쓰이고 있지만, 이를 표현하고 실행하는 현재 시스템은 여전히 비효율적이다. 본 논문은 LM 프로그램을 효율적으로 사용하는 데 두 가지 주요 과제가 있다고 본다. *첫째, LLM의 출력이 비결정적(non-deterministic)이어서 LM 프로그램을 작성하기가 번거롭고 어렵다.* LM 프로그램을 개발하려면 문자열을 많이 조작해야 하고, 프롬프트를 실험적으로 조정해야 하며, 깨지기 쉬운 출력 파싱 코드를 짜야 한다. 여러 입력 모달리티를 처리하고 병렬 처리 메커니즘도 구현해야 한다. 이런 복잡성 때문에 단순한 프로그램조차 읽기가 크게 어려워진다(2절).

*둘째로, 그리고 더 중요하게, 중복된 계산과 메모리 사용 때문에 LM 프로그램 실행이 비효율적이다.* 당시 최고 수준의 추론 엔진들(예: vLLM [23], TGI [16], TensorRT-LLM [34])은 워크로드에 대한 직접적인 정보 없이 지연 시간을 줄이고 처리량을 높이도록 최적화되었다. 그래서 이 시스템들은 범용적이고 견고하지만, 특정 워크로드에서는 상당한 비효율이 생긴다. 대표적인 예가 Key-Value(KV) 캐시 재사용이다(3절). KV 캐시는 추론 중에 만들어지는 중간 텐서들로 이루어진다. 이 텐서들은 생성형 추론에 꼭 필요하고, 다시 쓸 수 있다. LM 프로그램은 흔히 여러 인스턴스를 묶어 배치로 실행한다. 이때 공통 접두사(prefix)를 공유하는 LLM 호출이 많아서, 호출 사이에 KV 캐시를 재사용할 기회가 많다. 하지만 현재 시스템에는 이 재사용을 돕는 효과적인 메커니즘이 없어, 불필요한 계산과 메모리 낭비가 생긴다. 또 다른 예는 구조화된 출력(예: JSON 모드)을 위한 제약 디코딩(constrained decoding)이다. 제약 디코딩에서는 LLM의 출력이 정규 표현식으로 정의된 특정 문법 규칙을 따르도록 제한된다(4절). 이런 제약 아래에서는 여러 토큰을 한 번에 디코딩할 수 있는 경우가 많다. 그런데 기존 시스템은 한 번에 토큰 하나씩만 디코딩해 디코딩 속도가 최적보다 느리다.

**그림 1.** 시스템 구조: 인터프리터가 언어 프리미티브를 최적화된 런타임 위에서 실행한다.

이 과제들을 해결하기 위해 본 논문은 LLM을 위한 구조화 생성 언어(**S**tructured **G**eneration **Lang**uage)인 SGLang을 제안한다. 핵심 아이디어는 LM 프로그램 안의 다중 호출 구조를 체계적으로 활용해 실행을 효율화하는 것이다. 그림 1처럼 SGLang은 프런트엔드 언어와 백엔드 런타임, 두 부분으로 이루어진다. 프런트엔드는 LM 프로그램 작성을 단순하게 하고, 런타임은 그 실행을 가속한다. 두 부분은 함께 동작하면 성능이 더 좋아지지만, 각각 독립적으로도 동작할 수 있다.

SGLang은 Python에 내장된 도메인 특화 언어(domain-specific language)다. 생성용 프리미티브(예: `extend`, `gen`, `select`)와 병렬 처리 제어용 프리미티브(예: `fork`, `join`)를 제공한다. SGLang은 Python의 제어 흐름 및 라이브러리와 호환되므로, 사용자는 익숙한 Python 문법으로 고급 프롬프팅 워크플로를 쉽게 개발할 수 있다. 본 논문은 SGLang용 인터프리터와 컴파일러를 제공한다. 인터프리터는 프롬프트 상태를 하나의 스트림(stream, 연산이 차례로 쌓여 실행되는 큐)으로 관리한다. 프리미티브 연산은 이 스트림에 제출되어 비동기로 실행된다. 이렇게 해서 동기화와 프로그램 내부 병렬 처리를 제대로 제어한다. 또한 SGLang 프로그램을 트레이싱(tracing)해 컴파일하면 더 많은 최적화를 적용할 수 있다.

런타임 쪽에서는 SGLang 프로그램 실행을 가속하는 몇 가지 새로운 최적화를 제안한다. *첫 번째 기법*인 RadixAttention은 여러 생성 호출에 걸쳐 KV 캐시를 자동으로 재사용한다. 기존 추론 엔진은 요청 처리가 끝나면 그 요청의 KV 캐시를 버린다. 그래서 여러 호출 사이에서 KV 캐시를 재사용하지 못하고, 실행이 크게 느려진다. 반면 본 시스템은 모든 요청의 KV 캐시를 기수 트리(radix tree) 안에 LRU 캐시로 유지한다. 즉, KV 캐시를 전통적인 캐시처럼 관리하고, 기수 트리로 매칭·삽입·제거를 효율적으로 처리한다. 이렇게 캐시를 트리로 관리하면, 캐시 상태를 고려해 요청 순서를 정하는 캐시 인식 스케줄링(cache-aware scheduling) 정책을 붙일 수 있다. 그 결과 런타임은 다양한 재사용 패턴을 효율적으로 처리한다. *두 번째 기법*은 압축 유한 상태 기계로, 구조화된 출력을 위한 제약 디코딩을 더 빠르게 한다. 기존 시스템은 허용되지 않는 토큰의 확률을 마스킹하는 방식으로 다음 토큰 하나에만 제약을 적용한다. 그래서 한 번에 토큰 하나씩만 디코딩할 수 있다. 반면 본 시스템은 제약을 분석해, 그 제약을 표현하는 압축 유한 상태 기계를 만든다. 원래는 여러 토큰(여러 디코딩 스텝)에 걸쳐야 지나던 FSM 경로를, 가능하면 디코딩 한 스텝에 통과하는 간선 하나로 압축한다. 그 결과 여러 토큰을 한 번에 디코딩해 디코딩 속도를 높인다. 마지막으로, SGLang은 OpenAI의 GPT-4 같은 API 전용 모델도 지원한다. 이를 위해 *세 번째 기법*인 API 투기적 실행(API speculative execution)을 도입해, API 전용 모델에서 다중 호출 프로그램을 최적화한다.

> **역주.** 기수 트리는 트라이(trie, 문자열을 앞부분부터 한 글자씩 나눠 저장하는 트리)를 압축한 형태로, 간선 하나에 여러 원소로 된 시퀀스를 붙일 수 있다. LRU(least recently used) 캐시는 공간이 부족할 때 가장 오래전에 쓰인 항목부터 내보내는 캐시다. 투기적 실행은 결과를 미리 추측해 앞당겨 실행하는 것을 말하며, 5절에서 구체적으로 설명한다.

SGLang으로 다양한 LLM 애플리케이션을 구현했다. 에이전트 제어, 논리 추론, 퓨샷 학습 벤치마크, JSON 디코딩, 검색 증강 생성 파이프라인, 멀티턴 채팅, 멀티모달 처리가 여기에 포함된다. 성능은 NVIDIA A10G와 A100 GPU에서 여러 모델로 측정했다. 모델은 Llama-7B/70B [49], Mistral-8x7B [17], LLaVA-v1.5-7B(이미지) [28], LLaVA-NeXT-34B(비디오) [62]다. 실험 결과, SGLang은 Guidance [13], vLLM [23], LMQL [4] 등 기존 프로그래밍·추론 시스템에 비해 다양한 워크로드, 모델, 하드웨어 설정에서 최대 {{< katex >}}6.4\times{{< /katex >}} 높은 처리량을 달성했다.

> **역주.** 본문의 "Mistral-8x7B"는 원문 표기를 그대로 옮긴 것이며, 실험 절(6절)과 참고문헌 [17]에서는 같은 모델을 Mixtral-8x7B로 부른다.

## 2 Programming Model

이 절에서는 하나의 예제를 따라가며 SGLang 프로그래밍 모델을 소개한다. 이어서 언어 프리미티브와 실행 모드를 설명하고, 런타임 최적화의 기회를 개괄한다. 이 프로그래밍 모델은 유연하고 서로 조합할 수 있는 프리미티브를 제공한다. 이를 통해 다중 호출 워크플로의 번거로운 작업(예: 문자열 조작, API 호출, 제약 지정, 병렬 처리)을 단순하게 만든다.

> **역주.** 그림 오른쪽 설명은 위에서부터 다음과 같다. 채팅 템플릿과 멀티모달 입력 처리 / 확률이 가장 높은 선택지 고르기 / 결과를 가져와 Python 제어 흐름에 쓰기 / 런타임 최적화: KV 캐시 재사용(3절) / 여러 생성 호출을 병렬 실행 / 생성 결과 가져오기 / 런타임 최적화: API 투기적 실행(5절) / 런타임 최적화: 빠른 제약 디코딩(4절) / SGLang 프로그램 실행.

**A running example.** 이 언어는 Python에 내장된 도메인 특화 언어다. 그림 2는 branch-solve-merge 프롬프팅 방법 [40]으로 이미지에 관한 에세이를 평가하는 프로그램이다. 함수 `multi_dimensional_judge`는 `s`, `path`, `essay` 세 인자를 받는다. `s`는 프롬프트 상태를 관리하고, `path`는 이미지 파일 경로, `essay`는 에세이 텍스트다. 새 문자열과 SGLang 프리미티브는 `+=` 연산자로 상태 `s`에 덧붙여 실행할 수 있다. 함수는 먼저 이미지와 에세이를 프롬프트에 추가한다. 다음으로 `select`로 에세이가 이미지와 관련 있는지 확인하고, 그 결과를 `s["related"]`에 저장한다. 관련이 있으면 프롬프트를 세 개로 복제(fork)해 서로 다른 기준으로 병렬 평가한다. 복제된 각 프롬프트 상태 `f`에서 `gen`으로 생성한 평가는 `f["judgment"]`에 저장된다. 이어서 평가들을 합치고, 요약을 생성하고, 문자 등급(A, B 등)을 매긴다. 마지막으로 정규 표현식 제약 `regex`로 정의한 스키마에 맞춰 결과를 JSON 형식으로 반환한다. SGLang은 이 프로그램을 크게 단순화한다. OpenAI API 방식의 인터페이스로 같은 프로그램을 짜면, 문자열 조작과 병렬 처리 제어를 직접 해야 해서 코드 줄 수가 {{< katex >}}2.1\times{{< /katex >}}로 늘어난다.

> **역주.** branch-solve-merge는 문제를 여러 갈래(branch)로 나눠 각각 풀고(solve), 그 결과를 하나로 합치는(merge) 프롬프팅 기법이다. 그림 2에서는 명료성(Clarity)·독창성(Originality)·근거(Evidence) 세 기준이 세 갈래에 해당한다.

**Language primitives.** SGLang은 프롬프트 상태, 생성, 병렬 처리를 제어하는 프리미티브를 제공한다. 이 프리미티브는 Python 문법 및 라이브러리와 함께 쓸 수 있다. 프리미티브는 다음과 같다. "`gen`"은 모델을 호출해 생성하고, 그 결과를 첫 번째 인자로 지정한 이름의 변수에 저장한다. "`regex`" 인자를 주면 출력이 정규 표현식으로 정의된 문법(예: JSON 스키마)을 따르도록 제약할 수 있다. "`select`"는 모델을 호출해 목록에서 확률이 가장 높은 선택지를 고른다. 연산자 "`+=`" 또는 "`extend`"는 프롬프트에 문자열을 덧붙인다. 연산자 "`[variable_name]`"은 생성 결과를 가져온다. "`fork`"는 프롬프트 상태를 병렬로 복제한다. "`join`"은 복제한 프롬프트 상태를 다시 합친다. "`image`"와 "`video`"는 이미지와 비디오 입력을 받는다.

**Execution modes.** SGLang 프로그램을 실행하는 가장 간단한 방법은 인터프리터다. 인터프리터는 프롬프트를 비동기 스트림으로 다룬다. `extend`, `gen`, `select` 같은 프리미티브는 스트림에 제출되어 비동기로 실행된다. 이 호출들은 블로킹되지 않으므로, Python 코드는 생성이 끝나기를 기다리지 않고 계속 실행된다. CUDA 커널을 비동기로 실행하는 것과 비슷하다. 각 프롬프트는 백그라운드 스레드의 스트림 실행기(stream executor)가 관리하므로, 한 프로그램 안에서 병렬 처리가 가능하다. 생성 결과를 가져오는 연산은 결과가 준비될 때까지 블로킹되므로, 동기화가 올바르게 이루어진다. 다른 방법으로, SGLang 프로그램을 계산 그래프로 컴파일해 그래프 실행기로 실행할 수도 있다. 이렇게 하면 더 많은 최적화를 적용할 수 있다. 본 논문은 기본적으로 인터프리터 모드를 쓰며, 컴파일러 모드의 결과는 부록 D에서 다룬다. SGLang은 자체 런타임인 SGLang Runtime(SRT)으로 오픈 웨이트 모델(open-weight model, 가중치가 공개된 모델)을 지원하고, OpenAI와 Anthropic 모델 같은 API 모델도 지원한다.

**Comparison.** LLM용 프로그래밍 시스템은 고수준(예: LangChain, DSPy)과 저수준(예: LMQL, Guidance, SGLang)으로 나눌 수 있다. 고수준 시스템은 미리 정의되었거나 자동 생성된 프롬프트를 제공한다. DSPy의 프롬프트 최적화기가 그 예다. 저수준 시스템은 보통 프롬프트를 바꾸지 않고, 프롬프트와 프리미티브를 직접 다룰 수 있게 한다. SGLang은 LMQL, Guidance와 비슷한 저수준 시스템이다. 표 1에서 이들의 기능을 비교했다. SGLang은 런타임 효율에 더 집중하며, 프런트엔드 언어와 함께 설계한(co-designed) 자체 런타임을 갖춘다. 그래서 뒤에서 소개할 새로운 최적화를 적용할 수 있다. 고수준 언어(예: DSPy)는 저수준 언어(예: SGLang)로 컴파일될 수 있다. 6절에서는 런타임 효율을 높이기 위해 SGLang을 DSPy의 백엔드로 통합한 사례를 보인다.

**Runtime optimizations.** 그림 2에는 세 가지 런타임 최적화 기회가 나타나 있다. KV 캐시 재사용, 빠른 제약 디코딩, API 투기적 실행이다. 이어지는 절들에서 차례로 다룬다.

## 3 Efficient KV Cache Reuse with RadixAttention

SGLang 프로그램은 여러 생성 호출을 연달아 이을 수 있고, "`fork`" 프리미티브로 병렬 복사본을 만들 수 있다. 또한 서로 다른 프로그램 인스턴스가 공통 부분(예: 시스템 프롬프트)을 공유하는 경우가 많다. 이런 상황에서는 실행 중에 공유되는 프롬프트 접두사가 많이 생기고, 따라서 KV 캐시를 재사용할 기회도 많아진다. LLM 추론에서 KV 캐시는 순전파(forward pass)의 중간 텐서를 저장해 두었다가 이후 토큰을 디코딩할 때 재사용한다. 이름은 셀프 어텐션 메커니즘 [51]의 key-value 쌍에서 따왔다. KV 캐시 계산은 접두사 토큰에만 의존한다. 따라서 프롬프트 접두사가 같은 요청들은 KV 캐시를 재사용해 중복 계산과 메모리 사용을 줄일 수 있다. 자세한 배경과 몇 가지 예는 부록 A에 있다.

KV 캐시를 재사용할 기회가 이렇게 있으므로, SGLang 프로그램 최적화의 핵심 과제는 여러 호출과 인스턴스에 걸쳐 KV 캐시를 재사용하는 것이다. 몇몇 시스템이 특정 KV 캐시 재사용 사례를 다루기는 했지만 [23, 58, 18, 12], 대개 수동 설정이 필요하고 모든 재사용 패턴(예: 동적인 트리 구조)을 처리하지는 못한다. 그 결과 당시 최고 수준의 추론 시스템 대부분은 요청마다 KV 캐시를 다시 계산한다. 이 시스템들의 한계와 본 논문과의 차이는 7절에서 논의한다.

이 절에서는 런타임에 KV 캐시를 자동적·체계적으로 재사용하는 새로운 기법인 RadixAttention을 소개한다. 기존 시스템은 생성 요청이 끝나면 KV 캐시를 버린다. 반면 본 시스템은 프롬프트와 생성 결과의 캐시를 기수 트리에 보관해, 접두사 검색·재사용·삽입·제거를 효율적으로 처리한다. 캐시 적중률(cache hit rate)을 높이기 위해 LRU 제거 정책과 캐시 인식 스케줄링 정책을 구현했다. RadixAttention은 연속 배칭(continuous batching) [60], 페이지드 어텐션(paged attention) [23], 텐서 병렬화(tensor parallelism) [44] 같은 기법과 함께 쓸 수 있다. 또한 캐시 적중이 전혀 없을 때도 메모리와 시간 오버헤드는 무시할 만한 수준이다.

> **역주.** 연속 배칭은 배치 안의 요청 하나가 끝나면 곧바로 빼고 대기 중인 새 요청을 매 스텝 넣는 방식이다. 페이지드 어텐션(vLLM)은 KV 캐시를 운영체제의 페이지처럼 작은 블록 단위로 나눠 메모리에 흩어 저장한다. 텐서 병렬화는 한 레이어의 가중치 행렬을 여러 GPU에 나눠 계산하는 방식이다.

**RadixAttention.** 기수 트리는 고전적인 트라이(접두사 트리)를 공간 효율적으로 대체하는 자료 구조다. 일반 트리와 달리 기수 트리의 간선에는 원소 하나만이 아니라 길이가 다양한 원소 시퀀스도 붙일 수 있어 효율이 크게 높아진다. 본 시스템은 토큰 시퀀스와 그에 대응하는 KV 캐시 텐서 사이의 매핑을 기수 트리로 관리한다. 이 KV 캐시 텐서들은 연속되지 않은 페이지 단위 레이아웃으로 저장되며, 페이지 하나의 크기는 토큰 하나에 해당한다. GPU 메모리는 KV 캐시로 금방 가득 차므로, 가장 오래전에 쓰인 리프(leaf)부터 제거하는 간단한 LRU 제거 정책을 도입했다. 리프부터 제거하면, 그 리프들의 공통 조상은 계속 재사용할 수 있다. 공통 조상은 자신이 리프가 된 뒤에야 제거 대상이 된다.

연속 배칭 환경에서는 현재 실행 중인 배치가 쓰고 있는 노드를 제거할 수 없다. 그래서 각 노드는 참조 카운터(reference counter)를 유지한다. 이 값은 지금 그 노드를 쓰고 있는 실행 중 요청의 수다. 참조 카운터가 0인 노드만 제거할 수 있다. 본 시스템은 고정 크기의 메모리 풀을 캐시용으로 미리 할당하지 않는다는 점에 주의하자. 대신 캐시된 토큰과 현재 실행 중인 요청이 같은 메모리 풀을 공유한다. 즉, 시스템이 캐시와 실행 요청에 메모리를 동적으로 할당한다. 대기 요청이 충분히 많으면, 시스템은 배치 크기를 키우기 위해 필요하다면 캐시된 토큰을 모두 제거하기도 한다. 그림 3은 들어오는 여러 요청에 따라 기수 트리가 어떻게 유지되는지 보여 준다. 프런트엔드 인터프리터는 전체 프롬프트를 런타임에 보내고, 런타임이 접두사 매칭과 재사용을 수행한다. 트리 구조는 CPU에 저장되며, 유지 오버헤드는 무시할 만하다. `fork` 프리미티브를 실행할 때 프런트엔드는 먼저 접두사를 힌트로 보내 트리에 접두사가 제대로 삽입되게 한 뒤, 나머지 프롬프트를 보낸다. 이 "프런트엔드 힌트(Frontend Hint)"는 런타임의 스케줄링과 매칭을 단순하게 만든다. 프런트엔드와 런타임을 함께 설계했을 때 얻는 이점을 보여 주는 예다.

**Cache-aware scheduling.** 캐시 적중률은 {{< katex >}}\frac{\text{number of cached prompt tokens}}{\text{number of prompt tokens}}{{< /katex >}}로 정의한다. 즉, 프롬프트 토큰 가운데 캐시에서 찾은 토큰의 비율이다. 대기 큐에 요청이 많을 때는 실행 순서가 캐시 적중률에 크게 영향을 줄 수 있다. 예를 들어 요청 스케줄러가 서로 관련 없는 요청 사이를 자주 오가면 캐시 스래싱(cache thrashing, 캐시 항목이 다시 쓰이기 전에 계속 밀려나는 현상)이 일어나 적중률이 낮아진다. 그래서 캐시 적중률을 높이는 캐시 인식 스케줄링 알고리즘을 설계했다. 배치 처리 환경에서는 선착순(first-come, first-served) 스케줄 대신, 요청을 매칭된 접두사 길이로 정렬한다. 즉, 기수 트리에 이미 캐시된 부분과 겹치는 접두사가 긴 요청을 먼저 처리한다. 알고리즘 1(부록)은 연속 배칭과 함께 쓰는 캐시 인식 스케줄링의 의사 코드다. 이 알고리즘은 최장 공유 접두사 우선(longest-shared-prefix-first) 순서를 쓴다. 지연 시간에 더 민감한 환경이라도, 캐시 재사용을 늘리기 위해 요청 순서를 조금 바꾸는 정도는 받아들일 수 있을지 모른다. 또한 오프라인 경우의 최적 스케줄링에 대해 다음 정리를 증명했다.[^1]

[^1]: 실제로는 출력 토큰 수를 예측할 수 없다. 그래서 KV 캐시를 다시 계산하게 될 수 있으므로, 실제 계산은 정리 3.1의 증명에서 설명한 것과 같지 않다.

**정리 3.1 (Theorem 3.1).** 요청 배치가 주어지고 캐시 크기가 최대 요청 길이 이상({{< katex >}}\geq{{< /katex >}})이면, 요청들의 기수 트리를 깊이 우선 탐색(depth-first search, DFS) 순서로 방문해 최적의 캐시 적중률을 달성할 수 있다. 최장 공유 접두사 우선 순서는 깊이 우선 탐색 순서와 같다.

> **역주.** 여기서 "오프라인"은 처리할 요청 전체를 미리 알고 있는 경우, "온라인"은 요청이 실행 도중 계속 도착하는 경우를 뜻한다.

증명은 부록 A.3에 있다. 온라인 경우에는 DFS 순서가 깨지지만, 본 스케줄은 전체 기수 트리 가운데 새로 도착한 요청 때문에 늘어난 부분에 대해서는 여전히 DFS 동작을 근사한다. 이 내용도 부록 A.3에 설명했다. 탐욕적인 캐시 인식 스케줄링은 높은 처리량을 낼 수 있지만, 기아(starvation, 어떤 요청이 계속 뒤로 밀려 처리되지 못하는 상태)를 일으킬 수 있다. 다른 공정 스케줄링 방법 [42]과의 통합은 향후 과제로 남긴다.

**Distributed Cases.** RadixAttention은 여러 GPU로 확장할 수 있다. 텐서 병렬화에서는 각 GPU가 샤딩된(나눠 가진) KV 캐시를 유지한다. 트리 연산은 모든 GPU에서 똑같으므로 추가 동기화가 필요 없다. 여러 워커를 쓰는 데이터 병렬화는 부록 A.4에서 다룬다.

## 4 Efficient Constrained Decoding with Compressed Finite State Machine

LM 프로그램에서 사용자는 모델 출력이 JSON 스키마 같은 특정 형식을 따르도록 제약하고 싶을 때가 많다. 그러면 출력을 더 잘 제어할 수 있고, 견고성이 높아지며, 출력을 파싱하기도 쉬워진다. SGLang은 정규 표현식으로 이런 제약을 걸 수 있도록 `regex` 인자를 제공한다. 정규 표현식은 실제로 쓰이는 많은 상황을 표현하기에 충분하다. 기존 시스템은 정규 표현식을 유한 상태 기계(finite state machine, FSM)로 변환하는 방식으로 이를 지원한다 [54]. 디코딩하는 동안 기존 시스템은 현재 FSM 상태를 유지한다. 그리고 현재 상태에서 갈 수 있는 다음 상태들을 보고 허용 토큰을 정한다. 나머지 유효하지 않은 토큰의 확률은 0으로 만들고, 이렇게 토큰을 하나씩 디코딩한다. 그런데 이렇게 토큰을 하나씩 처리하는 방식은 여러 토큰을 한 번에 디코딩할 수 있는 상황에서는 비효율적이다. 예를 들어 그림 2의 상수 시퀀스 `{"summary": "`는 그림 4 (c)처럼 일반 디코딩 과정에서 여러 토큰에 걸쳐 있다. 이를 디코딩할 때 가능한 다음 토큰이 매번 하나뿐인데도 여러 디코딩 단계가 필요하다. 사실 이 시퀀스 전체는 한 단계(즉, 한 번의 순전파)로 디코딩할 수 있다. 하지만 기존 시스템에서는 FSM과 모델 실행기(model runner)가 통합되어 있지 않아 여러 토큰을 한꺼번에 처리하지 못한다. 그래서 한 번에 토큰 하나만 디코딩할 수 있고, 디코딩이 느려진다.

**그림 4.** 일반 FSM과 압축 FSM의 디코딩 과정(밑줄 `_`은 공백을 뜻한다).

> **역주.** (a)는 정규 표현식 `{"summary": "`에 대한 일반 FSM으로, 문자 하나마다 상태가 하나씩 이어진다. (b)는 같은 정규 표현식에 대한 압축 FSM으로, 전체 문자열이 간선 하나로 합쳐져 있다. (c)에서는 토큰 하나마다 LLM 디코딩(육각형)이 한 번씩 들어가지만, (d)에서는 네 토큰을 한꺼번에 붙인 뒤 LLM 디코딩을 한 번만 한다.

SGLang은 압축 FSM으로 빠른 제약 디코딩 런타임을 만들어 이 한계를 극복한다. 이 런타임은 FSM을 분석해, 인접한 단일 전이 간선(singular-transition edge)들을 그림 4 (b)처럼 하나의 간선으로 압축한다. 이를 통해 여러 토큰을 함께 디코딩할 수 있는 경우를 알아낸다. 그림 4 (d)에서는 압축된 전이 간선 위의 여러 토큰을 한 번의 순전파로 디코딩할 수 있어, 디코딩 과정이 크게 빨라진다. 이 방법은 범용적이어서 모든 정규 표현식에 적용할 수 있다. 배경과 구현에 대한 자세한 내용은 부록 B에 있다.

> **역주.** 단일 전이 간선은 다음 상태로 가는 길이 하나뿐이고 그 위에서 허용되는 문자도 하나뿐인 간선이다(정확한 정의는 부록 B.1). 이런 간선에서는 모델이 무엇을 출력할지 이미 정해져 있으므로, 모델에게 물어볼 필요 없이 그 문자열을 바로 붙일 수 있다.

## 5 Efficient Endpoint Calling with API Speculative Execution

앞 절들에서는 오픈 웨이트 모델을 위한 최적화를 소개했다. 이 최적화들은 모델 추론 과정 자체를 수정해야 한다. SGLang은 OpenAI의 GPT-4처럼 API로만 접근할 수 있는 모델도 지원한다. 하지만 이런 모델에서는 블랙박스 API 엔드포인트를 호출하는 것만 가능하다.

이 절에서는 블랙박스 API 모델을 위한 새로운 최적화를 소개한다. 이 최적화는 투기적 실행(speculative execution)을 이용해 다중 호출 SGLang 프로그램의 실행을 가속하고 API 비용을 줄인다. 예를 들어 어떤 프로그램이 다중 호출 패턴으로 캐릭터 설명을 생성하라고 모델에게 요청한다고 하자: `s += context + "name:" + gen("name", stop="\n") + "job:" + gen("job", stop="\n")`. 단순하게 실행하면 두 `gen` 프리미티브가 두 번의 API 호출이 된다. 즉, 사용자는 `context`에 대한 입력 토큰 요금을 두 번 내야 한다. SGLang에서는 첫 번째 호출에 투기적 실행을 켜서, 중단 조건을 무시하고 토큰 몇 개를 더 생성하게 할 수 있다. 인터프리터는 이렇게 추가로 생성된 출력을 보관해 두었다가, 뒤따르는 프리미티브와 매칭해 재사용한다. 프롬프트를 신중하게 설계하면 모델이 템플릿에 맞는 출력을 높은 정확도로 생성하는 경우가 있다. 그런 경우 API 호출 한 번의 지연 시간과 입력 비용을 아낄 수 있다.

> **역주.** 위 예에서 첫 번째 `gen`이 줄바꿈에서 멈추지 않고 계속 생성하면, 출력에 "job: …"까지 들어 있을 수 있다. 인터프리터는 이 추가 출력이 다음 템플릿 `"job:"`과 맞는지 확인하고, 맞으면 그 뒷부분을 두 번째 `gen`의 결과로 그대로 쓴다. 그래서 두 번째 API 호출이 필요 없어진다.

## 6 Evaluation

다양한 LLM 워크로드에서 SGLang의 성능을 평가한다. 이어서 구성 요소를 하나씩 빼거나 바꿔 보는 실험(ablation study)과 사례 연구로 개별 구성 요소의 효과를 보인다. SGLang은 PyTorch [37]로 구현했으며, FlashInfer [59]와 Triton [48]의 맞춤형 CUDA 커널을 사용한다.

### 6.1 Setup

**Models.** 밀집(dense) Llama-2 모델 [49], 희소 전문가 혼합(sparse mixture of experts, 입력마다 일부 전문가 레이어만 활성화하는 구조) Mixtral 모델 [17], 멀티모달 LLaVA 이미지 모델 [27]과 비디오 모델 [62], 그리고 API 모델인 OpenAI의 GPT-3.5를 테스트한다. 오픈 웨이트 모델의 파라미터 수는 70억에서 700억까지이며, float16 정밀도를 사용한다.

**Hardware.** 대부분의 실험은 NVIDIA A10G GPU(24GB)를 탑재한 AWS EC2 G5 인스턴스에서 수행한다. 7B 모델은 A10G GPU 한 장에서, 더 큰 모델은 텐서 병렬화 [44]로 여러 A10G GPU에서 실행한다. 일부 추가 실험은 A100G(80GB) GPU에서 수행한다.

**Baselines.** SGLang을 두 종류의 시스템과 비교한다. 하나는 고수준 프로그래밍 시스템으로, 각자의 언어와 기본 런타임을 그대로 쓴다. 다른 하나는 OpenAI 방식의 표준 Completion API를 제공하는 저수준 추론 엔진이다. 따로 언급하지 않는 한, 계산 결과를 바꾸는 최적화는 켜지 않아 모든 시스템이 같은 결과를 계산하도록 했다. 비교 대상은 다음과 같다.

- Guidance [13]: LLM을 제어하는 언어. llama.cpp 백엔드와 함께 Guidance v0.1.8을 사용한다.
- vLLM [23]: 처리량이 높은 추론 엔진. vLLM v0.2.5와 기본 API 서버를 사용한다.[^2]
- LMQL [4]: 질의 언어. Hugging Face Transformers 백엔드와 함께 LMQL v0.7.3을 사용한다.

[^2]: RadixAttention은 최신 버전의 vLLM에 선택 가능한 실험적 기능으로 일부 통합되었다. 그래서 비교에는 그 이전 버전을 사용했다.

**Workloads.** 다음 작업들을 테스트한다. 5-shot MMLU [14]와 20-shot HellaSwag [61] 벤치마크를 쓴다. MMLU에서는 토큰 하나를 디코딩하고, HellaSwag에서는 `select` 프리미티브로 확률이 가장 높은 답을 고른다. ReAct 에이전트 [57]와 생성형 에이전트(generative agents) [36]는 원 논문에서 실행 기록(trace)을 추출해 그대로 재생한다. GSM-8K 문제에는 Tree-of-thought [56]를, 팁 생성에는 Skeleton-of-thought [33]를 사용한다. branch-solve-merge [40] 기법을 쓰는 LLM 심사(LLM judge)를 사용한다. 정규 표현식으로 지정한 스키마에 맞춰 JSON을 디코딩한다. 멀티턴 채팅은 4턴이며, 각 턴의 입력 길이는 256\~512 토큰 사이에서 무작위로 뽑는다. 멀티턴 채팅(short)은 짧은 출력(4\~8 토큰), 멀티턴 채팅(long)은 긴 출력(256\~512 토큰)을 뜻한다. 마지막으로 DSPy의 공식 예제에 있는 검색 증강 생성(RAG) 파이프라인 [20]을 사용한다.

> **역주.** ReAct는 LLM이 추론(reasoning)과 행동(acting, 예: 검색 도구 호출)을 번갈아 수행하는 에이전트 방식이다. 생성형 에이전트는 여러 LLM 캐릭터가 가상 마을에서 기억을 쌓으며 상호작용하는 시뮬레이션이다. 두 경우 모두 원 논문의 실제 호출 기록을 다시 실행해 워크로드로 썼다는 뜻이다.

**Metrics.** 처리량(throughput)과 지연 시간(latency) 두 가지 성능 지표를 보고한다. 처리량은 충분히 큰 프로그램 인스턴스 배치를 실행해 최대 처리량을 구하고, 초당 실행한 프로그램 인스턴스 수(programs per second, p/s)로 비교한다. 지연 시간은 배칭 없이 한 번에 프로그램 하나씩 실행해, 여러 인스턴스에 대한 평균을 보고한다.

### 6.2 End-to-End Performance

**Results on open-weight models.** 지연 시간과 처리량 결과는 그림 5와 그림 6에 있다. SGLang은 처리량을 최대 {{< katex >}}6.4\times{{< /katex >}} 높이고 지연 시간을 최대 {{< katex >}}3.7\times{{< /katex >}} 줄인다. 이런 개선은 KV 캐시 재사용, 단일 프로그램 내부의 병렬성 활용, 더 빠른 제약 디코딩에서 나온다. 아래에서 벤치마크별로 속도가 빨라진 이유를 설명한다.

MMLU에서 SGLang은 RadixAttention으로 5-shot 예제의 KV 캐시를 재사용할 수 있다. RadixAttention은 처리량과 지연 시간 모두에 도움이 된다. KV 캐시를 공유하면 전체 메모리 사용량이 줄어 배치 크기를 키울 수 있고, 그만큼 최대 처리량이 높아진다. 또한 프리필(prefill, 입력 토큰 전체를 한 번에 처리하는 단계) 계산이 줄어 첫 토큰 지연 시간도 줄어든다. HellaSwag에서 SGLang은 퓨샷 예제의 KV 캐시와, 여러 선택지가 공유하는 공통 질문 접두사의 KV 캐시를 모두 재사용한다. 즉, 두 단계의 공유가 일어난다. ReAct 에이전트와 생성형 에이전트에서 SGLang은 에이전트 템플릿과 이전 호출의 KV 캐시를 재사용한다. Tree-of-thought와 Skeleton-of-thought에서는 한 프로그램 안의 생성 호출들을 병렬로 실행하고, KV 캐시를 최대한 재사용한다. JSON 디코딩에서는 압축 유한 상태 기계로 여러 토큰을 한 번에 디코딩해 디코딩을 가속한다. 멀티턴 채팅에서는 채팅 기록의 KV 캐시를 재사용한다. 이 속도 향상은 짧은 출력에서 더 뚜렷하다. KV 캐시 재사용은 주로 접두사 처리 시간을 줄이는 데 도움이 되기 때문이다. 긴 출력에서는 서로 다른 채팅 세션 사이에 공유되는 부분이 많지 않고 디코딩 시간이 대부분을 차지하므로, 속도 향상이 거의 없다. DSPy RAG 파이프라인에서 SGLang은 요청들이 공통으로 쓰는 맥락 예제(context example)의 KV 캐시를 재사용한다. 이 벤치마크들에서 캐시 적중률은 50%에서 99% 사이다. 그림 13(부록)에 모든 벤치마크의 실제 캐시 적중률과 최적 캐시 적중률을 정리했다. 이를 보면 본 논문의 캐시 인식 스케줄링은 평균적으로 최적 적중률의 96%에 이른다.

> **역주.** "최대 {{< katex >}}6.4\times{{< /katex >}}"와 "최대 {{< katex >}}3.7\times{{< /katex >}}"는 각각 그림 5·그림 6의 여러 벤치마크와 비교 대상 가운데 가장 큰 차이를 말한다. 벤치마크마다 개선 폭은 다르며, 멀티턴 채팅(long)처럼 거의 차이가 없는 경우도 있다.

그림 5·6의 마지막(오른쪽) 다섯 벤치마크 중 일부에서는 LMQL과 Guidance를 제외했다. 성능이 너무 느리거나 필요한 기능이 없기 때문이다. LMQL은 토큰 단위 처리가 느리고 백엔드가 최적화되어 있지 않다. Guidance는 배칭과 병렬 처리를 지원하지 않는다.

### 6.3 Ablation Study

**Cache hit rate vs. latency/throughput.** 그림 8(a)(b)는 tree-of-thought 벤치마크에서 캐시 적중률과 성능 지표(첫 토큰 지연 시간, 전체 지연 시간, 배치 크기, 처리량) 사이의 관계를 보여 준다. 캐시 적중률을 여러 값으로 맞추기 위해, 런타임에서 매칭된 토큰 일부를 일부러 쓰지 않게 해서 이 그림을 얻었다. 그림을 보면 캐시 적중률이 높을수록 배치 크기가 커지고, 처리량이 높아지며, 지연 시간이 줄어든다.

**Effectiveness of RadixAttention.** 몇 가지 대표 벤치마크에서 RadixAttention과 그 구성 요소의 효과를 테스트했다. 그림 8(c)의 각 설정은 다음과 같다. "No Cache"는 캐시를 전혀 쓰지 않는다. "No Tree-Structure"는 트리 구조 캐시 대신 단순한 테이블 기반 캐시를 쓴다. "FCFS Schedule"은 캐시 인식 스케줄링 대신 선착순(first-come-first-serve) 정책을 쓴다. "Random Schedule"은 요청을 무작위 순서로 스케줄링한다. "No Frontend Parallelism"은 인터프리터의 병렬 처리를 끈다. "No Frontend Hint"는 인터프리터가 fork 힌트를 보내지 않게 한다. "Full optimizations"는 모든 최적화를 켠 것이다. 실험 결과, 최고 성능을 내려면 이 구성 요소가 모두 필요했다. 프런트엔드 인터프리터의 병렬 처리와 힌트를 꺼도 런타임 성능이 최적보다 떨어졌다. 이는 프런트엔드 언어와 런타임을 함께 설계하는 것이 중요함을 보여 준다.

**Overhead of RadixAttention.** KV 캐시를 재사용할 기회가 전혀 없는 벤치마크에서 RadixAttention의 오버헤드를 측정했다. 이 벤치마크는 ShareGPT 데이터셋에서 처리량을 측정한다. 요청 100개를 실행하는 데 74.3초가 걸렸고, 그중 RadixAttention 자료 구조를 관리하는 데 쓴 시간은 0.2초뿐이었다. 0.3% 미만의 무시할 만한 오버헤드다. 트리 연산의 복잡도가 (토큰 수에 대해) 선형이고 작기 때문이다. 따라서 RadixAttention을 기본으로 켜 둘 수 있다.

**Effectiveness of the compressed finite state machine.** JSON 디코딩 벤치마크에서 압축 유한 상태 기계와 그 구성 요소의 효과를 테스트했다. 실험 결과, 압축 유한 상태 기계는 여러 토큰을 한 번에 디코딩할 수 있어 처리량을 {{< katex >}}1.6\times{{< /katex >}} 높였다. 또한 상태 기계는 미리 전처리해 두고 요청 배치 전체에서 재사용해야 한다. 요청마다 전처리를 다시 하면 처리량이 {{< katex >}}2.4\times{{< /katex >}} 낮아진다.

## 7 Related Work

KV 캐시 재사용을 다룬 연구는 여럿 있으며, 그중 상당수는 본 연구와 같은 시기에 진행되었다. 본 논문의 RadixAttention이 다른 점은 KV 캐시를 트리 기반 LRU 캐시로 다루자고 처음 제안했다는 것이다. RadixAttention은 다단계 공유(6.2절 HellaSwag처럼 접두사를 여러 층으로 겹쳐 공유하는 것), 캐시 인식 스케줄링, 프런트엔드-런타임 공동 스케줄링(3절의 프런트엔드 힌트처럼 프런트엔드가 런타임 스케줄링을 돕는 것), 분산 환경을 모두 지원하는 첫 해법이다. vLLM [23]과 ChunkedAttention [58]은 몇 가지 단순한 재사용 사례(예: 시스템 프롬프트 공유)를 다루지만, 다단계 트리 구조 공유나 LRU 캐싱은 다루지 않는다. PromptCache [12]는 접두사를 넘어 KV 캐시를 모듈 단위로 재사용하자고 제안하지만, 정확도가 최대 43%까지 떨어질 수 있다. HydraGen [18], FlashInfer [59], ChunkedAttention [58]은 CUDA 커널 최적화에 집중하며 LRU 캐시 개념은 포함하지 않는다. API Serve [1]와 LLM-SQL [29]은 특정 애플리케이션을 위한 KV 캐시 재사용을 연구한다. API Serve는 LLM 생성이 외부 API 호출과 번갈아 일어나는 경우를, LLM-SQL은 관계형 데이터베이스를 다룬다. 하지만 두 연구에는 본 논문의 기수 트리나 캐시 인식 스케줄링이 없다.

LLM 프로그래밍·에이전트 프레임워크도 여럿 있다. Guidance [13], LMQL [4], DSPy [20], LangChain [24], AutoGen [55], LLM Compiler [21] 등이다. 이 가운데 SGLang과 가장 비슷한 것은 Guidance와 LMQL이며, 2절에서 이들과 비교했다. 본 논문의 새로움은 제안한 프로그래밍 모델을 가속하는 새로운 런타임 최적화에 있다. SGLang은 다른 프레임워크와 호환되며, 그 프레임워크들을 가속할 수 있다(예: 평가에서 다룬 DSPy 예제). 또한 SGLang은 흔히 쓰이는 다른 여러 추론 최적화 [60, 39, 3, 23, 59, 10, 26, 15, 19, 32, 31, 11]와도 함께 쓸 수 있다.

## A Additional Details on RadixAttention

### A.1 Background on the KV Cache

GPT-3 [5], PaLM [9], LLaMA [49] 등 오늘날 쓰이는 LLM 대부분은 자기회귀(autoregressive) Transformer 구조 [51]에 기반한다. 이 모델들은 앞선 토큰들을 바탕으로 시퀀스의 다음 토큰 확률을 예측한다. 추론할 때 모델은 먼저 입력 토큰 시퀀스를 순전파로 처리한다. 이 과정을 "프리필(prefill)"이라 부른다. 이어서 출력 토큰을 하나씩 순서대로 디코딩하며, 각 토큰은 앞선 토큰들에 의존한다. 이 과정을 "디코딩(decoding)"이라 부른다. 입력 토큰 시퀀스를 받아 출력 토큰 시퀀스를 생성하는 과정 전체를 하나의 생성 호출(single-generation call)이라 부른다. 이 과정 내내 각 토큰은 중간 텐서를 만들고, 이 텐서들은 이후 토큰을 디코딩하는 데 쓰인다. 이 중간 텐서를 "KV 캐시"라 부르며, 이름은 셀프 어텐션 메커니즘의 key-value 쌍에서 따왔다. 본 논문의 최적화를 논의할 때 중요한 관찰이 하나 있다. KV 캐시 계산은 앞선 모든 토큰에만 의존한다. 그러므로 접두사가 같은 서로 다른 시퀀스는 접두사 토큰의 KV 캐시를 재사용해 중복 계산을 피할 수 있다.

LLM 프로그램에서는 여러 텍스트 조각과 생성 호출이 하나의 프롬프트에 차례로 덧붙는 경우가 많다. 이렇게 연결된 여러 호출에 걸쳐, 이전 토큰들에 대해 계산한 KV 캐시를 저장해 두면 중복 계산을 줄일 수 있다. 하지만 이 최적화는 공짜도 아니고 간단하지도 않다. 추가 저장 공간과 더 복잡한 메모리 관리가 필요하기 때문이다. 또한 LLM 프로그램에서는 프롬프트 하나에서 여러 출력을 생성하거나, 현재 상태에서 새 프롬프트를 갈라내는(fork) 일이 흔하다 [25]. 기본적인 접두사 공유는 vLLM [23]에서 연구된 바 있다. 하지만 LLM 프로그램에서는 불규칙한 트리 구조 공유처럼 더 복잡한 공유 패턴도 활용할 수 있다. 그림 9는 여러 호출에 걸친 KV 캐시 공유의 대표적인 네 가지 패턴을 보여 준다. 기존 시스템 중 이 패턴들을 모두 자동으로 처리하는 것은 없다. 반대로 3절의 RadixAttention은 런타임에 이 패턴들을 모두 자동으로 처리할 수 있다.

### A.3 Proof of the Theorem 3.1

**정리 3.1 (Theorem 3.1).** 요청 배치가 주어지고 캐시 크기가 최대 요청 길이 이상({{< katex >}}\geq{{< /katex >}})이면, 요청들의 기수 트리를 깊이 우선 탐색(DFS) 순서로 방문해 최적의 캐시 적중률을 달성할 수 있다. 최장 공유 접두사 우선 순서는 깊이 우선 탐색 순서와 같다.

*증명.* 먼저 깊이 우선 탐색(DFS) 순서가 최적의 캐시 적중률을 달성함을 보인다. {{< katex >}}R{{< /katex >}}을 배치 안의 요청 집합, {{< katex >}}T{{< /katex >}}를 {{< katex >}}R{{< /katex >}}로 만든 기수 트리라 하자. {{< katex >}}T{{< /katex >}}의 각 간선 {{< katex >}}e{{< /katex >}}에 대해, {{< katex >}}e{{< /katex >}}에 연결된 KV 캐시는 적어도 한 번은 계산해야 한다. {{< katex >}}e{{< /katex >}}에 연결된 KV 캐시의 크기를 {{< katex >}}|e|{{< /katex >}}로 쓰자. {{< katex >}}R{{< /katex >}}의 KV 캐시를 계산하는 계산량을 {{< katex >}}C{{< /katex >}}라 하자. 그러면 다음 하한을 얻는다.

{{< katex display=true >}}
C \geq \sum_{e \in \text{edges}(T)} |e|.
{{< /katex >}}

이제 기수 트리 {{< katex >}}T{{< /katex >}}를 DFS 순서로 방문한다고 하자. {{< katex >}}T{{< /katex >}}의 각 간선 {{< katex >}}e{{< /katex >}}에 대해, {{< katex >}}e{{< /katex >}}에 연결된 KV 캐시를 처음 계산하고 나면 곧이어 {{< katex >}}e{{< /katex >}} 아래의 서브트리 전체를 계산한다. {{< katex >}}e{{< /katex >}}의 서브트리를 계산하는 동안 간선 {{< katex >}}e{{< /katex >}}는 계속 캐시에 적중하므로 추가 계산이 생기지 않는다. {{< katex >}}e{{< /katex >}}를 루트로 하는 서브트리 계산이 끝나면 간선 {{< katex >}}e{{< /katex >}}는 다시 방문되지 않는다. 여기서 캐시 크기가 최대 요청 길이(기수 트리 {{< katex >}}T{{< /katex >}}에서 가장 긴 경로의 길이와 같다) 이상이면, {{< katex >}}e{{< /katex >}}의 서브트리를 계산하는 동안 간선 {{< katex >}}e{{< /katex >}}는 제거되지 않는다는 점에 주목하자. 서브트리의 공통 접두사(여기에는 {{< katex >}}e{{< /katex >}}가 포함된다)가 계속 적중하기 때문이다. 따라서 각 간선 {{< katex >}}e{{< /katex >}}에 연결된 KV 캐시는 정확히 한 번만 계산된다. 즉, 하한을 달성한다.

{{< katex display=true >}}
C = \sum_{e \in \text{edges}(T)} |e|.
{{< /katex >}}

캐시 적중률은 다음과 같이 정의된다.

{{< katex display=true >}}
\frac{\sum_{r\in R}\text{number of cached prefill tokens in } r}{\sum_{r\in R}\text{number of prefill tokens in } r},
{{< /katex >}}

이 값은 {{< katex >}}1 - \frac{C}{\sum_{r\in R}\text{number of prefill tokens}}{{< /katex >}}와 같다. {{< katex >}}C{{< /katex >}}가 하한에 도달했으므로 캐시 적중률은 상한에 도달하고, 따라서 최적이다.

> **역주.** 위 정의의 분자는 "요청 {{< katex >}}r{{< /katex >}}의 프리필 토큰 중 캐시에서 찾은 토큰 수"의 합, 분모는 "요청 {{< katex >}}r{{< /katex >}}의 프리필 토큰 수"의 합이다. 캐시에서 찾지 못한 토큰은 새로 계산해야 하고 그 양이 {{< katex >}}C{{< /katex >}}이므로, 적중률은 {{< katex >}}1-C/(\text{전체 프리필 토큰 수}){{< /katex >}}가 된다. 이 증명에서 {{< katex >}}C{{< /katex >}}는 계산량을 뜻하지만, 뒤의 온라인 경우 설명에서는 {{< katex >}}C{{< /katex >}}가 캐시된 노드의 집합을 뜻한다.

다음으로, 최장 공유 접두사 우선 순서가 DFS 순서와 같음을 귀납법으로 보인다.

- (기저) 처음에는 캐시된 것이 없으므로, {{< katex >}}T{{< /katex >}}의 어떤 노드 {{< katex >}}x{{< /katex >}}에 해당하는 임의의 요청 하나가 처리된다. {{< katex >}}x{{< /katex >}}의 요청을 처리하면 루트에서 {{< katex >}}x{{< /katex >}}까지의 경로 전체의 KV 캐시가 계산된다. 그래서 이 경로 위에 있는 노드 {{< katex >}}\{v_1, ..., v_n\}{{< /katex >}}에서 끝나는 요청들은 다시 계산할 필요가 없다. 노드 {{< katex >}}\{v_1,..., v_n, x\}{{< /katex >}}에서 끝나는 요청들의 계산은 유효한 DFS와 일치한다. 루트에서 {{< katex >}}x{{< /katex >}}까지의 경로는 캐시된다.
- (귀납) 방금 {{< katex >}}T{{< /katex >}}의 노드 {{< katex >}}y{{< /katex >}}를 방문했고, 지금까지 방문한 노드들이 DFS 순서와 일치한다고 가정하자. 루트에서 {{< katex >}}y{{< /katex >}}까지의 경로를 {{< katex >}}P{{< /katex >}}라 하자. 그러면 아직 방문하지 않은 각 노드는 방문한 노드들과의 최소 공통 조상(lowest common ancestor)을 {{< katex >}}P{{< /katex >}} 위에 가진다. {{< katex >}}P{{< /katex >}} 위의 노드들은 캐시되어 있으므로, 방문하지 않은 노드 가운데 최소 공통 조상이 {{< katex >}}P{{< /katex >}} 위에 있는 노드 {{< katex >}}z{{< /katex >}}가 가장 긴 공유 접두사를 가진다. 최장 공유 접두사 우선 순서는 {{< katex >}}z{{< /katex >}}를 선택하며, 이는 유효한 DFS 순서다. 루트에서 {{< katex >}}z{{< /katex >}}까지의 경로는 가장 최근에 쓰였으므로 캐시된다. ∎

> **역주.** 귀납 단계의 {{< katex >}}P{{< /katex >}}는 경로를 뜻하며, 알고리즘 1의 메모리 풀 {{< katex >}}P{{< /katex >}}와는 다른 기호다. 원문은 {{< katex >}}z{{< /katex >}}를 고르는 기준을 짧게만 적었는데, 방문하지 않은 노드 가운데 {{< katex >}}P{{< /katex >}}와의 최소 공통 조상이 가장 깊은(루트에서 가장 먼) 노드를 고른다는 뜻으로 읽힌다. 그런 노드가 캐시된 경로와 가장 긴 접두사를 공유하기 때문이다.

온라인 경우에는 DFS 순서가 깨진다. 하지만 최장 공유 접두사 스케줄은 여전히 DFS 동작을 근사한다. 지금까지 도착한 모든 요청으로 기수 트리를 만든다고 생각하자(실제로 따로 만들지는 않는다). 스케줄러는 그중 새 요청으로 늘어난 부분을 DFS에 가깝게 처리한다. 새 요청 배치를 추가하는 단계를 생각해 이를 보인다.

{{< katex >}}T{{< /katex >}}는 기수 트리 가운데 지금까지 방문한 부분이다. {{< katex >}}T'{{< /katex >}}은 새 요청 배치를 추가한 뒤의 기수 트리 전체다. {{< katex >}}C{{< /katex >}}는 {{< katex >}}T{{< /katex >}} 안에서 캐시된 노드의 집합이다. {{< katex >}}\text{longest}(C){{< /katex >}}는 다음 조건을 만족하는 노드다. 먼저 {{< katex >}}C{{< /katex >}}에 속하고, {{< katex >}}T'{{< /katex >}}에서 그 아래에 아직 방문하지 않은 부분이 남아 있어야 한다. 이런 노드 가운데 루트로부터의 경로가 가장 긴 노드가 {{< katex >}}\text{longest}(C){{< /katex >}}다.

그러면 최장 공유 접두사 스케줄은 {{< katex >}}T'{{< /katex >}}에서 {{< katex >}}\text{longest}(C){{< /katex >}}를 루트로 하는 서브트리를 DFS 순서로 처리한다. 이 과정에서 제거가 일어날 수 있으며, {{< katex >}}C{{< /katex >}}에서 남은 캐시 노드들은 {{< katex >}}C^{(1)} \subseteq C{{< /katex >}}가 된다. 이어서 {{< katex >}}T'{{< /katex >}}에서 {{< katex >}}\text{longest}(C^{(1)}){{< /katex >}}를 루트로 하는 서브트리에 대해 DFS가 일어난다.

마찬가지로 {{< katex >}}C^{(2)}, \ldots, C^{(k)}{{< /katex >}}를 얻는다. 이 과정은 {{< katex >}}C^{(k)}{{< /katex >}}에 리프 노드가 하나만 남을 때까지 계속된다. 이 리프는 {{< katex >}}T{{< /katex >}}에서는 리프지만, {{< katex >}}T'{{< /katex >}}에서는 그 아래에 아직 방문하지 않은 서브트리가 있는 노드다. 이 시점에서 유효한 DFS 상태에 도달한다. {{< katex >}}T'{{< /katex >}}의 나머지 부분은 정리 3.1의 증명에서 설명한 대로 DFS 순서로 방문된다.

### A.4 Data-Parallel Distributed RadixAttention

여러 복제 워커(replica worker)가 있는 분산 환경(즉, 데이터 병렬화)에 RadixAttention을 적용하는 메커니즘을 개발했다. 이 메커니즘에서 각 워커는 자신의 서브트리를 유지한다. 요청을 워커에 나눠 주는 라우터(router)는 메타 트리(meta-tree)를 관리한다. 이 메타 트리는 모든 서브트리와 그에 연결된 장치를 추적하는 트라이 역할을 한다. 새 요청 배치가 라우터에 도착하면 메타 트리에서 접두사 매칭을 수행한다. 각 요청의 친화도(affinity)에 기반한 여러 정책을 구현해, 중복 계산을 최소화하도록 요청을 효율적으로 배분한다. 친화도는 요청이 특정 워커와, 그리고 같은 그룹(group)에 속한 다른 요청과 접두사를 얼마나 길게 공유하는지로 측정한다. 새 요청이 처리될 때마다 라우터와 워커는 각자의 트리를 독립적으로 갱신한다. 워커 노드에서 제거가 일어나면 워커는 그 제거를 큐에 기록하고, 라우터는 부하가 적은 시간에 이 큐를 처리해 메타 트리를 갱신한다. 워커 4개와 MMLU 데이터셋으로 이 분산 구성을 벤치마크했다. 그 결과, 약한 일관성(weakly consistent)을 갖는 이 분산 캐시 설계는 오버헤드가 아주 작으면서도 선형 확장과 최적 캐시 적중률을 달성했다. 데이터 지역성(data locality)을 최대화하는 것과 병렬 처리 효율 사이에는 트레이드오프가 있다. 이 트레이드오프를 최적화하는 고급 스케줄링 정책은 향후 연구 과제로 남긴다. 또한 같은 시기의 연구인 Preble [45]은 초기 버전의 SGLang을 바탕으로 데이터 병렬 스케줄링을 연구했다.

> **역주.** "약한 일관성"이란 라우터의 메타 트리가 워커의 실제 캐시 상태를 즉시 반영하지 않는다는 뜻이다. 워커에서 일어난 제거는 큐를 거쳐 나중에 메타 트리에 반영되므로, 그 사이에는 라우터가 이미 제거된 캐시를 있다고 볼 수 있다.

## B Additional Details on Compressed Finite State Machine

이 절에서는 더 빠른 제약 디코딩을 위한 압축 유한 상태 기계의 배경과 구현 세부 사항을 다룬다. 목표는 LLM이 정규 표현식(regex)을 따르게 하는 것이다. 정규 표현식은 표현력이 높아 JSON 스키마 같은 흔한 형식을 나타낼 수 있다. 이를 위해 정규 표현식을 유한 상태 기계(FSM)로 변환해, 디코딩하는 동안 생성 과정을 안내한다 [54]. FSM은 본질적으로 노드(상태)와 간선(문자열·문자가 붙은 전이)으로 이루어진 그래프다. 초기 상태에서 출발해, 전이할 때마다 간선 위의 문자열을 덧붙이며 다음 상태로 이동한다. 종료 상태들의 집합에 도달하면 과정이 끝난다. 그림 10처럼 이 메커니즘은 FSM의 현재 상태에서 가능한 전이를 기준으로 유효하지 않은 토큰을 걸러 내 LLM의 디코딩을 안내한다. 디코딩은 종료 상태에 도달할 때까지 FSM에서 여러 번 전이할 수 있다.

제약 디코딩이 어려운 이유는 제약이 흔히 사람이 읽는 텍스트 형식으로 표현된다는 데 있다(원문 표현은 "natural language formats"). 즉, 정규 표현식은 문자·문자열로 기술되는데, LLM은 이를 토큰 단위로 해석하고 처리하도록 설계되어 있다. 문자열과 토큰 사이의 대응은 복잡하고 일대일이 아니므로 [22], 상황이 복잡해진다.

> **역주.** 예를 들어 같은 문자열 `summary`도 토크나이저에 따라 토큰 하나일 수도 있고 `summa`+`ry`처럼 여러 토큰일 수도 있다. 반대로 토큰 하나가 정규 표현식의 여러 문자에 걸칠 수도 있다. 그래서 문자 단위로 만든 FSM을 토큰 단위 디코딩에 맞추는 작업이 필요하다.

### B.1 Implementation Details of Compressed Finite State Machine

압축 FSM을 쉽게 만들기 위해, 원래 FSM을 토큰이 아닌 문자·문자열 단위로 구성한다. 단일 전이 간선과 압축 간선의 개념을 다음과 같이 형식적으로 정의한다.

- 단일 전이 간선(singular transition edge): 다음 두 조건을 만족하는 간선이다. 1) 출발 노드의 다음 노드가 하나뿐이고, 2) 간선 위에서 허용되는 문자·문자열이 하나뿐이다.
- 압축 간선(compressed edge): 연속으로 인접한 여러 간선 {{< katex >}}(e_0, e_1, \ldots, e_k){{< /katex >}}를 압축한 간선이다. 이렇게 압축할 수 있는 것은 {{< katex >}}e_1, \ldots, e_k{{< /katex >}}가 모두 단일 전이 간선일 때, 그리고 그때뿐이다. 압축 간선의 텍스트는 {{< katex >}}e_0, e_1, \ldots, e_k{{< /katex >}}의 텍스트를 이어 붙인 것이다.

> **역주.** 정의에서 첫 간선 {{< katex >}}e_0{{< /katex >}}은 단일 전이 간선이 아니어도 된다. 즉, 선택지가 여럿인 간선 뒤에 "정해진 길"이 이어지면, 그 길을 앞 간선에 붙여 하나로 만든다.

문자 단위 FSM에서 시작해, 더 이상 압축할 수 없을 때까지 단일 전이 간선을 앞 간선에 재귀적으로 병합하면 압축 FSM이 된다. 이 방식은 디코딩 과정을 빠르게 한다. 그림 11은 압축 FSM을 쓰는 SGLang 런타임이 얼마나 효율적인지 보여 준다.

### B.2 Handling Tokenization Artifacts with Retokenization

새 토큰이 생성되면 런타임은 먼저 그 토큰의 문자열을 얻는다. 그리고 현재 상태에서 나가는 간선 가운데 이 문자열로 시작하는 간선을 찾아, 그 간선을 따라 다음 상태로 이동한다. 특히 전이 간선이 잘 압축되어 아주 긴 문자열을 담고 있으면, 다음 몇 라운드에서 디코딩될 문자열까지 미리 알 수 있다. 바로 여기서 가속이 일어나며, 이 과정을 *점프 포워드(Jump Forward)*\ 라 부른다. 하지만 다음 디코딩 단계를 위해서는 이 문자열을 다시 토큰으로 바꿔야 한다. LLM마다 사전 학습 방식과 토큰화 방식이 다르기 때문에 이 작업은 간단하지 않다. 문자열을 아무렇게나 나누면 의도한 의미가 바뀔 수 있다 [50]. 예를 들어 그림 2의 정규 표현식에서 압축된 텍스트는 `{"summary": "`이다. 토크나이저에 따르면 이 텍스트는 `{"`, `summary`, `":`, `_"`로만 토큰화된다. `{"`, `summa`, `ry`, `":_"`처럼 임의로 나누면 안 된다. 이 문제를 해결하기 위해 원래 토크나이저로 이전 텍스트 전체와 압축 간선의 텍스트를 다시 토큰화(retokenize)한다. 그러면 LLM이 원래 받는 입력 형식과 맞출 수 있다. 재토큰화의 오버헤드는 작다.

> **역주.** 같은 문자열이라도 학습 때 본 적 없는 방식으로 토큰을 나누면, 모델은 그 입력을 낯설게 받아들여 이후 출력의 품질이 떨어질 수 있다. 재토큰화는 점프 포워드로 붙인 텍스트를 토크나이저가 원래 나눴을 방식 그대로 다시 나누어 이 문제를 피한다.

### B.3 Future Extension: Addressing Distorted Probability

문자열과 토큰 사이의 차이는 확률 분포가 왜곡되는 문제도 일으킨다 [50]. 예를 들어 그림 2에서 정규 표현식 `"[ABCD][+-]?"`는 `A+`부터 `D-`까지의 등급을 뜻한다. 그런데 이를 `Excellent|Above Average|Fair|Below Average`처럼 단어로 된, 더 넓은 범위의 표현으로 바꾸면 문제가 생길 수 있다. `Above Average`가 압축된 전이 위에 있기 때문에, 런타임이 `A`를 `Above Average`로 잘못 대응시킬 수 있다. 그러면 등급의 위계가 잘못 표현된다. 이런 일이 생기는 이유는 LLM이 어떤 선택지가 가능한지 모른 채 토큰을 고르기 때문이다. 그래서 부적절한 토큰 시퀀스가 만들어진다. 각 선택지의 정확한 확률을 계산하려면, 그 선택지가 되는 모든 토큰 시퀀스의 확률을 더해야 한다. 이는 디코딩을 복잡하게 하고 오버헤드를 늘린다. 한 가지 우회책은 선택지나 정규 표현식을 프리필 프롬프트에 직접 넣는 것이다. 그러면 LLM이 선택지를 알고 결정을 적절한 토큰 시퀀스로 출력하도록 유도할 수 있다. 하지만 이 방법은 확률 왜곡이라는 근본 문제를 해결하지 못한다. 따라서 압축 FSM의 정확도를 높이기 위한 추가 연구가 필요하다.

> **역주.** 위 예를 풀면 다음과 같다. 선택지가 `Excellent`, `Above Average`, `Fair`, `Below Average`일 때, 모델이 "최고 등급"이라는 뜻으로 첫 글자 `A`(A+ 같은 등급을 떠올리며)를 고르면, `A`로 시작하는 선택지는 `Above Average`뿐이므로 나머지가 압축 전이로 자동 완성된다. 모델이 실제로 의도한 것은 가장 높은 등급이었는데 결과는 두 번째 등급이 되는 셈이다.

## D Compiler Mode

본문에서 사용한 인터프리터 모드 외에, SGLang 프로그램을 실행하는 또 다른 방법은 프로그램을 계산 그래프로 컴파일해 그래프 실행기로 실행하는 것이다. 그래프를 다시 쓰고 정적 계획을 더 많이 세울 수 있으므로, 컴파일 최적화의 기회가 더 많아진다.

### D.1 Design and Implementation

SGLang용 중간 표현(intermediate representation, IR)을 설계했다. 이 IR은 SGLang 프로그램의 구조와 연산을 계산 그래프로 나타낸다. 그래프의 노드는 프리미티브 연산자이고, 간선은 의존 관계다. 그림 14a의 프로그램에 대응하는 그래프는 그림 14b에 있다. 프로그램에서는 데코레이터가 붙은 함수를 호출하거나 fork를 할 때마다 새 프롬프트 상태, 즉 새 스트림이 생긴다.

노드에는 여러 종류가 있다. SGLang 프로그램에서 연산자 `+=`와 `+`의 각 피연산자는 IR 노드 하나로 표현된다. 노드 종류는 `ConstantText`, `Argument`, `Gen`, `Select`, `Variable`, `Fork`, `GetForkItem`, `Join`이다. 의존 관계에는 두 종류가 있다. 첫째는 스트림 내부 의존(intra-stream dependency)이다. `+=`로 스트림에 제출된 연산은 그 스트림의 앞선 연산이 모두 끝난 뒤에 실행되어야 한다. 둘째는 스트림 간 의존(inter-stream dependency)이다. 한 스트림이 다른 스트림의 변수 값을 가져와야 할 때 생기며, 동기화가 필요하다. fork 같은 연산은 여러 스트림을 다루므로 스트림 간 의존을 만든다.

그래프를 만들기 위해 트레이싱을 쓴다. 즉, 추상적인 인자로 프로그램을 실행하면서 그래프를 동적으로 구성한다. 이 방법은 데이터에 따라 달라지는 제어 흐름이 없는 프로그램에만 쓸 수 있으며, 이 한계는 향후 해결할 계획이다. 그래프를 만들고 나면 그래프 실행기로 실행할 수 있으므로, 원래 Python 프로그램을 다시 해석할 필요가 없다. 그 결과 그래프 재작성 최적화, 런타임 오버헤드 감소, 프로그램 직렬화 같은 이점을 얻는다. 실행할 때는 데이터 스트림마다 스트림 실행기를 띄우고, IR 노드를 위상 정렬(topological order) 순서로 각 스트림에 보낸다.

> **역주.** "데이터에 따라 달라지는 제어 흐름"이란 그림 2의 `if s["related"] == "no": return`처럼 생성 결과에 따라 실행 경로가 달라지는 코드를 말한다. 트레이싱은 실제 값 없이 추상 인자로 한 번 실행하므로, 이런 분기의 어느 쪽을 그래프에 넣어야 할지 알 수 없다.

### D.2 A Case Study of Compiler Optimization: Code Movement for Improving Prefix Sharing

SGLang IR에 대한 컴파일 최적화로, 접두사 공유를 늘리기 위한 코드 이동(code movement)을 살펴본다. 자동 튜닝(auto-tuning)이나 명령어 선택(instruction selection) 같은 고전적인 컴파일러 기법도 더 적용할 수 있을 것으로 예상한다.

이 최적화의 목표는 그래프의 노드 순서를 바꿔 상수 접두사를 길게 만들어 접두사 공유를 늘리는 것이다. 이 최적화는 원래 계산을 엄밀하게 보존하지 않으므로 공격적인(aggressive) 최적화로 분류된다. 예를 들어 프롬프트를 "Here is a question + {question}. Please act as a math expert and solve the given question."에서 "Please act as a math expert and solve the given question. Here is a question + {question}."으로 바꾸면 공유 가능한 접두사가 길어진다. 이 최적화가 흥미로운 이유는, SGLang에는 자연어 지시문이 들어 있어 전통적인 프로그램 분석으로는 이를 할 수 없기 때문이다. 그래서 GPT-4에게 프롬프트를 주어 그래프 노드의 순서를 바꾸게 한다. 몇 가지 예시가 담긴 프롬프트를 작성해 GPT-4에게 SGLang IR의 개념을 가르쳤다. 그 결과 GPT-4가 몇몇 간단한 SGLang 프로그램에 이 최적화를 성공적으로 적용할 수 있음을 확인했다.

> **역주.** 예시에서 원래 프롬프트는 질문마다 다른 `{question}`이 앞쪽에 있어, 그 뒤의 공통 지시문 "Please act as a math expert …"를 요청끼리 공유할 수 없다. 지시문을 앞으로 옮기면 모든 요청이 이 지시문을 공통 접두사로 가지므로 KV 캐시를 재사용할 수 있다. 다만 문장 순서가 바뀌므로 모델이 받는 입력은 원래와 다르다.

이 최적화의 효과를 평가했다. 인터넷에서 프롬프트 템플릿 20개를 모아 SGLang으로 구현했다. 그중 5개는 퓨샷 학습 예시로 쓰고, 나머지 15개를 테스트 사례로 썼다. 평가 결과, 15개 템플릿 중 12개에서 GPT-4가 의미를 바꾸지 않고 그래프 노드 순서를 성공적으로 바꿨다. 의미 보존 여부는 수정된 프롬프트를 사람이 직접 검사해 확인했다. 평균적으로 이 최적화는 공유 가능한 접두사 길이를 60토큰 늘렸으며, GPT-4가 이 작업에 효과적임을 보여 준다. 최적화된 프롬프트 순서를 만들지 못한 경우는 GPT-4가 각 그래프 노드가 담은 의미를 잘못 이해했기 때문이다. 이런 경우 GPT-4는 지나치게 공격적이어서, 순서를 바꾸면 원래 의미가 달라지는데도 모든 상수를 앞으로 옮겼다. 이 사례 연구는 GPT-4를 컴파일러 최적화에 활용하는 가능성을 탐색하는 데 목적이 있다. 이런 종류의 최적화를 신뢰할 수 있게 만들려면 앞으로 더 많은 연구가 필요하다.
