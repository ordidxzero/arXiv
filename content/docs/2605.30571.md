## Abstract

로봇, 자율주행차, 체화 에이전트(embodied agent), 엣지 코파일럿 같은 피지컬 AI(physical AI) 시스템은 클라우드 LLM 서빙과는 다른 추론 워크로드를 돌리는 경우가 많다. 바로 단일 스트림(single-stream), 배치 1의 자기회귀 디코드다. 로봇 한 대, 카메라 피드 하나, 사용자 세션 하나가 다음 토큰을 기다리고 있는 상황이다. 이 워크로드는 보통 메모리 대역폭에 묶여 있다(memory-bandwidth-bound)고 설명된다. 디코드 스텝마다 모델 가중치와 현재 사용 중인 KV 캐시를 메모리에서 끝까지 읽어 와야 하므로, 지연 시간은 최대 HBM 대역폭에 비례해 줄어들어야 한다는 것이다. 본 논문은 이 설명이 맞지만 불완전하다는 것을 보인다.

7\~8B급 GQA 트랜스포머 세 종류의 배치 1 디코드를 NVIDIA GPU 네 종(H100 SXM5, A100-80GB SXM4, L40S, L4)에서 측정했다. 컨텍스트 길이는 2048부터 16384까지 평가했고, 통제된 bf16 SDPA 설정에서 유효한 셀(cell) 44개를 얻었다. 그 결과, 최대 HBM 대역폭이 높은 GPU일수록 실제로 달성한 대역폭의 비율은 오히려 낮아졌다. 대표 셀인 Qwen-2.5-7B ctx{{< katex >}}=2048{{< /katex >}}에서 L4는 해석적으로 계산한 메모리 하한(memory floor)의 약 81%에 도달한 반면, H100은 27%에 그쳤다. 피지컬 AI 디코드는 메모리가 지배하는 워크로드가 맞지만, 메모리가 빨라진다고 해서 그만큼 지연 시간이 줄지는 않는다.

빠진 항을 CUDA Graphs A/B 실험으로 검증했다. H100 ctx{{< katex >}}=2048{{< /katex >}}에서 CUDA Graphs는 새로 띄운 {{< katex >}}N{=}10{{< /katex >}}개 세션 전체에서 디코드 지연 시간을 {{< katex >}}1.259\times{{< /katex >}} 개선했고, 95% 부트스트랩 신뢰구간은 {{< katex >}}[1.253, 1.267]{{< /katex >}}이었다. 같은 조치가 L4에서는 {{< katex >}}1.028\times{{< /katex >}}에 불과했다. 이 결과는 빠른 GPU에서는 드러나지만 느리고 대역폭에 묶인 GPU에서는 대부분 가려져 있는, 커널 실행(launch) 쪽의 오버헤드를 분리해 보여 준다.

배포 관점의 시사점은, 메모리 절감은 런타임이 그것을 실제로 구현해 낼 때에만 의미가 있다는 것이다. L4에서 bf16 디코드는 메모리 하한에 가깝게 동작하지만, 흔히 쓰는 양자화 경로들은 기대했던 가중치 트래픽 {{< katex >}}4\times{{< /katex >}} 감소를 되찾지 못한다. bf16 기준 62.32 ms에서 bnb-nf4는 59.36 ms/step, AutoAWQ + Marlin은 45.24 ms/step에 그친다. Ada 아키텍처에 맞춰 조정된 int4 커널을 쓰는 GPTQ + ExLlamaV2는 17.36 ms/step에 도달한다. 피지컬 AI 추론의 병목은 최대 대역폭 하나가 아니라, 메모리 트래픽, 커널 실행 오버헤드, 그리고 압축된 가중치를 실제로 적게 옮기도록 해 주는 런타임 지원이 서로 맞물린 결과다.

> **역주.** 이 논문에서 *셀(cell)*\ 은 (모델 아키텍처, GPU, 컨텍스트 길이) 조합 하나를 뜻한다. 3개 모델 × 4개 GPU × 4개 컨텍스트 길이 = 48개 중 메모리 부족(OOM)으로 실패한 4개를 뺀 것이 44개다. *CUDA Graphs*는 GPU 커널들을 CPU가 하나씩 실행 지시하는 대신, 한 번 기록해 둔 커널 순서를 통째로 재생하는 CUDA 기능으로, CPU 쪽 실행 오버헤드를 줄인다.

## 1 Introduction

피지컬 AI 추론, 로봇 정책 헤드(policy head), 자율주행용 언어 코파일럿, 온디바이스 어시스턴트는 LLM 서빙 연구가 주로 겨냥하지 않는 워크로드를 공유한다. 7\~8B급 트랜스포머의 단일 스트림, 배치 1, 자기회귀 디코드다. 사용자는 사람 한 명, 로봇 한 대, 혹은 카메라 피드 하나다. 사용자가 체감하는 지표는 토큰 사이의 지연 시간이며, 처리량을 높이기 위한 배칭은 쓸 수 없다. 묶을 배치 자체가 없기 때문이다.

배치 1 디코드에 대한 표준적인 설명은 HBM 대역폭에 묶여 있다는 것이다. 디코드 스텝마다 모델 가중치와 레이어별 KV 캐시를 전역 메모리에서 한 번씩 읽어 들이는데, 산술 강도(arithmetic intensity, 읽은 바이트당 연산 수)가 너무 낮아 SM(GPU의 연산 유닛)을 바쁘게 만들지 못한다. 따라서 스텝 시간은 대략 {{< katex >}}(W + K)/B_{\mathrm{peak}}{{< /katex >}}가 된다. 이 설명은 최근 서빙 연구의 상당 부분에 동기를 제공했다. KV 캐시 압축 [29, 14, 27, 16, 10], 가중치 양자화 [7, 15, 26], KV 오프로딩이 그 예다. 또 이 설명은 배포 사다리 L4 {{< katex >}}\rightarrow{{< /katex >}} L40S {{< katex >}}\rightarrow{{< /katex >}} A100 {{< katex >}}\rightarrow{{< /katex >}} H100이 곧 토큰당 비용의 사다리라는 암묵적 가정을 낳는다. 사다리의 한 칸을 오를 때마다 최대 HBM 대역폭이 늘어나기 때문이다.

> **역주.** 식의 {{< katex >}}W{{< /katex >}}는 모델 가중치의 바이트 수, {{< katex >}}K{{< /katex >}}는 한 스텝에서 읽는 KV 캐시의 바이트 수, {{< katex >}}B_{\mathrm{peak}}{{< /katex >}}는 GPU 사양서에 적힌 최대 HBM 대역폭이다. 즉 "읽어야 할 바이트 ÷ 초당 읽을 수 있는 바이트"가 스텝 시간의 하한이라는 뜻이다. 여기서 {{< katex >}}K{{< /katex >}}는 어텐션의 키(key)가 아니라 KV 캐시 전체(키+값)의 바이트 수라는 점에 주의한다.

본 논문은 모델링 논문이 아니라 측정 연구다. 최대 HBM 대역폭이 {{< katex >}}10\times{{< /katex >}} 넘게 차이 나는 NVIDIA GPU 네 종(300 GB/s의 L4 [19]부터 3350 GB/s의 H100 SXM5 [18]까지), 7\~8B급 GQA 아키텍처 세 종 [2](Qwen-2.5-7B [21], Mistral-7B-v0.3 [11], Llama-3.1-8B), 2048에서 16384 사이의 컨텍스트 길이 네 가지에 대해 디코드 스텝 시간을 측정했다. 모두 배치 1, bf16 가중치, sdpa 어텐션을 쓰고 Modal 클라우드 호스트 [17]에서 실행했다. 직접 측정한 관측 대 하한 비율 {{< katex >}}R_{\mathrm{floor}} = t_{\mathrm{obs}}/t_{\mathrm{floor}}{{< /katex >}}(단 {{< katex >}}t_{\mathrm{floor}} = (W+K)/B_{\mathrm{peak}}{{< /katex >}})는 짧은 컨텍스트에서 L4의 {{< katex >}}\sim 0.8{{< /katex >}}에서 H100의 {{< katex >}}\sim 0.25{{< /katex >}}로 떨어진다. 달성 대역폭으로 환산하면, 이 워크로드에서 L4는 최대 HBM 대역폭의 약 81%에 도달하는 반면 H100은 27%에 그친다. 따라서 이 워크로드 부류에서 HBM 병목 예측은 빠른 실리콘에서 달성 가능한 속도 향상을 세 배가량 과대평가한다.

> **역주.** 여기서는 {{< katex >}}R_{\mathrm{floor}}{{< /katex >}}를 {{< katex >}}t_{\mathrm{obs}}/t_{\mathrm{floor}}{{< /katex >}}로 적었지만, 3.4절 이후의 정의와 모든 표는 그 역수인 {{< katex >}}t_{\mathrm{floor}}/t_{\mathrm{obs}}{{< /katex >}}를 쓴다. 0.81, 0.27 같은 값은 모두 후자, 즉 "하한 시간 ÷ 관측 시간"(1에 가까울수록 대역폭을 잘 쓰는 것)으로 읽어야 한다.

**Mechanism, falsified at {{< katex >}}N{=}10{{< /katex >}}.** 반증 가능한 핵심 주장은 메커니즘에 관한 것이다. H100에서 보이는 격차는 실리콘 때문이 아니라 커널마다 드는 CPU 쪽 실행 오버헤드(launch overhead) 때문이라는 주장이다. 이를 실행 항, 그리고 오직 실행 항만 건드리는 CUDA Graphs A/B로 검증했다. H100 ctx{{< katex >}}=2048{{< /katex >}} 대표 셀에서 독립된 Modal 세션 {{< katex >}}N{=}10{{< /katex >}}개에 걸쳐, 세션 내 graphed/eager 속도 향상은 {{< katex >}}1.259\times{{< /katex >}}, 95% 부트스트랩 신뢰구간 {{< katex >}}[1.253, 1.267]{{< /katex >}}, 세션 간 변동계수(CV, 표준편차/평균) 0.9%였다. 같은 셀의 L4에서는 같은 조치가 {{< katex >}}1.028\times{{< /katex >}}를 냈다. 이 예측은 H100 속도 향상이 대부분의 세션에서 {{< katex >}}\sim 1.15\times{{< /katex >}} 미만이거나, L4 속도 향상이 어느 한 세션에서라도 {{< katex >}}\sim 1.15\times{{< /katex >}}를 넘었다면 기각되었을 것이다. 두 조건 모두 일어나지 않았다.

**Deployment implication.** 실질적인 시사점은 토큰당 비용 사다리가 뒤집힌다는 것이다. 백엔드를 고정한 SDPA 측정에서, H100 배치 1 단일 디코드 형태에서는 PyTorch의 기본 SDPA 디스패처(dispatcher, 조건에 맞는 커널을 골라 호출하는 계층, {{< katex >}}36.05\,\mathrm{us}{{< /katex >}}/레이어)가 명시적인 `FLASH_ATTENTION` 컨텍스트({{< katex >}}44.35\,\mathrm{us}{{< /katex >}}), FlashInfer({{< katex >}}48.20\,\mathrm{us}{{< /katex >}}), FlashAttention-3({{< katex >}}79.25\,\mathrm{us}{{< /katex >}})보다 빠르다. 즉 H100에서는 커널 선택이 결정적인 제약이 아니다. 반면 L4에서는 커널 선택이 *바로* 결정적인 제약이다. 기본 Marlin 경로 대신 GPTQ + ExLlamaV2를 쓰면 Qwen-2.5-7B 스텝 시간이 62.32 ms(bf16)에서 17.36 ms로 줄어든다. 이 {{< katex >}}3.59\times{{< /katex >}} 향상은 Ada SM89에서 AutoAWQ + Marlin(45.24 ms)으로는 얻을 수 없다. ExLlamaV2를 쓴 L4는 Qwen-2.5-7B를 17.36 ms/step으로 돌리고, CUDA Graphs를 쓴 H100은 같은 워크로드를 11.78 ms/step으로 돌린다. 피지컬 AI의 주류인 스트리밍 워크로드에서는 GPU를 업그레이드하는 것보다 저렴한 실리콘에서 커널을 잘 고르는 쪽이 격차를 더 많이 좁힌다.

**Contributions.**

1. 7\~8B급 GQA 아키텍처 세 종, NVIDIA GPU 네 종, 컨텍스트 길이 네 가지에 걸친 배치 1 단일 스트림 디코드 측정 연구. 소프트웨어 스택과 워밍업을 통제하고 셀마다 30스텝을 측정했다. 유효 셀은 44개이며, L4의 긴 컨텍스트에서 난 OOM 4건은 모두 용량 한계가 아니라 A/B 프로토콜이 만든 인공물로 진단되었다.
2. 세션 내 및 세션 간 {{< katex >}}N{=}10{{< /katex >}}의 CUDA Graphs A/B 반증 실험. H100 짧은 컨텍스트 디코드에서는 실행 비용(launch tax) 해석을 확인하고, L4에서는 효과 없음(null) 결과로 이 해석을 기각한다.
3. H100 배치 1 단일 디코드 형태에서 백엔드를 고정한 어텐션 커널 측정. 이 형태에서는 PyTorch 기본 SDPA 디스패처가 FlashAttention-3, FlashInfer를 포함한 모든 명시적 백엔드보다 빠르며, cuDNN 어텐션 경로는 이 형태를 아예 지원하지 않음을 보인다.
4. 통제된 L4 양자화 비교(bf16, bnb-nf4, AutoAWQ + Marlin, GPTQ + ExLlamaV2). Ada SM89 실리콘에서 커널 구현에 따른 격차와, H100 대비 토큰당 비용이 뒤집히는 현상을 보인다.
5. 44개 셀 스윕, {{< katex >}}N{=}10{{< /katex >}} 대표 재현, 백엔드 고정 어텐션 행렬, L4 양자화 행렬을 모두 재현할 수 있는 Modal 스크립트 묶음과, 보관된 모든 JSON 산출물.

실행 병목(launch-bound) 관찰 자체가 새롭다고 주장하지는 않는다. CUDA Graphs와 실행 병목 영역은 커널 엔지니어들 사이에서 경험적으로 널리 알려져 있다. 본 논문이 기여로 주장하는 것은 통제된 GPU 간 스윕, {{< katex >}}N{=}10{{< /katex >}} 세션 내 반증 실험, 백엔드를 드러낸 어텐션 커널 순위, L4 양자화 결과, 그리고 피지컬 AI 추론에서 배포 사다리가 뒤집힌다는 점이다. 7\~8B GQA bf16 단일 스트림이라는 형태는 VLA(비전-언어-행동 모델) 정책 헤드(OpenVLA-7B [12], {{< katex >}}\pi_{0}{{< /katex >}} [3], RT-2급 [4]), 차량 실내 언어 스택, 온디바이스 코파일럿이 서빙 시점에 실제로 돌리는 바로 그 형태다. 따라서 이 역전은 이런 워크로드를 위해 추론 하드웨어 규모를 정하는 팀에게 직접적인 배포상의 결과를 낳는다.

## 2 Related work

**Roofline and arithmetic intensity.** Williams, Waterman, Patterson의 루프라인(roofline) 모델 [25]은 커널이 메모리 대역폭에 묶여 있는지 연산에 묶여 있는지를 진단하는 표준 도구이며, 본 논문이 검증하는 대역폭 병목 논리의 바탕이기도 하다. Pope et al. [20]은 이 틀을 트랜스포머 추론에 적용해 자기회귀 디코드의 메모리 병목 영역을 특징지었다. 루프라인에는 CPU 쪽에서 커널마다 드는 실행 항이 없는데, 본 논문의 CUDA Graphs A/B가 분리해 내는 것이 바로 이 성분이다.

> **역주.** 루프라인 모델은 커널의 성능 상한을 "최대 연산 속도"와 "메모리 대역폭 × 산술 강도" 중 작은 값으로 본다. 그래프로 그리면 지붕(roof) 모양이 되어 이런 이름이 붙었다. 이 모델은 GPU 내부의 연산과 메모리만 다루므로, CPU가 커널을 띄우는 데 걸리는 시간은 처음부터 고려 대상이 아니다.

**Attention kernels.** FlashAttention [6]과 FlashAttention-2 [5]는 어텐션 계산을 IO를 의식하도록(IO-aware, 느린 메모리 접근을 최소화하도록) 재구성해, 프리필(prefill)과 긴 컨텍스트 학습에서 큰 이득을 얻었다. 이들의 이득은 어텐션 연산이 병목인 곳에서 가장 크다. 배치 1 단일 토큰 디코드에서는 ctx{{< katex >}}\le 8192{{< /katex >}}일 때 스텝당 어텐션 KV 트래픽이 크지 않으며, H100에서 결정적인 제약은 어텐션 자체의 처리량이 아니라 트랜스포머 레이어를 이루는 수많은 작은 커널들의 실행이다. 6절에서 이를 직접 확인한다. H100 ctx{{< katex >}}=2048{{< /katex >}}에서 sdpa를 FA2로 바꾸면 디코드가 17.07 ms에서 24.16 ms로 오히려 느려진다.

**FlashDecoding++ (no public release).** Hong et al.의 FlashDecoding++ [9] ([arXiv:2311.01282](https://arxiv.org/abs/2311.01282); MLSys 2024)는 커널별 실행 오버헤드가 중요해지는 영역의 배치 1 디코드를 다룬, 가장 가까운 선행 연구다. 저자들은 세 가지 완화책을 제안한다. 통일된 최댓값을 쓰는 비동기 softmax, 이중 버퍼링을 쓰는 flat-GEMM 최적화, 하드웨어 자원에 적응하는 휴리스틱 데이터 흐름이다. 이들은 Hugging Face 기준선 대비 최대 {{< katex >}}4.86\times{{< /katex >}}, Flash-Decoding 대비 평균 {{< katex >}}1.37\times{{< /katex >}}의 속도 향상을 보고한다. 저자들이 소스 코드를 공개하지 않아, 본 논문의 테스트베드에서 FlashDecoding++ 셀은 하나도 재현할 수 없었다. FlashDecoding++를 Dao-AILab/flash-attention에 통합해 달라는 기능 요청([issue 653](https://github.com/Dao-AILab/flash-attention/issues/653))은 구현 없이 2024년 4월에 닫혔고, vLLM의 같은 요청([issue 1568](https://github.com/vllm-project/vllm/issues/1568))도 커널을 맡겠다는 사람 없이 열린 채로 남았다. 같은 저자들과 Infinigence-AI의 후속작 FlashDecoding++Next(IEEE TC 2025, DOI [10.1109/TC.2025.3585339](https://doi.org/10.1109/TC.2025.3585339)) 역시 비공개 소스다. 그래서 가장 가까운 비교 대상으로 공개된 디코드 단계 커널 두 가지, FlashAttention-3와 FlashInfer를 대신 사용했으며, 둘 다 6절에서 재현한다.

**FlashAttention-3 (Hopper-specific, reproduced here).** Dao et al.의 FlashAttention-3 [22] ([arXiv:2407.08608](https://arxiv.org/abs/2407.08608))는 Hopper에서 활발히 유지보수되고 있는 FA-2의 후속작이다. H100, ctx{{< katex >}}=2048{{< /katex >}}, 배치 1, bf16에서 커널 수준 마이크로벤치마크를 재현했다. Llama-3-8B의 스텝당 형태(Q 헤드 32개, KV 헤드 8개, head_dim 128, kv_len {{< katex >}}={{< /katex >}} 2049)에서 FA-3 어텐션 커널(`flash_attn_3.flash_attn_func`)과 이에 대응하는 PyTorch SDPA 호출을 비교하고, 32개 레이어에 대해 합산한 뒤 새 Modal 세션 3개에서 반복했다. 결과는 6절과 그림 7에 있다.

**FlashInfer (decode kernel library, reproduced here).** Ye et al.의 FlashInfer [28] (MLSys 2025; [flashinfer-ai/flashinfer](https://github.com/flashinfer-ai/flashinfer))는 명시적인 디코드 커널을 갖춘, LLM 서빙용 맞춤형 어텐션 엔진이다. H100, ctx{{< katex >}}=2048{{< /katex >}}, 배치 1, bf16에서 커널 수준 마이크로벤치마크를 재현했다. Llama-3-8B GQA 형태(Q 헤드 32개, KV 헤드 8개, head_dim 128, kv_len{{< katex >}}={{< /katex >}}2049, group_size 4)에서 `flashinfer.decode.single_decode_with_kv_cache`를 레이어당 한 번씩 32번 호출한 시간을 합산해, 이에 대응하는 PyTorch SDPA 호출과 비교했다. 논문의 나머지 부분에서 쓰는 Qwen-2.5-7B 형태 대신 Llama-3-8B 형태를 쓴 이유는, FlashInfer의 참조 단일 디코드 커널이 현재 group_size 7을 지원하지 않기 때문이다. 결과는 그림 7에 있다.

> **역주.** group_size는 KV 헤드 하나를 공유하는 쿼리 헤드의 수다. Llama-3-8B는 32/8 = 4, Qwen-2.5-7B는 28/4 = 7이다.

**CUDA Graphs.** CUDA Graphs(NVIDIA 개발자 문서 참조; PyTorch는 1.10부터 기본 지원)는 커널마다 CPU가 실행을 지시하는 대신, 미리 캡처한 DAG(커널 의존 그래프)를 한 번에 재생한다. 실행 병목 영역의 표준적인 완화책이다. 본 논문에서는 이를 배포 권장 사항이 아니라 측정 도구로 쓴다. 던지는 질문은 실행 오버헤드를 없앴을 때 GPU마다 스텝 시간이 실제로 달라지느냐이며, 이것이 실행 비용의 크기를 실험적으로 한정하고, 논문 나머지 부분의 반증 틀이 된다.

**Quantisation.** GPTQ [7]는 트랜스포머에 학습 후 int4 가중치 양자화를 도입했고, AWQ [15]는 활성값을 고려한 스케일링(activation-aware scaling)을 Marlin 방식의 패킹된 행렬곱 커널과 함께 추가했다. Marlin [8] 자체는 AWQ가 의존하는 고처리량 int4 행렬곱 커널로, 원래 SM80(Ampere)에 맞춰 조정되었다. SmoothQuant [26]는 W8A8 양자화(가중치·활성값 모두 8비트)에서 활성값 이상치 문제를 다룬다. bitsandbytes는 역양자화 후 bf16 행렬곱을 하는 구현으로 nf4 가중치 양자화를 제공한다. AWQ + Marlin과 bnb-nf4 모두 가중치 HBM 트래픽을 약 {{< katex >}}4\times{{< /katex >}} 줄일 수 있다고 기대된다. 그러나 L4에서 관찰한 실제 스텝 시간 감소는 {{< katex >}}4\times{{< /katex >}}에 한참 못 미친다(7절). 대역폭 절감이 워크로드에 실제로 반영되는지는 비트 폭이 아니라 배포 체인, 즉 커널 구현이 결정하기 때문이다.

**Serving systems.** PagedAttention [13]을 쓰는 vLLM과 TensorRT-LLM은 배치 1 지연 시간이 아니라 배치 처리량을 중심으로 설계된 프로덕션 서빙 시스템이다. Sarathi-Serve [1]는 청크 단위 프리필 스케줄링으로 이를 더 밀어붙여, 적당한 지연 시간에서 더 높은 처리량을 얻는다. 이 시스템들은 H100급 배포에서 내부적으로 CUDA Graphs를 사용하는데, 이는 본 논문이 그리는 그림과 일치한다. 다만 저자가 아는 한, 단일 스트림 배치 1 디코드의 GPU 간 교차 현상을 본 논문과 같은 통제된 A/B 실험으로 보인 결과는 발표된 적이 없다.

**What is new here.** 통제된 GPU 간 측정 스윕과 CUDA Graphs 반증 실험을 한 논문에 담았고, 범위는 Modal에서 호스팅한 NVIDIA 실리콘 위의 7\~8B급 GQA bf16 배치 1 디코드로 좁게 한정했다. 실행 병목 관찰 자체가 새롭다고 주장하지는 않는다.

## 3 Method

### 3.1 Measurement protocol

셀 하나는 (아키텍처, GPU, 컨텍스트 길이)의 세 쌍 하나다. 모델을 bf16으로 불러오고, 고정 길이의 프리필을 실행해 KV 캐시를 채운 뒤, 워밍업 디코드 5스텝과 이어지는 측정 대상 단일 토큰 디코드 30스텝을 배치 1로 시간 측정한다. 스텝 시간은 측정한 30스텝의 스텝별 벽시계 시간(wall time)의 중앙값이다. 기본 어텐션 구현은 PyTorch의 scaled-dot-product-attention(sdpa)이며, FlashAttention-2는 6절의 통제된 소프트웨어 스택 행렬에서만 쓴다. 셀들은 모든 호스트에서 같은 컨테이너 이미지를 써서 Modal 클라우드 GPU에서 실행한다(부록 A).

### 3.2 Measurement-pipeline provenance

Qwen-2.5-7B-Instruct의 주 행렬 셀 14개는 v10 스윕 스크립트로, Mistral-7B-Instruct-v0.3과 Llama-3.1-8B-Instruct의 주 행렬 셀 각 14개는 v11 스윕 스크립트로 측정했다. 두 스크립트는 같은 컨테이너 기본 이미지(PyTorch 2.4가 들어간 `debian_slim`), 같은 측정 프로토콜(워밍업 5스텝 + 측정 단일 토큰 AR 디코드 30스텝, sdpa 어텐션, bf16, 배치 크기 1), 같은 Modal 클라우드 GPU 호스트(H100, A100-80GB, L40S, L4)를 쓴다. 유일한 차이는 v11 스크립트가 Llama-3.1-8B를 위해 HuggingFace 게이트 모델 인증을 추가한다는 점이다. 아래에 기록한 Qwen-2.5-7B L4 긴 컨텍스트 OOM은 v14에서 v11 방식 스크립트로 다시 조사했다(5절, Qwen L4 재실행). `v10_results/cells/qwen25_7b_<gpu>_ctx<ctx>.json`에 있는 v10 Qwen 셀 JSON에는 v11 셀 JSON과 같은 필드(`p50_ms`, `step_times_ms`, `weight_bytes`, `kv_bytes_avg`, `bytes_per_token_kv`)가 들어 있으며, 통합 분석 스크립트가 읽는 것이 바로 이 필드들이다. 파생 Qwen 스윕(CUDA Graphs, 소프트웨어 스택, 프로파일, 양자화)은 `v11_results/cells/`에 있으며 v11 스크립트로 다시 측정했다.

### 3.3 Cells

아키텍처는 세 가지다. Qwen-2.5-7B-Instruct(레이어 28개, 쿼리 헤드 28개, KV 헤드 4개, head_dim 128, {{< katex >}}W{=}15.23{{< /katex >}} GB(10진 단위), 즉 14.18 GiB), Mistral-7B-Instruct-v0.3(레이어 32개, 쿼리 헤드 32개, KV 헤드 8개, head_dim 128, {{< katex >}}W{=}14.50{{< /katex >}} GB, 13.50 GiB), Llama-3.1-8B-Instruct(레이어 32개, 쿼리 헤드 32개, KV 헤드 8개, head_dim 128, {{< katex >}}W{=}16.06{{< /katex >}} GB, 14.96 GiB). 셋 모두 head_dim 128의 GQA 모델이다. GPU는 H100, A100-80GB, L40S, L4 네 가지, 컨텍스트 길이는 2048, 4096, 8192, 16384 네 가지다. {{< katex >}}3 \times 4 \times 4 = 48{{< /katex >}}개 셀 가운데 4개가 실패했고(Qwen-2.5-7B ctx{{< katex >}}=8192{{< /katex >}}, Qwen-2.5-7B ctx{{< katex >}}=16384{{< /katex >}}, Llama-3.1-8B ctx{{< katex >}}=8192{{< /katex >}}, Llama-3.1-8B ctx{{< katex >}}=16384{{< /katex >}}에서 L4 OOM, 모두 24 GB L4), 유효 셀 44개가 남았다.

Qwen-2.5-7B의 L4 OOM은 따로 짚어 둘 필요가 있다. 아키텍처로 계산해 보면 OOM이 나지 않아야 하기 때문이다. bf16 Qwen-2.5-7B는 {{< katex >}}W{=}15.23{{< /katex >}} GB이고 토큰당 KV 바이트는 {{< katex >}}2{\cdot}28{\cdot}4{\cdot}128{\cdot}2 = 56{{< /katex >}} KB다. ctx{{< katex >}}=8192{{< /katex >}}이면 KV는 0.47 GB로, 합계 15.70 GB다. bf16 Mistral-7B는 {{< katex >}}W{=}14.50{{< /katex >}} GB, 토큰당 KV 128 KB이며, ctx{{< katex >}}=8192{{< /katex >}}에서 KV 1.07 GB, 합계 15.57 GB다. 24 GB 장치에서 두 합계의 차이는 1% 이내다. 그런데 Mistral은 L4 ctx{{< katex >}}=8192{{< /katex >}}에서 정상 실행되고(표 1, {{< katex >}}R_{\mathrm{floor}}{=}0.478{{< /katex >}}) Qwen은 OOM이 난다. v14 재조사에서 Qwen OOM이 재현되었고, 원인도 드러났다. A/B 프로토콜의 eager 단계(arm)는 최대 할당 23.24 GB로 문제없이 실행되지만, 두 번째(graphed) 단계에서 eager 단계의 텐서가 해제되지 않은 상태로 새 `StaticCache`를 할당할 때 OOM이 난다. 따라서 ctx{{< katex >}}=8192{{< /katex >}}의 Qwen L4 셀은 단일 단계 리그에서는 측정 가능하다(세션 {{< katex >}}N{=}3{{< /katex >}}개에서 eager 단계 {{< katex >}}p_{50}{=}87.74{{< /katex >}} ms, `v14_results/data/v14_qwen_l4_rerun/PARTIAL_EAGER_qwen_l4_ctx8192_s{0,1,2}.json`). 이를 용량 한계가 아니라 측정 프로토콜이 만든 인공물로 기록하되, 이 셀들을 주 행렬 집계에 추가하지는 않는다. 대표 {{< katex >}}R_{\mathrm{floor}}{{< /katex >}} 표와의 하위 호환성을 위해 유효 44 + OOM 4라는 집계는 위에 보고한 그대로 둔다.

> **역주.** 토큰당 KV 바이트 식 {{< katex >}}2{\cdot}28{\cdot}4{\cdot}128{\cdot}2{{< /katex >}}는 (키와 값 2개) × (레이어 28) × (KV 헤드 4) × (head_dim 128) × (bf16 2바이트) = 57,344바이트 ≈ 56 KB다. 한편 이 절 첫 문단은 OOM 셀로 Qwen과 Llama를 들지만, 부록 C는 Mistral과 Llama를 든다. 표 1과 부록 B에서는 Mistral L4 셀이 모두 있고 Qwen·Llama L4 ctx 8192/16384가 빠져 있으므로, 이 절의 서술이 표와 일치한다.

{{< katex >}}B_{\mathrm{peak}}{{< /katex >}}로는 사양서의 최대 HBM 대역폭을 쓴다. H100 SXM5는 3350 GB/s, A100-80GB SXM4는 2039 GB/s, L40S는 864 GB/s, L4는 300 GB/s다(`v11_results/v11_fit_summary.json`, `bw_peak_gbs`).

### 3.4 The observed-over-floor ratio {{< katex >}}R_{\mathrm{floor}}{{< /katex >}}

사양서의 최대 HBM 대역폭과 스텝당 가중치 + 활성 KV 바이트 트래픽이 주어졌을 때, 단일 스트림 디코드 스텝 시간의 루프라인 하한은 다음과 같다.

{{< katex display=true >}}
t_{\mathrm{floor}}(G, M, \mathrm{ctx}) = \frac{W(M) + K(M, \mathrm{ctx})}{B_{\mathrm{peak}}(G)},
{{< /katex >}}

여기서 {{< katex >}}W(M){{< /katex >}}은 모델의 bf16 가중치 용량(바이트, 여기서 다루는 7\~8B GQA 모델은 10진 단위로 14.5\~16.1 GB)이고, {{< katex >}}K(M, \mathrm{ctx}) = 2 \cdot n_{\mathrm{layers}} \cdot n_{\mathrm{kv\_heads}} \cdot d_{\mathrm{head}} \cdot \mathrm{ctx} \cdot 2~\text{bytes}{{< /katex >}}는 스텝당 접근하는 KV 바이트다(앞의 2는 K와 V 두 가지를, 뒤의 2는 bf16 원소 크기를 나타낸다). {{< katex >}}G{{< /katex >}}는 GPU, {{< katex >}}M{{< /katex >}}은 모델이다. 직접 측정한 비율

{{< katex display=true >}}
R_{\mathrm{floor}}(G, M, \mathrm{ctx}) = \frac{t_{\mathrm{floor}}(G, M, \mathrm{ctx})}{t_{\mathrm{obs}}(G, M, \mathrm{ctx})}
{{< /katex >}}

는 셀마다 하나씩 얻는 실험값으로, {{< katex >}}t_{\mathrm{obs}}{{< /katex >}}(측정한 디코드 30스텝의 중앙값)와 {{< katex >}}t_{\mathrm{floor}}{{< /katex >}}(사양서 대역폭과 스텝당 바이트로 계산)로부터 구한다. 이것은 모델 적합 결과가 아니다. 두 항 모두 직접 측정하거나 해석적으로 계산한 양이다.

> **역주.** 즉 {{< katex >}}R_{\mathrm{floor}}{{< /katex >}}는 "이론상 최소 시간이 실제 시간의 몇 %인가", 다시 말해 최대 HBM 대역폭의 몇 %를 실제로 활용했는가를 나타낸다. 1이면 순수하게 대역폭에 묶인 이상적인 상태이고, 값이 작을수록 대역폭 외의 다른 무언가가 시간을 잡아먹고 있다는 뜻이다.

### 3.5 CUDA Graphs A/B

CUDA Graphs 실험은 디코드 스텝 하나의 커널 순서를 한 번 캡처한 뒤 재생한다. 측정 프로토콜은 그 밖에는 동일하다. 워밍업 재생 5회와 측정 재생 30회를 하고 지연 시간 중앙값을 쓴다. 목적은 커널 자체는 하나도 바꾸지 않은 채 커널마다 드는 CPU 쪽 실행 오버헤드만 분리하는 것이며, 따라서 차이(eager − graphed)는 GPU마다 실행 비용의 상한이 된다. 셀은 Qwen-2.5-7B의 (H100, ctx{{< katex >}}=2048{{< /katex >}}), (H100, ctx{{< katex >}}=8192{{< /katex >}}), (L4, ctx{{< katex >}}=2048{{< /katex >}})이다. v12 재현 스윕은 이를 대표 셀에서 GPU당 새 컨테이너 {{< katex >}}N{=}3{{< /katex >}}개로 확장한다. 결과는 5절에 있으며, 원본 셀 JSON은 `v11_results/cells/cudagraphs_*.json`과 `v12_results/cells/`에 있다.

## 5 The CUDA Graphs A/B test

4절의 44개 셀 스윕은 {{< katex >}}R_{\mathrm{floor}}{{< /katex >}}가 {{< katex >}}B_{\mathrm{peak}}{{< /katex >}}에 대해 단조적인 GPU 간 패턴을 확립한다. 이 패턴은 실행 비용 메커니즘과 들어맞지만 그것을 증명하지는 않는다. 메커니즘을 검증하기 위해 손잡이 하나만 돌리는 개입, 즉 CUDA Graphs를 실행했다. Graphs는 커널마다 CPU 쪽에서 실행을 지시하는 대신 캡처한 DAG를 한 번에 재생하며, 커널 자체는 바뀌지 않는다. H100 짧은 컨텍스트 디코드를 실행 비용이 지배한다면 Graphs는 H100 짧은 컨텍스트에서 스텝 시간을 줄여야 한다. L4 짧은 컨텍스트 디코드를 HBM 대역폭이 지배한다면 Graphs는 L4에서 스텝 시간을 줄이지 못해야 한다. 이 실험은 스윕에 대한 견고성 점검으로 위치시키며, 논문의 핵심 결과로 내세우지는 않는다.

**Pre-registered falsification thresholds.** 실행 비용 해석은 다음 두 결과 중 하나가 나왔다면 기각되었을 것이며, 이 기준은 A/B 실행 전에 정해 두었다.

- 짧은 컨텍스트(ctx{{< katex >}}=2048{{< /katex >}})에서 H100의 graphed 속도 향상이 {{< katex >}}\sim 1.15\times{{< /katex >}} 미만.
- 짧은 컨텍스트(ctx{{< katex >}}=2048{{< /katex >}})에서 L4의 graphed 속도 향상이 {{< katex >}}\sim 1.15\times{{< /katex >}} 초과.

**Removed launch overhead.** H100 ctx{{< katex >}}=2048{{< /katex >}} b{{< katex >}}=1{{< /katex >}}에서 eager 스텝의 평균은 14.83 ms, graphed 스텝의 평균은 11.78 ms다. 그 차이 3.05 ms가 Graphs가 제거하는 스텝당 실행 쪽 오버헤드이며, 원래 스텝의 약 {{< katex >}}20.6\%{{< /katex >}}다. 이 값을 추정 커널 실행 횟수로 나누지는 않는다. Graphs가 없애는 것은 커널별 호스트 실행만이 아니기 때문이다. Graphs는 스트림 이벤트를 합치고, 호출마다 드는 Python 및 C++ 프레임워크 디스패치를 없애고, 할당자(allocator) 패턴을 고정하고, torch 디스패처 작업도 없앤다. 3.05 ms는 호스트 쪽에서 드는 이 모든 스텝당 오버헤드의 합이지, 커널별 실행 비용만이 아니다. 커널별 비용으로 나누어 귀속하려면 호스트 실행과 프레임워크 디스패치를 구분하는 추적 도구가 필요하다(부록 D에 스텝당 커널 수와 그 내역이 있다).

> **역주.** "1.259배 빨라졌다"와 "20.6%를 제거했다"는 같은 결과를 다르게 표현한 것이다. {{< katex >}}14.83/11.78 \approx 1.259{{< /katex >}}이고, {{< katex >}}(14.83-11.78)/14.83 \approx 0.206{{< /katex >}}이다. 그림 3 캡션은 같은 결과를 "스텝 시간의 25% 회복"이라고 적는데, 본문은 이 값과 20.6%의 관계를 따로 설명하지 않는다.

GPU가 이미 실행 지시가 아니라 HBM을 기다리고 있으므로, CPU 실행 순서를 직렬로 제거해도 크게 도움이 될 수 없다. L4에서 Graphs가 효과 없다는 것은 정확히 이 메커니즘이 예측하는 바다.

## 7 Quantisation baseline on L4

교차점의 대역폭 병목 쪽에서 표준 처방은 가중치 양자화다. L4에서 ctx{{< katex >}}=2048{{< /katex >}}의 Qwen-2.5-7B로 통제된 기준 실험을 실행했다. 셀은 `v11_results/analyze_v2.txt` 163\~167행과 그 바탕이 되는 `v11_results/cells/quant_*.json`의 JSON에서 가져왔다.

bf16 기준선은 HBM 하한의 {{< katex >}}\sim 20{{< /katex >}}% 이내에 있으며, 이는 L4가 대역폭에 묶인 영역이라는 점과 일치한다. 15.23 GB의 bf16 가중치를 스텝마다 한 번씩 최대 300 GB/s의 HBM으로 읽으면 순수 가중치 트래픽만으로 50.77 ms가 들고, KV 항이 몇 ms를 더한다(작은 KV 기여를 포함한 {{< katex >}}t_{\mathrm{floor}}{=}51.17{{< /katex >}} ms). 단순하게 생각하면 양자화는 가중치 트래픽을 {{< katex >}}4\times{{< /katex >}} 줄여야 한다.

> **역주.** 표 7에서 bf16 행의 {{< katex >}}t_{\mathrm{floor}}{{< /katex >}}는 bf16 가중치 기준(51.17 ms)이고, 양자화 행들의 {{< katex >}}t_{\mathrm{floor}}{{< /katex >}} 13.09 ms는 가중치를 4배 줄인 기준이다. 따라서 양자화 행의 {{< katex >}}R_{\mathrm{floor}}{{< /katex >}}는 "4비트 가중치로 이론상 가능한 속도에 얼마나 가까운가"를 뜻한다.

그러나 스텝 시간에서는 그렇게 되지 않는다. nf4(bitsandbytes)는 59.36 ms로 bf16보다 거의 빠르지 않다. AWQ는 45.24 ms로 bf16 대비 스텝 시간 {{< katex >}}1.38\times{{< /katex >}} 향상인데, 가중치 트래픽 {{< katex >}}4\times{{< /katex >}} 감소가 예측하는 것에는 한참 못 미친다. 원인은 배포 체인이다. bitsandbytes의 nf4 경로는 즉석 역양자화 커널 다음에 bf16 행렬곱을 하는 방식으로 구현되어 있다(Dettmers et al., QLoRA, 2023; bitsandbytes `nn/modules.py`의 `Linear4bit` forward). 그래서 행렬곱마다 실제 HBM 트래픽은 nf4 가중치 용량이 아니라 중간 bf16 활성값과 역양자화 커널의 실행 오버헤드가 지배한다. AWQ는 Marlin 방식의 패킹 커널이 행렬곱을 int4 + fp16 스케일 형태로 유지하므로 훨씬 낫지만, 이 커널도 nf4 HBM 하한(13.09 ms)에는 도달하지 못한다.

**ExLlamaV2 measurement (v14).** 병목이 비트 폭 원리가 아니라 AutoAWQ의 Marlin 커널이었는지 검증하기 위해, int4 GEMM 커널이 Ada Lovelace(SM89)에 맞춰 명시적으로 조정된 런타임인 ExLlamaV2 0.2.4로 추가 측정을 했다. 셀: Qwen-2.5-7B-Instruct EXL2 4.25bpw(bartowski 브랜치), L4, ctx{{< katex >}}=2048{{< /katex >}}, batch{{< katex >}}=1{{< /katex >}}, 새 Modal 컨테이너 {{< katex >}}N{=}3{{< /katex >}}개. 세션별 {{< katex >}}p_{50}{{< /katex >}}: {{< katex >}}[17.361, 17.368, 17.360]{{< /katex >}} ms(평균 17.36, 표준편차 0.004). 세션별 최대 GPU 메모리: {{< katex >}}[6.96, 6.96, 6.95]{{< /katex >}} GB(평균 6.96). 원본 JSON은 `v14_results/data/v14_exllamav2_l4/`에 있다.

> **역주.** EXL2 4.25bpw는 ExLlamaV2 고유의 양자화 형식으로, 가중치 하나당 평균 4.25비트(bits per weight)를 쓴다는 뜻이다. bartowski는 이 형식으로 변환한 모델을 Hugging Face에 올린 배포자 이름이다.

ExLlamaV2는 L4에서 스텝 시간을 62.32 ms(bf16)에서 17.36 ms로 줄여 {{< katex >}}3.59\times{{< /katex >}} 향상을 낸다. AutoAWQ Marlin 경로는 {{< katex >}}1.38\times{{< /katex >}}에 그쳤다. Marlin은 Ampere SM80에 맞춰 조정되어 Ada SM89에서는 최고 수준이 아니며, ExLlamaV2의 Ada 전용 int4 GEMM 커널은 비트 폭 감소가 예측하는 대역폭 절감의 대부분을 회복한다. 이 셀은 이제 {{< katex >}}4\times{{< /katex >}} 줄인 하한 13.09 ms에 대해 {{< katex >}}R_{\mathrm{floor}} = 0.754{{< /katex >}}에 있고, 같은 하한에 대해 AWQ 셀은 0.289였다.

L4급 배포에 대한 실용적 시사점은 양자화 런타임이 양자화 방식만큼 중요하다는 것이다. 2026년 중반 기준으로 L4에서 쓸 만한 양자화 백엔드의 순위는 대략 ExLlamaV2 EXL2 {{< katex >}}>{{< /katex >}} AutoAWQ Marlin {{< katex >}}>{{< /katex >}} bnb-nf4다.

## 8 Per-kernel evidence with torch.profiler

Modal 클라우드 컨테이너에서는 Nsight Compute(`ncu`)를 쓸 수 없었다. `ncu`는 우리에게 없던 호스트 드라이버 접근 권한을 요구한다. 대안으로 `torch.profiler`와 해석적 바이트 수를 썼다. 프로파일러 자체가 H100의 절대 스텝 시간을 부풀린다(프로파일링하지 않을 때 16.97 ms가 프로파일링하면 54.38 ms로, 3.2{{< katex >}}\times{{< /katex >}} 오버헤드). 반면 L4에는 사실상 영향이 없다(프로파일링 없이 63.0 ms, 프로파일링 시 63.67 ms, 1.01{{< katex >}}\times{{< /katex >}}). 따라서 프로파일링한 스텝 시간을 `bw_util`의 분모로 쓰면 H100의 대역폭 활용도가 과소 보고된다. 핵심 수치로는 해당 프로덕션 셀의 스텝 시간 중앙값을 분모로 쓴 *프로파일링하지 않은* `bw_util`을 보고하고, 추적 가능하도록 두 값을 모두 적는다.

> **역주.** 프로파일러는 CPU 쪽에서 커널 호출마다 기록 작업을 덧붙인다. CPU 실행 오버헤드가 병목인 H100에서는 이 추가 작업이 그대로 스텝 시간에 더해지고, GPU 연산이 병목인 L4에서는 GPU 작업 뒤에 가려진다. 이 비대칭 자체가 4·5절의 실행 병목 해석과 맞아떨어진다.

**표 8.** GPU 간 스텝당 회계, Qwen-2.5-7B, ctx 값은 프로덕션 스윕과 맞췄다. `bw_util`은 스텝당 해석적 전송 바이트(가중치 + 활성 KV 구간)를 사양서 {{< katex >}}B_{\mathrm{peak}}{{< /katex >}}로 전송하는 시간을 스텝 시간으로 나눈 값이다. 프로파일링하지 않은 값은 프로덕션 스텝 시간 중앙값을, 프로파일링한 값은 `torch.profiler` 스텝 시간을 분모로 쓴다. `cpu/cuda`는 프로파일러 벽시계 시간 가운데 CPU 쪽에서 커널을 실행·동기화하는 데 쓴 시간을 GPU 커널 시간에 대한 비율로 나타낸 것이다. 출처: 프로파일링하지 않은 스텝 시간은 `v14_results/data/v14_n10_headline/`, 프로파일링한 스텝 시간과 `cpu/cuda`는 `v11_results/analyze_v2.txt` 169\~174행 및 `v11_results/profiles/`.

## 9 Limitations and threats to validity

**Explicit scope.** 이 논문의 모든 주장은 다음 범위로 한정된다.

- 7\~8B 파라미터 트랜스포머(Qwen-2.5-7B-Instruct, Mistral-7B-Instruct-v0.3, Llama-3.1-8B-Instruct);
- grouped-query attention [2]만 해당(MHA [24], MQA [23], MLA는 제외);
- head_dim 128만 해당;
- bf16 가중치만 해당(L4로 범위를 명시한 L4 양자화 기준 실험은 예외);
- 단일 토큰 자기회귀 디코드(추측 디코딩(speculative decoding), 병렬 샘플링은 제외);
- 배치 크기 1이 주 대상이며, 민감도 점검으로 H100과 L4에서 배치 4를 측정(5절);
- NVIDIA GPU만 해당: H100 SXM5, A100-80GB SXM4, L40S, L4(AMD MI300, Blackwell, Jetson, Apple은 제외);
- Modal 클라우드 호스팅만 해당(베어메탈, 다른 클라우드는 제외);
- 주 행렬은 sdpa 어텐션, FA2는 H100의 통제된 소프트웨어 스택 행렬에서만 사용.

GPU 간 패턴이 이 워크로드 부류를 넘어 일반화된다고 주장하지 않는다.

> **역주.** MHA(multi-head attention)는 쿼리 헤드마다 KV 헤드를 따로 두는 원래 방식, MQA(multi-query attention)는 모든 쿼리 헤드가 KV 헤드 하나를 공유하는 방식, GQA는 그 중간이다. MLA(multi-head latent attention)는 KV를 저차원 잠재 벡터로 압축해 저장하는 방식으로, DeepSeek 계열 모델에서 쓰인다.

**Architecture coverage.** 측정한 세 모델은 모두 head_dim 128의 GQA다(Qwen-2.5-7B는 KV 헤드 4개, 나머지 둘은 8개). 결과가 MQA, 완전한 MHA, 또는 head 차원이 크게 다른 모델로 옮겨 가지 않을 수 있다. 레이어당 {{< katex >}}\sim 10{{< /katex >}}개 커널이라는 기준값은 구조가 비슷한 GQA 트랜스포머 구현 세 개에서 관찰한 것이다. 보편적인 커널 순서를 주장하려면 더 넓은 아키텍처 스윕이 필요하다.

**Batch size.** 주 행렬과 대표 재현은 배치 1이다. 추가로 H100과 L4에서 배치 4로 전체 컨텍스트 범위에 걸쳐 CUDA Graphs A/B를 측정했다(5절, 그림 5). H100에서 배치 4일 때 스텝당 커널 작업은 Q/K/V 프로젝션에서 대략 {{< katex >}}4\times{{< /katex >}}, 토큰별 어텐션 출력에서도 대략 {{< katex >}}4\times{{< /katex >}} 늘어나지만, 스텝당 실행 횟수는 사실상 그대로다. 따라서 스텝 시간 중 실행 비용의 비율이 줄고, graphed 속도 향상도 함께 줄어든다. 배치 1의 그림이 교차점 너머까지 이어진다고 주장하는 대신 이를 그대로 보고한다. H100에서 배치 {{< katex >}}{\ge}8{{< /katex >}}, L4에서 배치 {{< katex >}}{>}4{{< /katex >}}는 측정하지 않았다.

> **역주.** 5절에 따르면 L4는 배치 4에서 모든 컨텍스트가 OOM이었으므로, 실제로 배치 4 측정값이 있는 것은 H100뿐이다.

**Cloud host noise.** Modal 클라우드 GPU는 드라이버 버전이 공개되지 않고 호스트 잡음을 공유한다. 이를 완화하기 위해 모든 실행에서 같은 컨테이너 이미지를 쓰고, 측정 30스텝의 중앙값을 보고하고, H100 ctx{{< katex >}}=2048{{< /katex >}} 대표 셀에서는 독립 세션 {{< katex >}}N{=}10{{< /katex >}}개를 실행했다. 이 셀에서 세션 내 스텝 시간 CV는 eager 0.9%, graphed 0.2%이므로, 단일 세션 안의 스텝 시간 잡음은 작다. 같은 구성의 세션 간 스텝 시간은 v10, v11, v14 실행에 걸쳐 더 넓게 퍼져 있다(eager 16.97 ms\~20.63 ms). 이는 실행 안의 지터라기보다 컨테이너 호스트 스케줄링과 리그 간 코드 경로 차이가 섞인 결과다. 세션 내 속도 향상이 더 안정적인 양이며(CV 0.9%, 95% 부트스트랩 신뢰구간 {{< katex >}}[1.253, 1.267]{{< /katex >}}), 그래서 세션 간 비율이 아니라 이것을 핵심 수치로 쓴다. 대표 셀을 예약 용량(reserved-capacity) H100 구성에서도 실행해 보았는데(기본은 최선 노력(best-effort) 스케줄링), 세션 내 CV는 개선되지 않았다. 남은 변동은 Modal 호스트 대기열 때문이 아니라 이 형태의 단일 스트림 디코드에 내재한 것으로 보인다.

> **역주.** 이 문단의 "세션 내 스텝 시간 CV 0.9%/0.2%"는 표 2와 부록 D에 따르면 실제로는 세션별 중앙값의 세션 간 CV다. 부록 D는 세션 내 30스텝의 CV가 eager {{< katex >}}<1\%{{< /katex >}}, graphed {{< katex >}}<0.5\%{{< /katex >}}라고 따로 적는다. 용어 구분은 부록 D의 "Replicate terminology"를 참고하면 된다.

**Profiler instrumentation.** Modal 컨테이너에서는 `ncu`를 쓸 수 없었다. `torch.profiler`와 해석적 바이트 수가 그 대안이다. 프로파일러 오버헤드는 절대 스텝 시간을 비대칭적으로 부풀린다. H100은 {{< katex >}}3.2\times{{< /katex >}} 부풀려지고(프로파일링 없이 16.97 ms에서 프로파일링 시 54.38 ms), L4는 {{< katex >}}1.01\times{{< /katex >}}(사실상 오버헤드 없음)다. 따라서 프로파일링한 분모를 쓰면 H100의 대역폭 활용도가 과소 보고된다. 8절은 프로파일링하지 않은 분모의 `bw_util`을 핵심 수치로 보고하고(H100 26.9%, L4 79.4%로, 프로파일링 시간을 그대로 받아들일 때 나타나는 {{< katex >}}10\times{{< /katex >}}가 아니라 {{< katex >}}3\times{{< /katex >}} 격차), 추적 가능하도록 프로파일링 시간도 함께 적는다. cpu/cuda 열은 분모 문제의 영향을 받지 않는다.

**Attention-compute regime at long context on small GPUs.** {{< katex >}}R_{\mathrm{floor}}{{< /katex >}}의 정의는 가중치와 활성 KV의 HBM 트래픽이 디코드 비용을 지배한다고 가정한다. L4에서 ctx{{< katex >}}{\ge}8192{{< /katex >}}이면 어텐션의 QK 계산과 softmax 연산이 가중치 HBM 전송에 비해 무시할 수 없을 만큼 커지고, {{< katex >}}t_{\mathrm{floor}}{{< /katex >}}는 GPU가 실제로 하는 일을 덜 세게 된다. 긴 컨텍스트의 Mistral-7B L4 셀은 이 단서를 달고 읽어야 한다(`v11_results/analyze_v2.txt` 132\~133행).

**Failed deployment configurations.** `torch.compile` 변형들과 FlashAttention-2 + CUDA Graphs 셀은 CUDA 캐싱 할당자 오류로 실패했다. 충돌을 우회하는 대신 이 셀들을 제외했으며, 그래서 6절의 소프트웨어 스택 행렬은 의도보다 성기다. 목록은 부록 C에 있다.

**FlashDecoding++ (no public release).** FlashDecoding++ 논문은 저자들의 공개 소스 코드가 없고(관련된 닫힌 이슈 링크는 2절 참조), 같은 그룹과 Infinigence-AI의 후속작 FlashDecoding++Next도 비공개 소스다. 우리 테스트베드에서 FlashDecoding++ 셀은 하나도 재현할 수 없었다. 6절에서 FlashAttention-3와 FlashInfer 재현을 가장 가까운 공개 비교 대상으로 대신 썼다. 실행 비용 완화책으로서 커널 융합과 CUDA Graphs를 논문 간에 비교하는 일은 미해결로 남아 있으며, 앞으로 FlashDecoding++ 코드가 공개되어야 가능하다.

## 10 Conclusion

Modal에서 호스팅한 H100 SXM5에서 짧은 컨텍스트, 배치 1, bf16 가중치로 7\~8B급 GQA 트랜스포머를 돌리는 이 워크로드에서 결정적인 제약은 커널별 CPU 실행 오버헤드다. ctx{{< katex >}}=2048{{< /katex >}} 대표 셀에서 {{< katex >}}N{=}10{{< /katex >}}으로 측정한 세션 내 CUDA Graphs A/B는 {{< katex >}}1.259\times{{< /katex >}} 속도 향상을 내며, 95% 부트스트랩 신뢰구간은 {{< katex >}}[1.253, 1.267]{{< /katex >}}, 세션 간 CV는 0.9%다. 같은 컨텍스트의 Modal 호스팅 L4에서는 결정적인 제약이 HBM 대역폭이며, 같은 개입의 A/B 결과는 효과 없음({{< katex >}}1.028\times{{< /katex >}})이다.

Graphs 개입은 이 논문이 결정적인 제약을 기록한 영역, 즉 H100, 배치 1, 짧은 컨텍스트에서 가장 가치가 크다. H100에서 배치 4가 되면 스텝당 커널 작업은 늘어나는데 실행 예산은 사실상 고정되어 있으므로, 실행 비용의 비율이 줄고 graphed 속도 향상도 함께 준다(9절). Graphs 결과는 *단일 스트림 디코드에서 어떤 제약이 결정적인가*에 대한 증거로 보고하는 것이지, 배치 크기와 무관하게 통하는 보편적 최적화 처방으로 내놓는 것이 아니다.

피지컬 AI 추론에 대한 배포 시사점은 GPU 간 스윕만 보았을 때보다 더 뚜렷하다. L4에서 GPTQ + ExLlamaV2로 바꾸면 Qwen-2.5-7B 스텝 시간이 62.32 ms(bf16)에서 17.36 ms로 줄어든다. 이 {{< katex >}}3.59\times{{< /katex >}} 향상은 Ada SM89에서 AutoAWQ + Marlin(45.24 ms, bf16 대비 {{< katex >}}1.38\times{{< /katex >}})으로는 얻을 수 없다. 이 워크로드에서는 L4에서의 커널 선택이 GPU 업그레이드보다 중요하다. ExLlamaV2를 쓴 L4는 Qwen-2.5-7B를 17.36 ms/step으로, CUDA Graphs를 쓴 H100은 같은 워크로드를 11.78 ms/step으로 돌린다. 피지컬 AI, 로보틱스, 엣지 코파일럿, 온디바이스 어시스턴트의 주류인 스트리밍 디코드 워크로드에서 배포 사다리 L4 {{< katex >}}\rightarrow{{< /katex >}} L40S {{< katex >}}\rightarrow{{< /katex >}} A100 {{< katex >}}\rightarrow{{< /katex >}} H100은 서빙한 토큰당 비용의 사다리가 아니다.

측정한 7\~8B GQA bf16 단일 스트림 형태는 VLA 정책 헤드(OpenVLA-7B [12], {{< katex >}}\pi_{0}{{< /katex >}} [3], RT-2급 [4]), 차량 실내 언어 스택, 온디바이스 코파일럿이 서빙 시점에 돌리는 바로 그 형태다. 이런 배포에서 중요한 질문은 최대 FLOPs나 최대 HBM 대역폭이 아니라, 커널과 Graphs 수단을 적용한 뒤 배치 1에서 실제로 달성한 스텝 시간이다. 이 지표로 보면 ExLlamaV2를 쓴 L4 경로는 17.36 ms/step, Graphs를 쓴 H100 경로는 11.78 ms/step이며, L4는 Modal 공시 요금 기준 GPU 시간당 약 {{< katex >}}12\times{{< /katex >}} 저렴한 실리콘이다 [17]. 이 워크로드 부류에서 서빙한 토큰당 비용의 격차는 배포 사다리를 따라가지 않는다.

더 큰 배치(배치 4에서 이미 Graphs의 효과가 줄어든다, 9절), head_dim{{< katex >}}=128{{< /katex >}}의 GQA 이외의 어텐션 변형, bf16 이외의 데이터 타입, NVIDIA 이외의 가속기, Blackwell급 NVIDIA 실리콘, Modal 이외의 호스팅, 다중 스트림 서빙으로의 일반화는 범위 밖이다. 이를 주장하지 않는다.

## A Reproducibility

**Modal setup.** 모든 셀은 Modal(프로필 `kaikaku`)에서 실행했다. 컨테이너 이미지는 `debian_slim` 기반에 PyTorch 2.4, transformers 4.45.x, 미리 빌드한 `flash-attn` 2.6.3 휠, `autoawq` 0.2.7.post3을 설치한 것이다. GPU 종류는 Modal의 네 가지 SKU인 H100, A100-80GB, L40S, L4다. 결과는 Modal 볼륨 `paper-b7-v11-results`에 저장한다.

**Measurement-pipeline provenance.** 주 행렬의 Qwen-2.5-7B-Instruct 셀 14개는 `v10_results/cells/qwen25_7b_<gpu>_ctx<ctx>.json`에 있으며 v10 스윕 스크립트로 만들었다. 주 행렬의 Mistral-7B-Instruct-v0.3 셀 14개와 Llama-3.1-8B-Instruct 셀 14개는 `v11_results/cells/`에 있으며 v11 스윕 스크립트로 만들었다. 두 스크립트는 같은 컨테이너 기본 이미지(PyTorch 2.4가 들어간 `debian_slim`), 같은 측정 프로토콜(워밍업 5스텝 + 측정 단일 토큰 AR 디코드 30스텝, sdpa 어텐션, bf16, 배치 크기 1), 같은 Modal 클라우드 GPU 호스트를 쓴다. 유일한 차이는 v11 스크립트가 Llama를 위해 HuggingFace 게이트 모델 인증을 추가한다는 점이다. 통합 분석 스크립트가 읽는 필드(`p50_ms`, `step_times_ms`, `weight_bytes`, `kv_bytes_avg`, `bytes_per_token_kv`)는 두 스크립트 버전에서 동일하다. 파생 Qwen 스윕(CUDA Graphs, 소프트웨어 스택, 프로파일, 양자화)은 v11 스크립트로 다시 측정했으며 `v11_results/cells/`에 있다.

**Cell artefacts.** 측정 셀마다 `v11_results/cells/` 아래에 JSON 파일이 하나씩 생긴다(주 행렬 Qwen 셀은 `v10_results/cells/` 아래). 셀 JSON에는 `arch`, `gpu`, `ctx`, `p50_ms`, `weight_bytes`, `bytes_per_token_kv`, `avg_ctx_during_measure`, `kv_bytes_avg`, `bw_peak_gbs`, `t_floor_ms`, `R_floor`, `n_layers`, `source`(그 셀을 만든 측정 스크립트 버전) 키가 들어 있다. CUDA Graphs 셀에는 추가로 `eager_p50_ms`와 `graphed_p50_ms`가, OFT 셀에는 `attn`, `compile`, `graphs` 플래그가, 프로파일 셀에는 `bw_util`과 `cpu_cuda_ratio`가 들어 있다.

> **역주.** OFT는 6절의 소프트웨어 스택 행렬(표 5)을 만든 리그를 가리키는 저자들의 내부 이름이다. 본문은 약어를 풀어 쓰지 않는다.

**Re-running.** 측정 스크립트는 모두 `paper_b7/modal_validate/v11/` 아래에 있다. 스윕을 다시 실행하려면 그 디렉터리에서 Modal CLI를 호출한다: `modal run <script>.py`. 스크립트는 Modal 볼륨에 직접 결과를 쓰고, `analyze.py`가 볼륨 내용을 `v11_results/cells/`로 가져와 `v11_results/v11_fit_summary.json`과 `v11_results/analyze_v2.txt`를 만든다.

**Seeds and allocator state.** 난수 시드는 고정하지 않았다. 각 셀은 측정 단일 토큰 디코드 30스텝의 중앙값을 보고하므로 실행 간 호스트 잡음이 흡수된다. 일부 H100 셀에서 보이는 이봉(bimodal) 워밍업 꼬리(측정 스텝 앞쪽 16개는 20\~21 ms 대역, 뒤쪽 14개는 17\~18 ms 대역)는 모델 출력의 무작위성보다는 GPU 클럭이나 커널 선택기의 수렴과 들어맞는다.

**The `\artifact` notation.** 논문 전반에서 `v11_results/some_file.json` 형태의 인용은 `paper_b7/` 아래 저장소 기준 상대 경로를 가리킨다. 본문에서 인용한 모든 수치는 이 산출물 중 하나로 거슬러 올라갈 수 있다. 셀별 관측 스텝 시간과 하한은 `v11_results/analyze.py`가 출력한 `v11_results/analyze_v2.txt`에서, 세션별 CUDA Graphs A/B 중앙값은 5절에서 인용한 셀 JSON에서 가져왔다.

### A.1 Replication discipline

대표 셀의 세션별 JSON을 모두 공개한다. 여기에는 독립적인 H100 ctx{{< katex >}}=2048{{< /katex >}} eager 세션 세 개(v10 주 행렬 스윕, v11 OFT sdpa+eager 리그, v11 CUDA Graphs A/B 리그)와 독립적인 H100 ctx{{< katex >}}=2048{{< /katex >}} graphed 세션 두 개(v11 OFT sdpa+eager+Graphs 리그, v11 CUDA Graphs A/B 리그)가 포함된다. 세션 간 분산은 묻어 두지 않고 5절에 보고했다.

v10 주 스윕, v11 OFT 소프트웨어 스택 스윕, v11 CUDA Graphs A/B는 같은 모델 로딩 코드와 같은 디코드 루프 코드를 쓰지만 리그 스크립트가 다르고 서로 다른 날에 실행했다. 그래서 세션 간 분산을 논할 때 이들을 독립 세션으로 취급한다. 세 리그 스크립트는 같은 컨테이너 기본 이미지(PyTorch 2.4가 들어간 `debian_slim`), 같은 워밍업 5 + 측정 30 프로토콜, 같은 sdpa 어텐션 경로, 같은 bf16 가중치, 같은 Modal GPU SKU(H100), 같은 Qwen-2.5-7B-Instruct 체크포인트를 공유한다. 차이는 측정 구간이 시작되기 전에 워밍업 상태에 도달하는 방식뿐이며(OFT 리그는 FA2 대조 단계를 추가로 만들고, A/B 리그는 워밍업 후 CUDA Graph를 추가로 캡처한다), 이것이 바로 한정하고자 하는 변동성이다.

v12 재현 스윕은 이 논문의 기준(gold-standard) 재현이다. 단일 리그 스크립트(`modal_validate/v11/cuda_graphs_replication.py`), GPU당(H100과 L4) 새 Modal 컨테이너 {{< katex >}}N{=}3{{< /katex >}}개, A/B 리그와 같은 프로토콜(워밍업 5스텝, 측정 30스텝, StaticCache, sdpa 어텐션, bf16)을 썼다. 세션별 중앙값, 세션 간 평균, 속도 향상 범위는 표 3에 보고했다. 컨테이너마다 새 GPU를 할당받고 모델을 콜드 상태에서 다시 불러왔다. 드라이버 쪽에서 반환값 딕셔너리를 역직렬화하다 오류가 났기 때문에, 세션별 원본 p50 값은 워커 컨테이너의 stdout에서 추출했으며 `v12_results/replication/extracted_from_log.json`에 있다. 세션별 원본 30스텝 배열은 컨테이너 안에서 계산되었지만 이 실행에서는 복구할 수 없었다. 세션별 p50 수치가 논문에서 쓰는 핵심 통계이며, `v12_results/replication_run.log`의 컨테이너 stdout 기록에 있는 그대로 보고한다.

## B Per-cell observed step times and bandwidth floors

## C Failed experiments and missing cells

투명성을 위해 쓸 만한 데이터를 내지 못한 실험을 나열한다.

**Sweep writer crash to volume root.** 스윕 드라이버의 첫 버전은 Modal 컨테이너의 `/results`에 요약 JSON을 쓰려다 `PermissionError`로 실패했다. 개별 셀 JSON은 컨테이너 *안에서* Modal 볼륨에 정상적으로 쓰였다. 해결은 절차적이었다. 볼륨 마운트에만 쓰고 집계는 오프라인에서 한다. 과학적 한계가 아니라 배포상의 메모일 뿐이다.

**OOM on L4.** 24 GB VRAM의 L4에서 셀 네 개가 OOM이 났다. 수 킬로 토큰 KV 캐시를 쓰는 7\~8B bf16이니 예상한 결과다. Mistral-7B의 ctx{{< katex >}}=8192{{< /katex >}}와 ctx{{< katex >}}=16384{{< /katex >}}, Llama-3.1-8B의 ctx{{< katex >}}=8192{{< /katex >}}와 ctx{{< katex >}}=16384{{< /katex >}}다. 이 셀들은 행렬에서 빠져 있으며, 유효 셀 수를 48에서 44로 줄인다.

> **역주.** 이 목록은 3.3절, 표 1, 표 9와 맞지 않는다. 표들에는 Mistral-7B의 L4 셀 네 개가 모두 있고, 빠진 것은 Qwen-2.5-7B와 Llama-3.1-8B의 L4 ctx 8192/16384다. 또한 3.3절은 Qwen의 OOM이 용량 한계가 아니라 A/B 프로토콜의 인공물이라고 진단하는 반면, 이 문단은 "예상한 결과"라고 적는다. 원문 그대로 옮겼다.

**CUDA caching allocator errors.** H100 소프트웨어 스택 행렬의 셀 네 개가 CUDA 캐싱 할당자 오류로 실패했다.

- `torch.compile` + eager (sdpa)
- `torch.compile` + CUDA Graphs (sdpa)
- FlashAttention-2 + CUDA Graphs
- `torch.compile` + FlashAttention-2

충돌을 우회하지 않았으며, 이 셀들은 표 5에서 제외했다. 실행된 두 셀(sdpa+eager와 sdpa+eager+Graphs)이 관심 있는 비교를 담고 있으므로 해석상의 손실은 제한적이다.

**Background-process death.** 초기 스윕 드라이버는 오래 걸리는 Modal 작업을 백그라운드로 돌리기 위해 셸 패턴 `(cmd &)`를 썼는데, 실행한 셸이 종료되자 백그라운드 프로세스도 죽었다. 부모 프로세스 그룹에서 떼어 내기 위해 `setsid nohup`으로 바꾸었다. 절차상의 메모이며 과학적 한계는 아니다.

**ncu blocked on Modal.** Nsight Compute는 Modal 클라우드 컨테이너에서는 쓸 수 없는 호스트 드라이버 접근 권한을 요구한다. 대신 `torch.profiler`와 해석적 바이트 수를 썼다(8절). 이 대체로 인해 커널별 HBM과 SM 활용도의 정답 값을 잃었고, 프로파일러에서는 GPU 간 패턴 증거만 얻는다.

## D Kernel count and replicate terminology

**Kernel-count breakdown per decode step.** 5절과 6절에서 인용한 레이어당 {{< katex >}}\sim 10{{< /katex >}}개 커널이라는 수치는, 고정된 레이어별 커널 순서에 스텝 전체에 한 번씩 도는 소수의 전역 커널을 더해 얻은 것이다. 여기서 측정한 GQA 아키텍처 세 종(head_dim 128의 Qwen-2.5-7B, Mistral-7B, Llama-3.1-8B)에서 디코더 블록 하나의 커널 순서는 다음과 같다.

1. RMSNorm (입력);
2. Q 프로젝션 (GEMM);
3. K 프로젝션 (GEMM);
4. V 프로젝션 (GEMM);
5. RoPE 회전 (일부 PyTorch 경로에서는 프로젝션에 융합, 다른 경로에서는 별도);
6. SDPA 어텐션 호출 (주 행렬에서 쓴 디스패처에서는 융합 커널 하나);
7. 출력 프로젝션 (GEMM);
8. 잔차 덧셈;
9. RMSNorm (어텐션 뒤);
10. MLP gate 프로젝션 (GEMM);
11. MLP up 프로젝션 (GEMM, 흔히 gate와 융합);
12. SiLU 활성화 (융합);
13. MLP down 프로젝션 (GEMM);
14. 잔차 덧셈.

블록당 {{< katex >}}\sim 10{{< /katex >}}개 커널이라는 실행 횟수 기준값은, 셀에서 쓴 PyTorch 2.4 디스패치 경로에서 이 단계들 중 여러 개가 하나의 실행으로 융합된다는 점을 반영한다(RoPE를 프로젝션에 융합, gate-up 융합, 잔차 덧셈을 다음 연산에 흡수). 아키텍처와 선택된 SDPA 백엔드에 따라 블록당 서로 다른 실행이 8\~12개 관찰된다. 여기에 스텝 전체의 전역 커널로 임베딩 조회(실행 1회), 마지막 RMSNorm(실행 1회), LM 헤드 프로젝션(실행 1회)이 더해져, Qwen-2.5-7B(디코더 블록 28개)에서는 디코드 스텝당 대략 {{< katex >}}28 \cdot 10 + 3 \approx 283{{< /katex >}}회의 커널 실행이 된다. Llama-3.1-8B와 Mistral-7B-v0.3은 블록 32개를 쓰므로 323 근처가 된다. 이것은 실행 예산을 따져 보기 위한 크기 수준의 기준값이지 고정된 횟수가 아니며, 정확한 값은 워밍업 때 디스패처가 내리는 선택에 달려 있다. 이전 초안에서 쓴 커널당 31 {{< katex >}}\mu{{< /katex >}}s 수치는 삭제했다. 융합된 실행 여러 개가 서로 다른 양의 일을 할 때는 커널당으로 나누는 것이 잘 정의되지 않기 때문이다. 이제는 커널당 평균이 아니라 스텝당 전체 실행 오버헤드를 기준으로 논한다.

> **역주.** 그림 4는 같은 양을 "28 layers × \~10 kernels/layer = 281 kernels"로 적고, 이 부록은 283으로 적는다. 둘 다 어림값이며 본문은 차이를 설명하지 않는다.

**Replicate terminology.** 논문은 *반복 측정(replicate)*\ 이라는 말을 두 가지 다른 뜻으로 쓰며, 여기서 이를 정리한다.

*세션 내 반복 측정(within-session replicates)*\ 은 Modal 컨테이너 실행 하나 안에서, 워밍업 5스텝 뒤에 측정한 단일 토큰 디코드 30스텝이다. 이 30스텝의 중앙값이 셀이 보고하는 {{< katex >}}t_{\mathrm{obs}}{{< /katex >}}다. 30스텝에 걸친 CV는 워밍업된 한 세션 안의 스텝별 지터를 정량화하며, 작다({{< katex >}}N{=}10{{< /katex >}}의 H100 ctx{{< katex >}}=2048{{< /katex >}} 대표 셀에서 eager {{< katex >}}<1\%{{< /katex >}}, graphed {{< katex >}}<0.5\%{{< /katex >}}).

*세션 간 반복 측정(cross-session replicates)*\ 은 같은 셀을 독립적인 Modal 컨테이너로 실행한 것이다. 세션 간 반복 측정마다 콜드 컨테이너에서 시작해 모델을 다시 불러오고, 워밍업을 반복하고, 자체 30스텝 세션 내 구간을 만든다. H100 ctx{{< katex >}}=2048{{< /katex >}} 셀의 {{< katex >}}N{=}10{{< /katex >}} 대표 재현은 이런 의미의 세션 간 반복이다. 독립 컨테이너 실행 열 번이 각자 eager와 graphed의 세션 내 중앙값을 내고, 짝지은 graphed/eager 속도 향상 열 개가 나오며, 부트스트랩 95% 신뢰구간은 이 짝지은 비율 열 개에 걸쳐 계산한다.

핵심 수치의 안정성 주장을 뒷받침하는 CV는 세션 내 중앙값들의 세션 간 CV(eager 0.9%, graphed 0.2%)이며, 반복 측정과 30스텝 구간 전체를 한데 모은 스텝 시간의 세션 간 CV가 *아니다*. 후자는 세션 내 지터와 세션 간 호스트 잡음을 섞어 버리므로 논문에서 쓰지 않는다. 본문에서 앞서 아무 설명 없이 *N=3 replicate*라고 쓴 곳은 *N=3 세션 간 반복 측정*을 뜻하고, *N=30*이라고 쓴 곳은 *셀당 세션 내 스텝 측정 30회*를 뜻한다.
