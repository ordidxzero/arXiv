## Abstract

대규모 언어 모델(LLM)을 높은 처리량(throughput)으로 서빙하려면 한 번에 충분히 많은 요청을 배치(batch)로 묶어 처리해야 한다. 그러나 기존 시스템은 이를 잘 해내지 못한다. 요청마다 필요한 키-값 캐시(KV cache) 메모리가 매우 크고, 그 크기가 동적으로 커졌다 줄어들기 때문이다. 이 메모리를 비효율적으로 관리하면 단편화(fragmentation)와 중복 저장 때문에 상당량이 낭비되고, 배치 크기가 제한된다. 이 문제를 해결하기 위해 본 논문은 운영체제의 고전적인 가상 메모리와 페이징 기법에서 착안한 어텐션 알고리즘인 PagedAttention을 제안한다. 이를 기반으로 LLM 서빙 시스템 vLLM을 구축했다. vLLM은 (1) KV 캐시 메모리 낭비를 거의 0에 가깝게 줄이고, (2) 요청 내부와 요청 사이에서 KV 캐시를 유연하게 공유해 메모리 사용량을 더 줄인다. 평가 결과, vLLM은 FasterTransformer, Orca 같은 당시 최고 수준의 시스템과 같은 수준의 지연 시간(latency)에서 널리 쓰이는 LLM의 처리량을 2–4배 높였다. 이 향상 폭은 시퀀스가 길수록, 모델이 클수록, 디코딩 알고리즘이 복잡할수록 더 커진다. vLLM의 소스 코드는 https://github.com/vllm-project/vllm 에 공개되어 있다.

> **역주.** 이 논문 전체에서 "요청(request)"은 사용자가 LLM 서비스에 보낸 하나의 프롬프트와 그에 대한 생성 작업을, "서빙(serving)"은 학습이 끝난 모델을 서비스로 띄워 요청에 응답하는 일을 뜻한다. 키-값 캐시, 단편화 등은 본문에서 처음 나올 때 풀어서 설명한다.

## 1 Introduction

GPT [5, 37], PaLM [9] 같은 대규모 언어 모델(LLM)이 등장하면서 프로그래밍 어시스턴트 [6, 18], 범용 챗봇 [19, 35] 같은 새로운 애플리케이션이 가능해졌고, 이들은 우리의 업무와 일상에 깊은 영향을 미치기 시작했다. 많은 클라우드 기업 [34, 44]이 이런 애플리케이션을 호스팅 서비스로 제공하려고 경쟁하고 있다. 하지만 이 애플리케이션을 돌리는 데는 GPU 같은 하드웨어 가속기가 대량으로 필요해 비용이 매우 많이 든다. 최근 추정에 따르면 LLM 요청 하나를 처리하는 비용은 전통적인 키워드 검색 질의의 10배에 이를 수 있다 [43]. 이처럼 비용이 높으므로, LLM 서빙 시스템의 처리량을 높여 요청당 비용을 낮추는 일이 점점 더 중요해지고 있다.

LLM의 중심에는 자기회귀(autoregressive) Transformer 모델 [53]이 있다. 이 모델은 입력(프롬프트)과 지금까지 자신이 생성한 출력 토큰 시퀀스를 바탕으로 단어(토큰)를 한 번에 하나씩 생성한다. 요청마다 모델이 종료 토큰을 출력할 때까지 이 비싼 과정을 반복한다. 이렇게 순차적으로 생성하기 때문에 작업이 메모리 병목(memory-bound)이 되어 GPU의 연산 능력이 충분히 활용되지 못하고, 서빙 처리량이 제한된다.

여러 요청을 한 배치로 묶으면 처리량을 높일 수 있다. 다만 많은 요청을 한 배치에서 처리하려면 요청별 메모리 공간을 효율적으로 관리해야 한다. 예를 들어 그림 1(왼쪽)은 40GB RAM을 가진 NVIDIA A100 GPU에서 130억(13B) 파라미터 LLM을 서빙할 때의 메모리 분포를 보여 준다. 메모리의 약 65%는 서빙 중 변하지 않는 모델 가중치에 할당된다. 30% 가까이는 요청의 동적 상태를 저장하는 데 쓰이는데, Transformer에서 이 상태는 어텐션 메커니즘의 키(key)와 값(value) 텐서이며 흔히 KV 캐시 [41]라고 부른다. KV 캐시는 앞선 토큰들의 문맥을 담고 있어, 새 출력 토큰을 차례로 생성할 때 쓰인다. 나머지 작은 비율은 활성값(activation, LLM을 계산하는 동안 임시로 만들어지는 텐서) 등 다른 데이터에 쓰인다. 모델 가중치는 일정하고 활성값은 GPU 메모리의 작은 부분만 차지하므로, KV 캐시를 어떻게 관리하느냐가 최대 배치 크기를 정하는 핵심이 된다. KV 캐시를 비효율적으로 관리하면 그림 1(오른쪽)처럼 배치 크기가, 나아가 LLM의 처리량이 크게 제한될 수 있다.

> *(그림 1: 원문 PDF 1쪽 참조. 왼쪽은 A100 40GB에서 13B LLM 서빙 시의 메모리 구성, 오른쪽은 배치 크기에 따른 처리량 그래프.)*

**그림 1.** 왼쪽: NVIDIA A100에서 130억 파라미터 LLM을 서빙할 때의 메모리 구성. 파라미터(회색)는 서빙하는 동안 GPU 메모리에 계속 남아 있다. KV 캐시(빨간색)용 메모리는 서빙 요청마다 할당·해제된다. 적은 양의 메모리(노란색)는 활성값을 위해 임시로 쓰인다. 오른쪽: vLLM은 기존 시스템 [31, 60]에서 나타나는 KV 캐시 메모리의 가파른 증가 곡선을 완만하게 만들어, 서빙 처리량을 눈에 띄게 높인다.

본 논문은 기존 LLM 서빙 시스템 [31, 60]이 KV 캐시 메모리를 효율적으로 관리하지 못한다는 점을 관찰했다. 주된 이유는 이 시스템들이 요청 하나의 KV 캐시를 연속된(contiguous) 메모리 공간에 저장하기 때문이며, 대부분의 딥러닝 프레임워크 [33, 39]가 텐서를 연속된 메모리에 저장하도록 요구하기 때문이다. 그런데 기존 딥러닝 워크로드의 텐서와 달리 KV 캐시에는 고유한 특성이 있다. 모델이 새 토큰을 생성함에 따라 시간에 따라 동적으로 커지고 줄어들며, 수명과 길이를 미리 알 수 없다. 이런 특성 때문에 기존 시스템의 방식은 두 가지 면에서 크게 비효율적이다.

첫째, 기존 시스템 [31, 60]은 내부 단편화와 외부 단편화를 모두 겪는다. 요청의 KV 캐시를 연속된 공간에 저장하려고, 요청의 최대 길이(예: 2048 토큰)만큼 연속된 메모리 덩어리를 미리 할당한다. 요청의 실제 길이는 최대 길이보다 훨씬 짧을 수 있으므로(예: 그림 11) 심각한 내부 단편화(internal fragmentation, 할당된 덩어리 안에서 쓰이지 않고 남는 공간)가 생길 수 있다. 게다가 실제 길이를 미리 안다 하더라도 사전 할당은 여전히 비효율적이다. 요청이 살아 있는 동안 덩어리 전체가 예약되므로, 지금 쓰이지 않는 부분이 있어도 더 짧은 다른 요청이 그 일부를 쓸 수 없기 때문이다. 또한 사전 할당 크기가 요청마다 다르므로 외부 단편화(external fragmentation, 할당된 덩어리들 사이에 조각난 빈 공간)도 상당할 수 있다. 실제로 그림 2의 프로파일링 결과를 보면 기존 시스템에서 KV 캐시 메모리 중 실제 토큰 상태를 저장하는 데 쓰이는 비율은 20.4%–38.2%에 불과하다.

> *(그림 2: 원문 PDF 2쪽 참조. Orca (Max), Orca (Pow2), Orca (Oracle), vLLM의 KV 캐시 사용 내역을 토큰 상태·예약·내부 단편화·외부 단편화 및 기타로 나눈 막대그래프.)*

**그림 2.** 6.2절의 실험 중 여러 LLM 서빙 시스템에서 낭비된 메모리의 평균 비율.

둘째, 기존 시스템은 메모리를 공유할 기회를 활용하지 못한다. LLM 서비스는 요청 하나에서 여러 출력을 생성하는 병렬 샘플링(parallel sampling), 빔 서치(beam search) 같은 고급 디코딩 알고리즘을 자주 쓴다. 이 경우 요청은 KV 캐시를 부분적으로 공유할 수 있는 여러 시퀀스로 이루어진다. 그러나 기존 시스템에서는 시퀀스들의 KV 캐시가 서로 다른 연속 공간에 따로 저장되므로 메모리 공유가 불가능하다.

이런 한계를 해결하기 위해 본 논문은 운영체제(OS)가 메모리 단편화와 공유 문제를 해결하는 방식, 즉 페이징을 사용하는 가상 메모리에서 착안한 어텐션 알고리즘 PagedAttention을 제안한다. PagedAttention은 요청의 KV 캐시를 블록(block)으로 나누며, 각 블록은 정해진 개수의 토큰에 대한 어텐션 키와 값을 담는다. PagedAttention에서 KV 캐시 블록은 연속된 공간에 저장될 필요가 없다. 따라서 OS의 가상 메모리처럼 KV 캐시를 더 유연하게 관리할 수 있다. 블록은 페이지, 토큰은 바이트, 요청은 프로세스에 해당한다고 보면 된다. 이 설계는 비교적 작은 블록을 필요할 때마다 할당해 내부 단편화를 줄이고, 모든 블록의 크기가 같으므로 외부 단편화를 없앤다. 마지막으로 같은 요청에 속한 서로 다른 시퀀스 사이, 심지어 서로 다른 요청 사이에서도 블록 단위로 메모리를 공유할 수 있다.

본 연구에서는 PagedAttention 위에 분산 LLM 서빙 엔진 vLLM을 구축했으며, KV 캐시 메모리 낭비를 거의 0에 가깝게 줄였다. vLLM은 PagedAttention과 함께 설계한(co-designed) 블록 단위 메모리 관리와 선점형(preemptive) 요청 스케줄링을 사용한다. vLLM은 GPT [5], OPT [62], LLaMA [52] 같은 널리 쓰이는 LLM을 지원하며, 단일 GPU의 메모리 용량을 넘는 크기의 모델도 지원한다. 다양한 모델과 워크로드에서 평가한 결과, vLLM은 모델 정확도에 전혀 영향을 주지 않으면서 당시 최고 수준의 시스템 [31, 60]보다 LLM 서빙 처리량을 2–4배 높였다. 이 향상은 시퀀스가 길수록, 모델이 클수록, 디코딩 알고리즘이 복잡할수록 더 두드러진다(4.3절).

> **역주.** 위 문단에서 "4.3절"로 연결된 참조는 원문 그대로이며, 성능 평가 결과 자체는 6절에 있다.

요약하면 본 논문의 기여는 다음과 같다.

- LLM 서빙에서 메모리 할당이 안고 있는 문제를 규명하고, 그것이 서빙 성능에 미치는 영향을 정량화한다.
- OS의 가상 메모리와 페이징에서 착안해, 페이지 단위로 나뉘어 비연속 메모리에 저장된 KV 캐시 위에서 동작하는 어텐션 알고리즘 PagedAttention을 제안한다.
- PagedAttention 위에 구축한 분산 LLM 서빙 엔진 vLLM을 설계하고 구현한다.
- 다양한 시나리오에서 vLLM을 평가하여, FasterTransformer [31], Orca [60] 같은 기존 최고 수준 솔루션을 크게 앞선다는 것을 보인다.

## 2 Background

이 절에서는 일반적인 LLM의 생성·서빙 절차와 LLM 서빙에 쓰이는 반복 단위(iteration-level) 스케줄링을 설명한다.

### 2.1 Transformer-Based Large Language Models

언어 모델링(language modeling)의 과제는 토큰 리스트 {{< katex >}}(x_1, \ldots, x_n){{< /katex >}}의 확률을 모델링하는 것이다. 언어에는 자연스러운 순서가 있으므로, 전체 시퀀스에 대한 결합 확률을 조건부 확률의 곱으로 분해하는 것이 일반적이다(자기회귀 분해(autoregressive decomposition) [3]라고도 한다).

{{< katex display=true >}}
P(x) = P(x_1) \cdot P(x_2 \mid x_1) \cdots P(x_n \mid x_1, \ldots, x_{n-1}). \tag{1}
{{< /katex >}}

Transformer [53]는 위 확률을 대규모로 모델링하는 사실상의 표준 아키텍처가 되었다. Transformer 기반 언어 모델에서 가장 중요한 구성 요소는 셀프 어텐션(self-attention) 층이다. 입력 은닉 상태 시퀀스 {{< katex >}}(x_1, \ldots, x_n) \in \mathbb{R}^{n \times d}{{< /katex >}}가 주어지면, 셀프 어텐션 층은 먼저 각 위치 {{< katex >}}i{{< /katex >}}에 선형 변환을 적용해 쿼리, 키, 값 벡터를 얻는다.

{{< katex display=true >}}
q_i = W_q x_i, \quad k_i = W_k x_i, \quad v_i = W_v x_i. \tag{2}
{{< /katex >}}

그다음 한 위치의 쿼리 벡터를 그 위치 이전(자기 자신 포함)의 모든 키 벡터와 곱해 어텐션 점수 {{< katex >}}a_{ij}{{< /katex >}}를 계산하고, 출력 {{< katex >}}o_i{{< /katex >}}를 값 벡터들의 가중 평균으로 계산한다.

{{< katex display=true >}}
a_{ij} = \frac{\exp(q_i^\top k_j / \sqrt{d})}{\sum_{t=1}^{i} \exp(q_i^\top k_t / \sqrt{d})}, \quad o_i = \sum_{j=1}^{i} a_{ij} v_j. \tag{3}
{{< /katex >}}

> **역주.** 즉 {{< katex >}}i{{< /katex >}}번째 토큰은 자신과 앞선 토큰들의 키와 얼마나 비슷한지(내적)에 비례해 앞선 토큰들의 값을 섞어 출력을 만든다. 뒤의 토큰은 보지 않는다. 이 때문에 이미 계산한 앞쪽 토큰의 키·값 벡터는 이후 단계에서 다시 계산할 필요 없이 저장해 두고 재사용할 수 있으며, 이것이 KV 캐시이다.

식 (3)의 계산(원문에는 "Eq. 4"로 적혀 있다) 외에, 임베딩 층, 피드포워드 층, 층 정규화(layer normalization) [2], 잔차 연결(residual connection) [22], 출력 로짓 계산, 식 (2)의 쿼리·키·값 변환 등 Transformer 모델의 나머지 구성 요소는 모두 {{< katex >}}y_i = f(x_i){{< /katex >}} 형태로 각 위치에 독립적으로 적용된다.

> **역주.** 원문은 "Besides the computation in Eq. 4"라고 쓰지만, 문맥상 어텐션 계산은 식 (3)이다(식 (4)는 4.1절의 블록 단위 어텐션이다). 번역에서는 원문 표기의 불일치를 위와 같이 밝혀 둔다.

### 2.2 LLM Service & Autoregressive Generation

학습을 마친 LLM은 흔히 조건부 생성 서비스(예: 완성(completion) API [34]나 챗봇 [19, 35])로 배포된다. LLM 서비스에 보내는 요청은 입력 프롬프트 토큰 리스트 {{< katex >}}(x_1, \ldots, x_n){{< /katex >}}를 제공하고, 서비스는 식 (1)에 따라 출력 토큰 리스트 {{< katex >}}(x_{n+1}, \ldots, x_{n+T}){{< /katex >}}를 생성한다. 프롬프트와 출력 리스트를 이어 붙인 것을 시퀀스(sequence)라고 한다.

식 (1)의 분해 때문에 LLM은 새 토큰을 하나씩만 샘플링해 생성할 수 있고, 각 새 토큰의 생성은 해당 시퀀스의 이전 모든 토큰, 구체적으로는 그 토큰들의 키와 값 벡터에 의존한다. 이 순차 생성 과정에서 기존 토큰의 키와 값 벡터는 이후 토큰 생성에 쓰이도록 캐시해 두는 경우가 많으며, 이것이 KV 캐시이다. 한 토큰의 KV 캐시는 그 앞의 모든 토큰에 의존한다는 점에 유의하자. 즉 같은 토큰이 시퀀스의 서로 다른 위치에 나타나면 그 KV 캐시는 서로 다르다.

요청 프롬프트가 주어졌을 때, LLM 서비스의 생성 계산은 두 단계로 나눌 수 있다.

**프롬프트 단계(prompt phase).** 사용자 프롬프트 전체 {{< katex >}}(x_1, \ldots, x_n){{< /katex >}}를 입력으로 받아 첫 번째 새 토큰의 확률 {{< katex >}}P(x_{n+1} \mid x_1, \ldots, x_n){{< /katex >}}을 계산한다. 이 과정에서 키 벡터 {{< katex >}}k_1, \ldots, k_n{{< /katex >}}과 값 벡터 {{< katex >}}v_1, \ldots, v_n{{< /katex >}}도 함께 생성된다. 프롬프트 토큰 {{< katex >}}x_1, \ldots, x_n{{< /katex >}}이 모두 이미 알려져 있으므로 프롬프트 단계의 계산은 행렬-행렬 곱셈 연산으로 병렬화할 수 있다. 따라서 이 단계는 GPU가 본래 가진 병렬성을 효율적으로 활용한다.

**자기회귀 생성 단계(autoregressive generation phase).** 나머지 새 토큰을 순차적으로 생성한다. 반복 {{< katex >}}t{{< /katex >}}에서 모델은 토큰 {{< katex >}}x_{n+t}{{< /katex >}} 하나를 입력으로 받아, 키 벡터 {{< katex >}}k_1, \ldots, k_{n+t}{{< /katex >}}와 값 벡터 {{< katex >}}v_1, \ldots, v_{n+t}{{< /katex >}}를 사용해 확률 {{< katex >}}P(x_{n+t+1} \mid x_1, \ldots, x_{n+t}){{< /katex >}}를 계산한다. 위치 1부터 {{< katex >}}n+t-1{{< /katex >}}까지의 키·값 벡터는 이전 반복에서 이미 캐시되어 있으므로, 이번 반복에서는 새 키·값 벡터 {{< katex >}}k_{n+t}{{< /katex >}}와 {{< katex >}}v_{n+t}{{< /katex >}}만 계산한다. 이 단계는 시퀀스가 최대 길이(사용자가 지정하거나 LLM이 허용하는 길이)에 도달하거나 시퀀스 종료(`<eos>`) 토큰이 나오면 끝난다. 서로 다른 반복의 계산은 데이터 의존성 때문에 병렬화할 수 없고, 대체로 효율이 낮은 행렬-벡터 곱셈을 쓴다. 그 결과 이 단계는 GPU 연산을 크게 덜 쓰는 메모리 병목 상태가 되며, 요청 하나의 지연 시간 중 대부분을 차지한다.

### 2.3 Batching Techniques for LLMs

여러 요청을 배치로 묶으면 LLM 서빙의 연산 활용도를 높일 수 있다. 요청들이 같은 모델 가중치를 공유하므로, 가중치를 옮기는 오버헤드가 배치 안의 요청들에 나뉘어 분담되고(amortized), 배치 크기가 충분히 크면 이 오버헤드는 계산 오버헤드에 묻힌다. 그러나 LLM 서비스의 요청을 배치로 묶는 일은 두 가지 이유로 쉽지 않다. 첫째, 요청이 도착하는 시각이 서로 다르다. 단순한 배칭 전략은 먼저 온 요청이 나중 요청을 기다리게 하거나, 먼저 온 요청이 끝날 때까지 새로 도착한 요청을 늦추게 되어 큰 대기 지연(queueing delay)을 일으킨다. 둘째, 요청마다 입력과 출력 길이가 크게 다를 수 있다(그림 11). 가장 단순한 배칭 기법은 요청들의 입력과 출력에 패딩을 넣어 길이를 맞추는데, 이는 GPU 연산과 메모리를 낭비한다.

이 문제를 해결하기 위해 셀룰러 배칭(cellular batching) [16], 반복 단위 스케줄링(iteration-level scheduling) [60] 같은 세밀한(fine-grained) 배칭 메커니즘이 제안되었다. 요청 단위로 동작하는 기존 방식과 달리 이 기법들은 반복(iteration) 단위로 동작한다. 매 반복이 끝난 뒤 완료된 요청은 배치에서 빼고 새 요청을 넣는다. 따라서 새 요청은 배치 전체가 끝나기를 기다리지 않고 한 번의 반복만 기다리면 처리될 수 있다. 또한 특수한 GPU 커널을 쓰면 입력과 출력에 패딩을 넣을 필요도 없어진다. 대기 지연과 패딩으로 인한 비효율을 줄임으로써, 세밀한 배칭 메커니즘은 LLM 서빙의 처리량을 크게 높인다.

## 3 Memory Challenges in LLM Serving

세밀한 배칭은 연산 낭비를 줄이고 요청을 더 유연하게 묶을 수 있게 해 주지만, 함께 배치할 수 있는 요청 수는 여전히 GPU 메모리 용량, 특히 KV 캐시를 저장하는 데 할당된 공간에 의해 제한된다. 다시 말해 서빙 시스템의 처리량은 메모리 병목이다. 이 병목을 넘으려면 메모리 관리에서 다음 과제들을 해결해야 한다.

**Large KV cache.** KV 캐시 크기는 요청 수에 따라 빠르게 늘어난다. 예를 들어 130억 파라미터 OPT 모델 [62]에서 토큰 하나의 KV 캐시는 800KB를 차지하며, 이는 2(키와 값 벡터) × 5120(은닉 상태 크기) × 40(층 수) × 2(FP16당 바이트 수)로 계산된다. OPT는 최대 2048 토큰의 시퀀스를 생성할 수 있으므로, 요청 하나의 KV 캐시를 저장하는 데 필요한 메모리는 최대 1.6GB에 이를 수 있다. 현재 GPU의 메모리 용량은 수십 GB 수준이다. 사용 가능한 메모리를 전부 KV 캐시에 할당하더라도 수용할 수 있는 요청은 수십 개 정도다. 게다가 그림 2처럼 메모리를 비효율적으로 관리하면 배치 크기가 더 줄어든다. 또한 현재 추세에서는 GPU의 연산 속도가 메모리 용량보다 빠르게 증가한다 [17]. 예를 들어 NVIDIA A100에서 H100으로 넘어갈 때 FLOPS는 2배 넘게 늘지만 GPU 메모리는 최대 80GB로 그대로다. 따라서 저자들은 메모리가 갈수록 더 중요한 병목이 될 것이라고 본다.

**Complex decoding algorithms.** LLM 서비스는 사용자가 고를 수 있는 여러 디코딩 알고리즘을 제공하며, 알고리즘마다 메모리 관리의 복잡도에 미치는 영향이 다르다. 예를 들어 사용자가 하나의 입력 프롬프트로부터 여러 개의 랜덤 샘플을 요청하는 경우(프로그램 제안 [18]의 전형적인 사용 사례), 프롬프트 부분의 KV 캐시는 공유해 메모리 사용량을 최소화할 수 있다. 이 부분은 실험(6.3절)에서 전체 KV 캐시 메모리의 12%를 차지했다. 반면 자기회귀 생성 단계의 KV 캐시는 샘플 결과가 서로 다르고 문맥과 위치에 의존하므로 공유하지 않아야 한다. KV 캐시를 공유하는 정도는 사용하는 디코딩 알고리즘에 따라 달라진다. 빔 서치 [49] 같은 더 정교한 알고리즘에서는 서로 다른 빔들이 KV 캐시의 더 큰 부분을 공유할 수 있으며(최대 55%의 메모리 절감, 6.3절 참조), 디코딩이 진행됨에 따라 공유 패턴도 변한다.

**Scheduling for unknown input & output lengths.** LLM 서비스의 요청은 입력과 출력 길이가 제각각이다. 그래서 메모리 관리 시스템은 폭넓은 범위의 프롬프트 길이를 수용해야 한다. 또 디코딩 중에 요청의 출력 길이가 늘어나면 그 KV 캐시에 필요한 메모리도 함께 커지며, 그 결과 새로 들어온 요청이나 이미 진행 중인 생성을 위한 가용 메모리가 바닥날 수 있다. 시스템은 일부 요청의 KV 캐시를 삭제하거나 GPU 메모리 밖으로 스왑 아웃(swap out)하는 등의 스케줄링 결정을 내려야 한다.

### 3.1 Memory Management in Existing Systems

현재 딥러닝 프레임워크 [33, 39]의 대부분의 연산자는 텐서가 연속된 메모리에 저장되어 있어야 하므로, 기존 LLM 서빙 시스템 [31, 60]도 요청 하나의 KV 캐시를 여러 위치에 걸친 하나의 연속된 텐서로 저장한다. LLM의 출력 길이를 예측할 수 없기 때문에, 이 시스템들은 요청의 실제 입력 길이나 최종 출력 길이와 무관하게 요청이 가질 수 있는 최대 시퀀스 길이를 기준으로 메모리 덩어리를 정적으로 할당한다.

그림 3은 최대 가능 시퀀스 길이가 2048인 요청 A와 최대 512인 요청 B, 두 요청을 보여 준다. 기존 시스템의 덩어리 사전 할당 방식에는 메모리 낭비의 주요 원인이 세 가지 있다. 미래 토큰을 위한 예약 슬롯(reserved), 가능한 최대 시퀀스 길이에 맞춰 과하게 할당(over-provisioning)해서 생기는 내부 단편화, 그리고 버디 할당자(buddy allocator, 메모리를 2의 거듭제곱 크기로 쪼개고 합치며 할당하는 방식) 같은 메모리 할당자에서 비롯되는 외부 단편화다. 외부 단편화는 생성된 토큰에 쓰이는 일이 결코 없으며, 이는 요청을 서빙하기 전에 이미 알 수 있다. 내부 단편화도 쓰이지 않고 남지만, 이는 요청의 샘플링이 끝나고 나서야 알 수 있다. 이 둘은 순수한 메모리 낭비이다. 예약된 메모리는 결국 사용되기는 하지만, 특히 예약 공간이 클 때 요청이 진행되는 내내 그 공간을 붙들고 있어, 다른 요청을 처리하는 데 쓸 수 있었던 공간을 차지하게 된다. 그림 2는 실험에서 낭비된 메모리의 평균 비율을 보여 주며, 기존 시스템에서 실제로 유효한 메모리가 20.4%까지 낮을 수 있음을 드러낸다.

> *(그림 3: 원문 PDF 4쪽 참조. 요청 A(최대 2048)와 요청 B(최대 512)의 KV 캐시 슬롯 배치도. 요청 A는 프롬프트 7개와 생성 토큰 1개, 예약 슬롯 2개, 쓰이지 않는 슬롯 2038개로, 요청 B는 프롬프트 3개와 예약 슬롯 1개, 쓰이지 않는 슬롯 507개로 표시되고, 그 사이에 외부 단편화가 있다.)*

**그림 3.** 기존 시스템의 KV 캐시 메모리 관리. 예약(reserved), 내부 단편화, 외부 단편화의 세 가지 메모리 낭비가 있어 다른 요청이 메모리에 들어가지 못하게 한다. 각 메모리 슬롯에 적힌 토큰은 그 토큰의 KV 캐시를 나타낸다. 같은 토큰이라도 위치가 다르면 KV 캐시가 다를 수 있음에 유의하자.

단편화에 대한 잠재적 해법으로 압축(compaction) [54]이 제안되어 있지만, 성능에 민감한 LLM 서빙 시스템에서는 KV 캐시가 방대하기 때문에 압축을 수행하는 것이 비현실적이다. 압축을 하더라도, 기존 메모리 관리 시스템에서는 요청마다 사전 할당된 덩어리 공간 때문에 디코딩 알고리즘에 특화된 메모리 공유가 여전히 불가능하다.

## 4 Method

본 연구에서는 3절에서 설명한 과제를 해결하기 위해 새로운 어텐션 알고리즘 PagedAttention을 개발하고 LLM 서빙 엔진 vLLM을 구축한다. vLLM의 아키텍처는 그림 4와 같다. vLLM은 중앙 집중식 스케줄러(centralized scheduler)를 두어 분산된 GPU 워커들의 실행을 조율한다. KV 캐시 매니저는 PagedAttention 덕분에 KV 캐시를 페이지 방식으로 효과적으로 관리한다. 구체적으로 KV 캐시 매니저는 중앙 스케줄러가 보낸 명령에 따라 GPU 워커들의 물리적 KV 캐시 메모리를 관리한다.

### 4.1 PagedAttention

3절의 메모리 문제를 해결하기 위해, 운영체제의 고전적 아이디어인 페이징 [25]에서 착안한 어텐션 알고리즘 PagedAttention을 도입한다. 기존 어텐션 알고리즘과 달리 PagedAttention은 논리적으로 연속된 키와 값을 비연속 메모리 공간에 저장할 수 있게 한다. 구체적으로 PagedAttention은 각 시퀀스의 KV 캐시를 KV 블록으로 나눈다. 각 블록은 고정된 개수의 토큰에 대한 키와 값 벡터를 담으며,[^1] 이 개수를 KV 블록 크기(block size) {{< katex >}}B{{< /katex >}}라 한다. 키 블록을 {{< katex >}}K_j = (k_{(j-1)B+1}, \ldots, k_{jB}){{< /katex >}}, 값 블록을 {{< katex >}}V_j = (v_{(j-1)B+1}, \ldots, v_{jB}){{< /katex >}}라 하자. 그러면 식 (3)의 어텐션 계산(원문 표기는 Eq. 4)은 다음과 같은 블록 단위 계산으로 바꿀 수 있다.

[^1]: Transformer에서 각 토큰은 층(layer)마다, 그리고 한 층 안의 어텐션 헤드마다 키와 값 벡터 집합을 가진다. 모든 키·값 벡터를 하나의 KV 블록에서 함께 관리할 수도 있고, 헤드와 층마다 키·값 벡터에 별도의 블록을 두고 별도의 블록 테이블로 관리할 수도 있다. 두 설계 사이에 성능 차이는 없으며, 구현이 쉬운 두 번째 방식을 택했다.

어텐션을 계산하는 동안 PagedAttention 커널은 서로 다른 KV 블록을 따로 찾아서 가져온다. 그림 5는 PagedAttention의 예이다. 키와 값 벡터가 세 개의 블록에 나뉘어 있고, 이 세 블록은 물리 메모리에서 연속되어 있지 않다. 커널은 매번 쿼리 토큰("forth")의 쿼리 벡터 {{< katex >}}q_i{{< /katex >}}를 한 블록 안의 키 벡터 {{< katex >}}K_j{{< /katex >}}(예: 블록 0의 "Four score and seven"의 키 벡터)와 곱해 어텐션 점수 {{< katex >}}A_{ij}{{< /katex >}}를 계산하고, 나중에 {{< katex >}}A_{ij}{{< /katex >}}를 한 블록 안의 값 벡터 {{< katex >}}V_j{{< /katex >}}와 곱해 최종 어텐션 출력 {{< katex >}}o_i{{< /katex >}}를 얻는다.

### 4.2 KV Cache Manager

vLLM의 메모리 매니저의 핵심 아이디어는 운영체제의 가상 메모리 [25]와 유사하다. OS는 메모리를 고정 크기의 페이지로 나누고, 사용자 프로그램의 논리 페이지(logical page)를 물리 페이지(physical page)에 대응시킨다. 연속된 논리 페이지가 비연속 물리 메모리 페이지에 대응될 수 있어서, 사용자 프로그램은 메모리가 연속된 것처럼 접근할 수 있다. 또한 물리 메모리 공간을 미리 전부 예약할 필요가 없으므로 OS가 필요에 따라 물리 페이지를 동적으로 할당할 수 있다. vLLM은 가상 메모리의 이런 아이디어를 이용해 LLM 서비스의 KV 캐시를 관리한다. PagedAttention 덕분에 KV 캐시를 가상 메모리의 페이지처럼 고정 크기 KV 블록으로 구성한다. 요청의 KV 캐시는 논리 KV 블록의 연속으로 표현되며, 새 토큰과 그 KV 캐시가 생성될 때마다 왼쪽에서 오른쪽으로 채워진다. 마지막 KV 블록의 채워지지 않은 위치는 이후 생성을 위해 예약된다. GPU 워커에서는 블록 엔진(block engine)이 GPU DRAM의 연속된 덩어리를 할당해 물리 KV 블록으로 나눈다(스와핑을 위해 CPU RAM에서도 같은 일을 한다. 4.5절 참조). KV 블록 매니저는 또한 블록 테이블(block table), 즉 각 요청의 논리 KV 블록과 물리 KV 블록 사이의 대응 관계를 관리한다. 블록 테이블의 각 항목은 논리 블록에 대응하는 물리 블록과 채워진 위치의 개수를 기록한다. 논리 KV 블록과 물리 KV 블록을 분리한 덕분에, vLLM은 모든 위치의 메모리를 미리 예약하지 않고도 KV 캐시 메모리를 동적으로 늘릴 수 있으며, 그림 2처럼 기존 시스템의 메모리 낭비 대부분이 사라진다.

### 4.3 Decoding with PagedAttention and vLLM

다음으로 그림 6과 같은 예를 따라가며, 입력 시퀀스 하나를 디코딩하는 동안 vLLM이 PagedAttention을 어떻게 실행하고 메모리를 어떻게 관리하는지 보인다.

① OS의 가상 메모리처럼 vLLM은 처음부터 생성될 수 있는 최대 시퀀스 길이만큼의 메모리를 예약하지 않는다. 대신 프롬프트 계산 중에 생성되는 KV 캐시를 담는 데 꼭 필요한 KV 블록만 예약한다. 이 예에서 프롬프트는 7개 토큰이므로, vLLM은 처음 두 개의 논리 KV 블록(0, 1)을 두 개의 물리 KV 블록(각각 7, 1)에 대응시킨다. 프리필(prefill) 단계에서 vLLM은 일반적인 셀프 어텐션 알고리즘(예: [13])으로 프롬프트와 첫 번째 출력 토큰의 KV 캐시를 생성한다. 그다음 처음 4개 토큰의 KV 캐시를 논리 블록 0에, 이어지는 3개 토큰의 KV 캐시를 논리 블록 1에 저장한다. 남은 슬롯 하나는 뒤따르는 자기회귀 생성 단계를 위해 예약해 둔다.

② 첫 번째 자기회귀 디코딩 단계에서 vLLM은 물리 블록 7과 1에 대해 PagedAttention 알고리즘으로 새 토큰을 생성한다. 마지막 논리 블록에 빈 슬롯이 하나 남아 있으므로 새로 생성된 KV 캐시는 거기에 저장하고, 블록 테이블의 #filled 기록을 갱신한다.

③ 두 번째 디코딩 단계에서는 마지막 논리 블록이 가득 찼으므로, vLLM은 새로 생성된 KV 캐시를 새 논리 블록에 저장한다. 이를 위해 새 물리 블록(물리 블록 3)을 할당하고 이 대응 관계를 블록 테이블에 저장한다.

전체적으로 보면, 매 디코딩 반복마다 vLLM은 먼저 배칭할 후보 시퀀스 집합을 고르고(4.5절에서 자세히 설명), 새로 필요해진 논리 블록을 위한 물리 블록을 할당한다. 그런 다음 현재 반복의 모든 입력 토큰(프롬프트 단계 요청의 모든 토큰과 생성 단계 요청의 최신 토큰)을 하나의 시퀀스로 이어 붙여 LLM에 입력한다. LLM이 계산하는 동안 vLLM은 PagedAttention 커널로 논리 KV 블록 형태로 저장된 이전 KV 캐시에 접근하고, 새로 생성된 KV 캐시를 물리 KV 블록에 저장한다. KV 블록 하나에 여러 토큰을 저장하면(블록 크기 > 1) PagedAttention 커널이 더 많은 위치의 KV 캐시를 병렬로 처리할 수 있어 하드웨어 활용도가 올라가고 지연 시간이 줄어든다. 다만 블록 크기가 커지면 메모리 단편화도 늘어난다. 블록 크기의 영향은 7.2절에서 살펴본다.

### 4.4 Application to Other Decoding Scenarios

4.3절에서는 하나의 사용자 프롬프트를 입력으로 받아 하나의 출력 시퀀스를 생성하는 그리디(greedy) 디코딩이나 샘플링 같은 기본 디코딩 알고리즘을 PagedAttention과 vLLM이 어떻게 다루는지 보였다. 성공한 많은 LLM 애플리케이션 [18, 34]에서 LLM 서비스는 더 복잡한 디코딩 시나리오를 제공해야 하는데, 이런 시나리오는 접근 패턴이 복잡하고 메모리를 공유할 기회가 더 많다. 이 절에서는 vLLM이 이런 시나리오에도 범용적으로 적용될 수 있음을 보인다.

**Parallel sampling.** LLM 기반 프로그램 어시스턴트 [6, 18]에서는 LLM이 하나의 입력 프롬프트에 대해 여러 샘플 출력을 생성하고, 사용자는 여러 후보 중 마음에 드는 출력을 고를 수 있다. 지금까지는 요청 하나가 시퀀스 하나를 생성한다고 암묵적으로 가정했다. 이 논문의 나머지 부분에서는 요청 하나가 여러 시퀀스를 생성하는 더 일반적인 경우를 가정한다. 병렬 샘플링에서는 한 요청이 같은 입력 프롬프트를 공유하는 여러 샘플을 포함하므로 프롬프트의 KV 캐시도 공유할 수 있다. PagedAttention과 페이지 방식 메모리 관리 덕분에 vLLM은 이 공유를 쉽게 구현해 메모리를 절약한다.

그림 8은 두 출력을 병렬로 디코딩하는 예이다. 두 출력이 같은 프롬프트를 공유하므로, 프롬프트 단계에서 프롬프트 상태를 한 부분만 저장할 공간을 예약한다. 두 시퀀스의 프롬프트에 해당하는 논리 블록은 같은 물리 블록에 대응된다. 즉 두 시퀀스의 논리 블록 0과 1은 각각 물리 블록 7과 1에 대응된다. 하나의 물리 블록이 여러 논리 블록에 대응될 수 있으므로 물리 블록마다 참조 횟수(reference count)를 둔다. 이 경우 물리 블록 7과 1의 참조 횟수는 모두 2이다. 생성 단계에서는 두 출력이 서로 다른 출력 토큰을 샘플링하므로 KV 캐시를 따로 저장해야 한다. vLLM은 여러 시퀀스가 수정해야 하는 물리 블록에 대해 블록 단위의 쓰기 시 복사(copy-on-write) 메커니즘을 구현한다. 이는 OS 가상 메모리의 쓰기 시 복사 기법(예: 프로세스를 포크(fork)할 때)과 비슷하다. 구체적으로 그림 8에서 샘플 A1이 마지막 논리 블록(논리 블록 1)에 쓰려 할 때, vLLM은 대응하는 물리 블록(물리 블록 1)의 참조 횟수가 1보다 크다는 것을 확인하고 새 물리 블록(물리 블록 3)을 할당한 뒤 블록 엔진에 물리 블록 1의 내용을 복사하라고 지시하고 참조 횟수를 1로 줄인다. 다음에 샘플 A2가 물리 블록 1에 쓸 때는 참조 횟수가 이미 1로 줄어 있으므로, A2는 새로 생성한 KV 캐시를 물리 블록 1에 바로 쓴다.

> *(그림 8: 원문 PDF 7쪽 참조. 병렬 샘플링 예. 샘플 A1("... our fathers")과 A2("... our mothers")가 물리 블록 7, 1을 공유하다가 쓰기 시 복사로 블록 3이 새로 할당되며, 참조 횟수가 2 → 1로 줄어든다.)*

요약하면 vLLM은 마지막 논리 블록(쓰기 시 복사 메커니즘으로 관리)을 제외하면, 프롬프트의 KV 캐시를 저장하는 공간의 대부분을 여러 출력 샘플이 공유할 수 있게 한다. 물리 블록을 여러 샘플이 공유하면 특히 입력 프롬프트가 길 때 메모리 사용량을 크게 줄일 수 있다.

**Beam search.** 기계 번역 [59] 같은 LLM 작업에서 사용자는 LLM이 출력하는 가장 적절한 번역 상위 {{< katex >}}k{{< /katex >}}개를 기대한다. 빔 서치 [49]는 표본 공간 전체를 순회하는 계산 복잡도를 줄여 주므로, LLM에서 가장 확률이 높은 출력 시퀀스를 디코딩하는 데 널리 쓰인다. 이 알고리즘은 빔 폭(beam width) 파라미터 {{< katex >}}k{{< /katex >}}에 의존하며, {{< katex >}}k{{< /katex >}}는 매 단계에서 유지하는 상위 후보의 수를 정한다. 디코딩 중에 빔 서치는 빔 안의 각 후보 시퀀스를 가능한 모든 토큰으로 확장하고, LLM으로 각각의 확률을 계산한 다음, {{< katex >}}k \cdot |V|{{< /katex >}}개의 후보 중 확률이 가장 높은 상위 {{< katex >}}k{{< /katex >}}개 시퀀스를 남긴다. 여기서 {{< katex >}}|V|{{< /katex >}}는 어휘 크기이다.

병렬 디코딩과 달리 빔 서치는 처음의 프롬프트 블록뿐 아니라 서로 다른 후보 사이의 다른 블록도 공유할 수 있게 하며, 공유 패턴은 디코딩이 진행됨에 따라 동적으로 변한다. 이는 OS에서 복합 포크(compound fork)로 만들어지는 프로세스 트리와 비슷하다. 그림 9는 {{< katex >}}k = 4{{< /katex >}}인 빔 서치 예에서 vLLM이 KV 블록을 어떻게 관리하는지 보여 준다. 점선으로 표시된 반복 이전에는 각 후보 시퀀스가 가득 찬 논리 블록 4개를 사용했다. 모든 빔 후보는 첫 번째 블록 0(즉 프롬프트)을 공유한다. 후보 3은 두 번째 블록부터 다른 후보들과 갈라진다. 후보 0–2는 처음 세 블록을 공유하다가 네 번째 블록에서 갈라진다. 이후 반복에서는 상위 4개의 확률 높은 후보가 모두 후보 1과 2에서 나온다. 원래 후보 0과 3은 더 이상 상위 후보에 들지 못하므로 그 논리 블록을 해제하고 해당 물리 블록의 참조 횟수를 줄인다. vLLM은 참조 횟수가 0이 된 모든 물리 블록(블록 2, 4, 5, 8)을 해제한다. 그다음 새 후보의 새 KV 캐시를 저장할 새 물리 블록(블록 9–12)을 할당한다. 이제 모든 후보가 블록 0, 1, 3을 공유하고, 후보 0과 1은 블록 6을, 후보 2와 3은 블록 7을 추가로 공유한다.

> *(그림 9: 원문 PDF 7쪽 참조. 빔 폭 4인 빔 서치에서 후보 0–3이 물리 블록 0–12를 공유하는 방식과, 점선 이후 해제되는 블록 및 새로 할당되는 블록 9–12를 나타낸 도식.)*

기존 LLM 서빙 시스템은 빔 후보들 사이에서 KV 캐시를 자주 메모리 복사해야 한다. 예를 들어 그림 9의 경우 점선 이후 후보 3은 생성을 이어 가려면 후보 2의 KV 캐시 중 큰 부분을 복사해야 한다. vLLM의 물리 블록 공유는 이런 빈번한 메모리 복사 오버헤드를 크게 줄인다. vLLM에서는 서로 다른 빔 후보의 대부분의 블록을 공유할 수 있다. 쓰기 시 복사 메커니즘은 병렬 디코딩에서처럼 새로 생성된 토큰이 기존의 공유 블록 안에 들어갈 때에만 적용된다. 이때는 블록 하나의 데이터만 복사하면 된다.

**Shared prefix.** 보통 LLM 사용자는 작업에 대한 (긴) 설명을 제공하는데, 여기에는 지시문과 입출력 예시가 들어 있으며 시스템 프롬프트(system prompt) [36]라고도 한다. 이 설명은 실제 작업 입력과 이어 붙여 요청의 프롬프트가 된다. LLM은 전체 프롬프트를 바탕으로 출력을 생성한다. 그림 10이 그 예이다. 더욱이 공유되는 접두사(prefix)는 프롬프트 엔지니어링으로 더 튜닝해 다운스트림 작업의 정확도를 높일 수 있다 [26, 27]. 이런 유형의 애플리케이션에서는 많은 사용자 프롬프트가 접두사를 공유하므로, LLM 서비스 제공자는 접두사의 KV 캐시를 미리 저장해 두어 접두사에 쓰이는 중복 계산을 줄일 수 있다. vLLM에서는 LLM 서비스 제공자가 미리 정의한 공유 접두사 집합에 물리 블록 집합을 예약해 두는 식으로 이를 간편하게 구현할 수 있으며, 이는 OS가 프로세스 사이에서 공유 라이브러리를 다루는 방식과 같다. 공유 접두사를 가진 사용자 입력 프롬프트는 자신의 논리 블록을 캐시된 물리 블록에 대응시키기만 하면 된다(마지막 블록은 쓰기 시 복사로 표시). 프롬프트 단계의 계산은 사용자의 작업 입력에 대해서만 수행하면 된다.

> *(그림 10: 원문 PDF 8쪽 참조. 기계 번역 예. "Translate English to French:"와 세 개의 예시(sea otter → loutre de mer, peppermint → menthe poivrée, plush girafe → girafe en peluche)가 공유 접두사이며, 시퀀스 A는 "cheese" → "fromage", 시퀀스 B는 "I love you" → "Je t'amie"를 작업 입력과 출력으로 가진다.)*

**Mixed decoding methods.** 앞에서 논의한 디코딩 방법들은 메모리 공유와 접근 패턴이 서로 다르다. 그럼에도 vLLM은 서로 다른 디코딩 선호를 가진 요청을 동시에 처리할 수 있게 해 주는데, 기존 시스템은 이를 효율적으로 하지 못한다. vLLM이 논리 블록을 물리 블록으로 변환하는 공통 대응 계층(mapping layer)을 통해 서로 다른 시퀀스 사이의 복잡한 메모리 공유를 가려 주기 때문이다. LLM과 그 실행 커널은 시퀀스마다 물리 블록 ID 리스트만 볼 뿐, 시퀀스 사이의 공유 패턴을 다룰 필요가 없다. 기존 시스템과 비교해 이 방식은 샘플링 요구가 서로 다른 요청들을 배칭할 기회를 넓혀 시스템의 전체 처리량을 높인다.

### 4.5 Scheduling and Preemption

요청 트래픽이 시스템 용량을 넘으면 vLLM은 일부 요청에 우선순위를 주어야 한다. vLLM은 모든 요청에 선입선출(first-come-first-serve, FCFS) 스케줄링 정책을 쓰며, 이는 공정성을 보장하고 기아(starvation)를 막는다. vLLM이 요청을 선점(preempt)해야 할 때는 가장 먼저 도착한 요청부터 서비스하고 가장 나중에 도착한 요청부터 선점한다.

LLM 서비스는 고유한 어려움에 직면한다. LLM의 입력 프롬프트는 길이가 크게 다를 수 있고, 그에 따른 출력 길이는 입력 프롬프트와 모델 모두에 달려 있어 미리 알 수 없다. 요청과 그 출력이 늘어나면 vLLM은 새로 생성된 KV 캐시를 저장할 GPU의 물리 블록이 바닥날 수 있다. 이때 vLLM이 답해야 할 고전적인 질문이 두 가지 있다. (1) 어떤 블록을 내보낼(evict) 것인가? (2) 내보낸 블록이 다시 필요하면 어떻게 복구할 것인가? 일반적으로 축출(eviction) 정책은 어떤 블록이 미래에 가장 늦게 접근될지를 휴리스틱으로 예측해 그 블록을 내보낸다. 여기서는 한 시퀀스의 모든 블록이 함께 접근된다는 것을 알고 있으므로, 전부 아니면 전무(all-or-nothing)의 축출 정책을 구현한다. 즉 한 시퀀스의 블록을 모두 내보내거나 하나도 내보내지 않는다. 더 나아가 한 요청 안의 여러 시퀀스(예: 한 빔 서치 요청의 빔 후보들)는 시퀀스 그룹(sequence group)으로 묶어 함께 스케줄링(gang-scheduling)한다. 이 시퀀스들 사이에 메모리 공유가 있을 수 있으므로, 한 시퀀스 그룹 안의 시퀀스들은 항상 함께 선점되거나 다시 스케줄링된다. 두 번째 질문인 내보낸 블록의 복구에는 두 가지 기법을 고려한다.

**Swapping.** 대부분의 가상 메모리 구현에서 쓰는 고전적인 기법으로, 내보낸 페이지를 디스크의 스왑 공간에 복사한다. 여기서는 내보낸 블록을 CPU 메모리로 복사한다. 그림 4처럼 vLLM에는 GPU 블록 할당자 외에, CPU RAM으로 스왑된 물리 블록을 관리하는 CPU 블록 할당자가 있다. vLLM이 새 토큰을 위한 빈 물리 블록을 다 쓰면, 내보낼 시퀀스 집합을 골라 그 KV 캐시를 CPU로 옮긴다. 시퀀스를 선점하고 그 블록을 내보낸 뒤에는, 선점된 모든 시퀀스가 완료될 때까지 vLLM이 새 요청을 받지 않는다. 요청이 완료되면 그 블록은 메모리에서 해제되고, 선점된 시퀀스의 블록은 다시 불러와 그 시퀀스의 처리를 이어 간다. 이 설계에서는 CPU RAM으로 스왑되는 블록의 수가 GPU RAM의 전체 물리 블록 수를 넘지 않으므로, CPU RAM의 스왑 공간은 KV 캐시에 할당된 GPU 메모리에 의해 상한이 정해진다.

**Recomputation.** 이 경우 선점된 시퀀스가 다시 스케줄링될 때 KV 캐시를 그냥 다시 계산한다. 디코딩 중 생성된 토큰을 원래 사용자 프롬프트와 이어 붙여 새 프롬프트로 쓸 수 있고 모든 위치의 KV 캐시를 프롬프트 단계 한 번의 반복으로 생성할 수 있으므로, 재계산 지연 시간은 원래의 지연 시간보다 크게 낮을 수 있다.

스와핑과 재계산의 성능은 CPU RAM과 GPU 메모리 사이의 대역폭, 그리고 GPU의 연산 능력에 달려 있다. 스와핑과 재계산의 속도는 7.3절에서 살펴본다.

### 4.6 Distributed Execution

많은 LLM은 파라미터 크기가 단일 GPU의 용량을 넘는다 [5, 9]. 따라서 이를 분산된 GPU에 나누어 모델 병렬(model parallel) 방식 [28, 63]으로 실행해야 하며, 이를 위해서는 분산 메모리를 다룰 수 있는 메모리 매니저가 필요하다. vLLM은 Transformer에 널리 쓰이는 Megatron-LM 스타일의 텐서 모델 병렬(tensor model parallelism) 전략 [47]을 지원해 분산 환경에서도 효과적으로 동작한다. 이 전략은 SPMD(Single Program Multiple Data) 실행 스케줄을 따른다. 선형 층을 나누어 블록 단위 행렬 곱셈을 수행하고, GPU들은 올-리듀스(all-reduce) 연산으로 중간 결과를 계속 동기화한다. 구체적으로 어텐션 연산자는 어텐션 헤드 차원으로 분할되며, 각 SPMD 프로세스는 멀티헤드 어텐션에서 헤드의 일부를 맡는다.

모델 병렬 실행에서도 각 모델 샤드(shard)가 여전히 같은 입력 토큰 집합을 처리하므로 같은 위치들의 KV 캐시가 필요하다는 점을 관찰했다. 그래서 vLLM은 그림 4처럼 중앙 스케줄러 안에 하나의 KV 캐시 매니저를 둔다. 서로 다른 GPU 워커는 이 매니저와 논리 블록→물리 블록 대응을 함께 사용한다. 이 공통 대응 덕분에 GPU 워커는 각 입력 요청에 대해 스케줄러가 제공한 물리 블록으로 모델을 실행할 수 있다. 각 GPU 워커는 같은 물리 블록 ID를 갖지만, 워커는 자신이 맡은 어텐션 헤드에 해당하는 KV 캐시 일부만 저장한다.

매 단계에서 스케줄러는 먼저 배치 안의 각 요청에 대한 입력 토큰 ID와 각 요청의 블록 테이블을 담은 메시지를 준비한다. 다음으로 스케줄러는 이 제어 메시지를 GPU 워커들에 브로드캐스트한다. 그러면 GPU 워커들은 입력 토큰 ID로 모델 실행을 시작한다. 어텐션 층에서 GPU 워커는 제어 메시지의 블록 테이블에 따라 KV 캐시를 읽는다. 실행 중에 GPU 워커는 [47]에서처럼 스케줄러의 조율 없이 올-리듀스 통신 프리미티브로 중간 결과를 동기화한다. 마지막으로 GPU 워커는 이번 반복에서 샘플링한 토큰을 스케줄러에 돌려보낸다. 요약하면 GPU 워커는 메모리 관리에 대해 동기화할 필요가 없고, 각 디코딩 반복의 시작 시점에 단계 입력과 함께 모든 메모리 관리 정보를 받기만 하면 된다.

## 5 Implementation

vLLM은 FastAPI [15] 프런트엔드와 GPU 기반 추론 엔진으로 이루어진 엔드투엔드 서빙 시스템이다. 프런트엔드는 OpenAI API [34] 인터페이스를 확장해, 사용자가 최대 시퀀스 길이나 빔 폭 {{< katex >}}k{{< /katex >}} 같은 샘플링 파라미터를 요청마다 지정할 수 있게 한다. vLLM 엔진은 Python 8.5K줄과 C++/CUDA 2K줄로 작성되었다. 스케줄러와 블록 매니저를 포함한 제어 관련 구성 요소는 Python으로 개발하고, PagedAttention 같은 핵심 연산에는 맞춤형 CUDA 커널을 개발했다. 모델 실행기(model executor)로는 GPT [5], OPT [62], LLaMA [52] 같은 널리 쓰이는 LLM을 PyTorch [39]와 Transformers [58]로 구현했다. 분산 GPU 워커 사이의 텐서 통신에는 NCCL [32]을 쓴다.

### 5.1 Kernel-level Optimization

PagedAttention은 기존 시스템이 효율적으로 지원하지 않는 메모리 접근 패턴을 만들어 내므로, 이를 최적화하기 위해 여러 GPU 커널을 개발했다. (1) 리셰이프와 블록 쓰기의 융합(Fused reshape and block write). 모든 Transformer 층에서 새 KV 캐시는 블록으로 나뉘고, 블록 읽기에 최적화된 메모리 레이아웃으로 재구성(reshape)된 뒤, 블록 테이블이 지정한 위치에 저장된다. 커널 실행(launch) 오버헤드를 줄이기 위해 이들을 하나의 커널로 융합했다. (2) 블록 읽기와 어텐션의 융합(Fusing block read and attention). FasterTransformer [31]의 어텐션 커널을 블록 테이블에 따라 KV 캐시를 읽고 어텐션 연산을 즉석에서(on the fly) 수행하도록 수정했다. 메모리 접근이 병합(coalesced)되도록 블록 하나를 읽는 데 GPU 워프(warp) 하나를 할당한다. 또한 요청 배치 안에서 가변적인 시퀀스 길이를 지원하도록 했다. (3) 블록 복사의 융합(Fused block copy). 쓰기 시 복사 메커니즘이 일으키는 블록 복사 연산은 불연속적인 블록을 대상으로 할 수 있다. 이때 `cudaMemcpyAsync` API를 쓰면 작은 데이터 이동이 수없이 호출될 수 있다. 이 오버헤드를 줄이기 위해, 서로 다른 블록에 대한 복사 연산을 하나의 커널 실행으로 묶어 처리하는 커널을 구현했다.

### 5.2 Supporting Various Decoding Algorithms

vLLM은 fork, append, free라는 세 가지 핵심 메서드로 다양한 디코딩 알고리즘을 구현한다. fork 메서드는 기존 시퀀스로부터 새 시퀀스를 만든다. append 메서드는 시퀀스에 새 토큰을 덧붙인다. 마지막으로 free 메서드는 시퀀스를 삭제한다. 예를 들어 병렬 샘플링에서 vLLM은 fork 메서드로 하나의 입력 시퀀스에서 여러 출력 시퀀스를 만든다. 그다음 매 반복마다 append로 이 시퀀스들에 새 토큰을 추가하고, 종료 조건을 만족한 시퀀스는 free로 삭제한다. 빔 서치와 접두사 공유에도 vLLM은 같은 전략을 적용한다. 앞으로 나올 디코딩 알고리즘도 이 메서드들을 조합해 지원할 수 있을 것으로 기대한다.

## 6 Evaluation

이 절에서는 다양한 워크로드에서 vLLM의 성능을 평가한다.

### 6.1 Experimental Setup

**Model and server configurations.** 평가에는 130억(13B), 660억(66B), 1750억(175B) 파라미터의 OPT [62] 모델과 130억 파라미터의 LLaMA [52]를 사용한다. LLM 리더보드 [38]에서 보듯 13B와 66B는 LLM에서 널리 쓰이는 크기이고, 175B는 유명한 GPT-3 [5] 모델의 크기이다. 모든 실험에서 Google Cloud Platform의 NVIDIA A100 GPU를 쓰는 A2 인스턴스를 사용한다. 자세한 모델 크기와 서버 구성은 표 1에 나와 있다.

**Workloads.** ShareGPT [51]와 Alpaca [50] 데이터셋을 바탕으로 워크로드를 합성한다. 두 데이터셋에는 실제 LLM 서비스의 입력과 출력 텍스트가 들어 있다. ShareGPT 데이터셋은 사용자가 공유한 ChatGPT [35] 대화 모음이다. Alpaca 데이터셋은 self-instruct [57]를 사용해 GPT-3.5로 생성한 지시문(instruction) 데이터셋이다. 데이터셋을 토큰화하고 그 입력·출력 길이를 사용해 클라이언트 요청을 합성한다. 그림 11처럼 ShareGPT 데이터셋은 Alpaca 데이터셋에 비해 평균 입력 프롬프트가 8.4배, 출력이 5.8배 길고 분산도 더 크다. 이 데이터셋에는 타임스탬프가 없으므로, 요청률(request rate)을 바꿔 가며 푸아송(Poisson) 분포로 요청 도착 시각을 생성한다.

**Baseline 1: FasterTransformer.** FasterTransformer [31]는 지연 시간에 맞춰 크게 최적화된 분산 추론 엔진이다. FasterTransformer에는 자체 스케줄러가 없으므로, Triton [30] 같은 기존 서빙 시스템과 비슷한 동적 배칭(dynamic batching) 메커니즘을 갖춘 맞춤형 스케줄러를 구현했다. 구체적으로 실험마다 GPU 메모리 용량에 맞춰 최대 배치 크기 {{< katex >}}B{{< /katex >}}를 가능한 한 크게 설정한다. 스케줄러는 가장 먼저 도착한 요청을 최대 {{< katex >}}B{{< /katex >}}개까지 가져와 그 배치를 FasterTransformer에 보내 처리한다.

**Baseline 2: Orca.** Orca [60]는 처리량에 맞춰 최적화된, 당시 최고 수준의 LLM 서빙 시스템이다. Orca는 공개되어 있지 않아 직접 사용할 수 없으므로 자체 버전의 Orca를 구현했다. Orca가 KV 캐시를 저장할 메모리 주소를 정하는 데 버디 할당 알고리즘을 쓴다고 가정한다. 요청 출력용 공간을 얼마나 과하게 예약하는지에 따라 Orca를 세 가지 버전으로 구현했다.

- **Orca (Oracle).** 시스템이 요청에서 실제로 생성될 출력의 길이를 안다고 가정한다. 이는 Orca의 성능 상한을 보여 주며, 실제로는 달성할 수 없다.
- **Orca (Pow2).** 시스템이 출력용 공간을 최대 2배까지 과하게 예약한다고 가정한다. 예를 들어 실제 출력 길이가 25이면 출력용으로 32개 위치를 예약한다.
- **Orca (Max).** 시스템이 항상 모델의 최대 시퀀스 길이, 즉 2048 토큰까지 공간을 예약한다고 가정한다.

**Key metrics.** 서빙 처리량에 초점을 맞춘다. 구체적으로 요청률이 서로 다른 워크로드를 사용해, Orca [60]에서처럼 정규화 지연 시간(normalized latency), 즉 각 요청의 엔드투엔드 지연 시간을 그 요청의 출력 길이로 나눈 값의 평균을 측정한다. 처리량이 높은 서빙 시스템은 높은 요청률에서도 정규화 지연 시간을 낮게 유지해야 한다. 대부분의 실험에서는 1시간짜리 트레이스로 시스템을 평가한다. 예외로 OPT-175B 모델은 비용 제한 때문에 15분짜리 트레이스를 쓴다.

### 6.2 Basic Sampling

세 모델과 두 데이터셋에서 기본 샘플링(요청당 샘플 하나)으로 vLLM의 성능을 평가한다. 그림 12의 첫 번째 행은 ShareGPT 데이터셋의 결과이다. 곡선을 보면 요청률이 올라감에 따라 지연 시간은 처음에는 완만하게 늘다가 갑자기 폭발한다. 이는 요청률이 서빙 시스템의 용량을 넘으면 대기열 길이가 끝없이 길어지고 요청의 지연 시간도 그에 따라 끝없이 늘어나기 때문이다.

ShareGPT 데이터셋에서 vLLM은 비슷한 지연 시간을 유지하면서 Orca (Oracle)보다 1.7–2.7배, Orca (Max)보다 2.7–8배 높은 요청률을 견딜 수 있다. 이는 vLLM의 PagedAttention이 메모리 사용량을 효율적으로 관리해 Orca보다 더 많은 요청을 배칭할 수 있기 때문이다. 예를 들어 그림 13a에서 보듯 OPT-13B에서 vLLM은 Orca (Oracle)보다 2.2배, Orca (Max)보다 4.3배 많은 요청을 동시에 처리한다. FasterTransformer와 비교하면 vLLM은 최대 22배 높은 요청률을 견딜 수 있다. FasterTransformer는 세밀한 스케줄링 메커니즘을 쓰지 않고 Orca (Max)처럼 메모리를 비효율적으로 관리하기 때문이다.

그림 12의 두 번째 행과 그림 13b는 Alpaca 데이터셋의 결과를 보여 주며, ShareGPT 데이터셋과 비슷한 경향을 따른다. 한 가지 예외는 그림 12(f)로, Orca (Oracle) 및 Orca (Pow2)에 대한 vLLM의 우위가 덜 두드러진다. OPT-175B의 모델 및 서버 구성(표 1)은 KV 캐시를 저장할 GPU 메모리 공간이 크고, Alpaca 데이터셋은 시퀀스가 짧기 때문이다. 이 설정에서는 Orca (Oracle)와 Orca (Pow2)도 메모리 관리가 비효율적임에도 많은 요청을 배칭할 수 있다. 그 결과 시스템의 성능은 메모리 병목이 아니라 연산 병목(compute-bound)이 된다.

### 6.3 Parallel Sampling and Beam Search

PagedAttention의 메모리 공유가 얼마나 효과적인지를 두 가지 널리 쓰이는 샘플링 방법, 병렬 샘플링과 빔 서치로 평가한다. 병렬 샘플링에서는 요청 안의 모든 병렬 시퀀스가 프롬프트의 KV 캐시를 공유할 수 있다. 그림 14의 첫 번째 행에서 보듯 샘플링할 시퀀스 수가 많을수록 Orca 기준선에 대한 vLLM의 개선 폭이 커진다. 마찬가지로 그림 14의 두 번째 행은 빔 폭을 달리한 빔 서치의 결과를 보여 준다. 빔 서치는 공유가 더 많이 일어나므로 vLLM의 성능 이득이 더 크다. OPT-13B와 Alpaca 데이터셋에서 Orca (Oracle) 대비 vLLM의 개선 폭은 기본 샘플링의 1.3배에서 빔 폭 6인 빔 서치의 2.3배로 커진다.

그림 15는 메모리 절감량을 나타낸다. 이는 공유로 절약한 블록 수를 공유하지 않았을 때의 전체 블록 수로 나누어 계산한 값이다. 병렬 샘플링에서는 6.1%–9.8%, 빔 서치에서는 37.6%–55.2%의 메모리 절감을 확인했다. 같은 실험을 ShareGPT 데이터셋에서 수행했을 때는 병렬 샘플링에서 16.2%–30.5%, 빔 서치에서 44.3%–66.3%의 메모리 절감을 보았다.

### 6.4 Shared prefix

그림 10에 나온 것처럼 서로 다른 입력 프롬프트가 접두사를 공유하는 경우에 vLLM이 얼마나 효과적인지 살펴본다. 모델은 다국어를 지원하는 LLaMA-13B [52]를 사용한다. 워크로드로는 WMT16 [4] 영어→독일어 번역 데이터셋을 사용하고, 지시문과 몇 개의 번역 예시를 포함하는 두 가지 접두사를 합성한다. 첫 번째 접두사는 예시 하나(원샷, one-shot)를, 다른 접두사는 예시 5개(퓨샷, few-shot)를 포함한다. 그림 16(a)에서 보듯 원샷 접두사를 공유할 때 vLLM은 Orca (Oracle)보다 1.67배 높은 처리량을 낸다. 더 많은 예시를 공유하면(그림 16(b)) vLLM은 Orca (Oracle)보다 3.58배 높은 처리량을 낸다.

### 6.5 Chatbot

챗봇 [8, 19, 35]은 LLM의 가장 중요한 응용 중 하나이다. 챗봇을 구현하기 위해, 대화 기록과 마지막 사용자 질의를 이어 붙여 프롬프트로 만들고 모델이 응답을 생성하게 한다. 대화 기록과 사용자 질의는 ShareGPT 데이터셋으로 합성한다. OPT-13B 모델의 문맥 길이(context length)가 제한적이므로 프롬프트를 마지막 1024 토큰으로 자르고 모델이 최대 1024 토큰을 생성하게 한다. 대화 라운드 사이에는 KV 캐시를 저장하지 않는다. 그렇게 하면 라운드 사이에 다른 요청이 쓸 공간을 차지하게 되기 때문이다.

그림 17은 vLLM이 세 가지 Orca 기준선보다 2배 높은 요청률을 견딜 수 있음을 보여 준다. ShareGPT 데이터셋에는 긴 대화가 많아서 대부분의 요청에서 입력 프롬프트가 1024 토큰이다. 버디 할당 알고리즘 때문에 Orca 기준선들은 출력 길이를 어떻게 예측하든 요청 출력에 1024 토큰 분량의 공간을 예약한다. 이 때문에 세 Orca 기준선은 비슷하게 동작한다. 반면 vLLM은 PagedAttention이 메모리 단편화와 예약 문제를 해결하므로 긴 프롬프트를 효과적으로 처리할 수 있다.

## 7 Ablation Studies

이 절에서는 vLLM의 여러 측면을 연구하고, 우리가 내린 설계 선택을 절제(ablation) 실험(구성 요소를 바꿔 가며 효과를 확인하는 실험)으로 평가한다.

### 7.1 Kernel Microbenchmark

PagedAttention의 동적 블록 대응은 저장된 KV 캐시와 관련된 GPU 연산, 즉 블록 읽기/쓰기와 어텐션의 성능에 영향을 준다. 기존 시스템과 비교하면 vLLM의 GPU 커널(5절)에는 블록 테이블 접근, 추가 분기 실행, 가변 시퀀스 길이 처리라는 추가 오버헤드가 있다. 그림 18a에서 보듯 이 때문에 고도로 최적화된 FasterTransformer 구현에 비해 어텐션 커널 지연 시간이 20–26% 더 높다. 이 오버헤드는 모델의 Linear 같은 다른 연산자가 아니라 어텐션 연산자에만 영향을 주므로 작다고 본다. 이런 오버헤드가 있음에도 PagedAttention 덕분에 vLLM은 엔드투엔드 성능에서 FasterTransformer를 크게 앞선다(6절).

### 7.2 Impact of Block Size

블록 크기의 선택은 vLLM의 성능에 큰 영향을 줄 수 있다. 블록 크기가 너무 작으면 vLLM이 KV 캐시를 읽고 처리하는 데 GPU의 병렬성을 충분히 활용하지 못할 수 있다. 블록 크기가 너무 크면 내부 단편화가 늘고 공유할 확률이 줄어든다.

그림 18b에서는 고정된 요청률 아래에서 기본 샘플링으로 ShareGPT와 Alpaca 트레이스를 사용해 블록 크기에 따른 vLLM의 성능을 평가한다. ShareGPT 트레이스에서는 블록 크기가 16에서 128일 때 성능이 가장 좋다. Alpaca 트레이스에서는 블록 크기 16과 32가 좋은 성능을 내지만, 더 큰 블록 크기에서는 시퀀스가 블록 크기보다 짧아지기 때문에 성능이 크게 떨어진다. 실제로 대부분의 워크로드에서 블록 크기 16은 GPU를 효율적으로 활용할 만큼 크면서 심각한 내부 단편화를 피할 만큼 작다는 것을 확인했다. 따라서 vLLM은 기본 블록 크기를 16으로 설정한다.

### 7.3 Comparing Recomputation and Swapping

vLLM은 복구 메커니즘으로 재계산과 스와핑을 모두 지원한다. 두 방법 사이의 트레이드오프를 이해하기 위해, 그림 19와 같이 두 방법의 엔드투엔드 성능을 평가하고 그 오버헤드를 마이크로벤치마크로 측정했다. 결과를 보면 블록 크기가 작을 때 스와핑의 오버헤드가 과도하다. 블록 크기가 작으면 CPU와 GPU 사이에 작은 데이터 전송이 많이 일어나 유효 PCIe 대역폭이 제한되는 경우가 많기 때문이다. 반면 재계산은 KV 블록을 쓰지 않으므로 오버헤드가 블록 크기와 무관하게 일정하다. 따라서 블록 크기가 작을 때는 재계산이, 클 때는 스와핑이 더 효율적이다. 다만 재계산의 오버헤드는 스와핑 지연 시간의 20%를 넘지 않는다. 16에서 64 사이의 중간 크기 블록에서는 두 방법의 엔드투엔드 성능이 비슷하다.

## 8 Discussion

**Applying the virtual memory and paging technique to other GPU workloads.** 가상 메모리와 페이징의 아이디어가 LLM 서빙의 KV 캐시 관리에 효과적인 것은, 이 워크로드가 동적 메모리 할당을 필요로 하고(출력 길이를 미리 알 수 없으므로) 성능이 GPU 메모리 용량에 의해 제한되기 때문이다. 그러나 이것이 모든 GPU 워크로드에 일반적으로 성립하지는 않는다. 예를 들어 DNN 학습에서는 텐서 모양이 대체로 고정되어 있으므로 메모리 할당을 미리 최적화할 수 있다. 또 다른 예로 LLM이 아닌 DNN을 서빙할 때는 성능이 주로 연산 병목이므로, 메모리 효율이 좋아져도 성능 향상으로 이어지지 않을 수 있다. 이런 경우 vLLM의 기법을 도입하면 메모리 간접 참조(indirection)와 비연속 블록 메모리의 추가 오버헤드 때문에 오히려 성능이 떨어질 수 있다. 그렇지만 LLM 서빙과 비슷한 성질을 가진 다른 워크로드에 vLLM의 기법이 적용되는 모습을 보게 된다면 반가울 것이다.

**LLM-specific optimizations in applying virtual memory and paging.** vLLM은 애플리케이션 고유의 의미(semantics)를 활용해 가상 메모리와 페이징의 아이디어를 재해석하고 보강한다. 한 예는 vLLM의 전부 아니면 전무(all-or-nothing) 스왑 아웃 정책으로, 요청을 처리하려면 대응하는 모든 토큰 상태가 GPU 메모리에 저장되어 있어야 한다는 사실을 활용한다. 또 다른 예는 내보낸 블록을 복구하는 재계산 방법으로, OS에서는 쓸 수 없는 방식이다. 이 밖에도 vLLM은 메모리 접근 연산용 GPU 커널을 어텐션 같은 다른 연산의 커널과 융합해, 페이징의 메모리 간접 참조 오버헤드를 줄인다.

## 9 Related Work

**General model serving systems.** 모델 서빙은 최근 몇 년간 활발한 연구 분야였으며, 딥러닝 모델 배포의 여러 측면을 다루는 수많은 시스템이 제안되었다. Clipper [11], TensorFlow Serving [33], Nexus [45], InferLine [10], Clockwork [20]는 초기의 범용 모델 서빙 시스템이다. 이들은 단일 또는 다수 모델을 서빙하기 위한 배칭, 캐싱, 배치(placement), 스케줄링을 연구한다. 더 최근에는 DVABatch [12]가 다중 진입·다중 종료(multi-entry multi-exit) 배칭을 도입했다. REEF [21]와 Shepherd [61]는 서빙을 위한 선점을 제안한다. AlpaServe [28]는 모델 병렬을 활용해 통계적 다중화(statistical multiplexing)를 한다. 그러나 이런 범용 시스템들은 LLM 추론의 자기회귀 특성과 토큰 상태를 고려하지 못해, 최적화 기회를 놓친다.

**Specialized serving systems for transformers.** Transformer 아키텍처가 중요하기 때문에 이를 위한 많은 특화 서빙 시스템이 개발되었다. 이 시스템들은 효율적인 서빙을 위해 GPU 커널 최적화 [1, 29, 31, 56], 고급 배칭 메커니즘 [14, 60], 모델 병렬 [1, 41, 60], 파라미터 공유 [64]를 활용한다. 이 중에서 Orca [60]가 본 연구의 접근과 가장 관련이 깊다.

**Comparison to Orca.** Orca [60]의 반복 단위 스케줄링과 vLLM의 PagedAttention은 서로 보완적인 기법이다. 두 시스템 모두 GPU 활용도를, 그리하여 LLM 서빙의 처리량을 높이는 것을 목표로 하지만, Orca는 요청을 스케줄링하고 끼워 넣어(interleaving) 더 많은 요청을 병렬로 처리하는 방식으로, vLLM은 메모리 활용도를 높여 더 많은 요청의 워킹 셋(working set)이 메모리에 들어가게 하는 방식으로 이를 달성한다. 메모리 단편화를 줄이고 공유를 가능하게 함으로써 vLLM은 배치에서 더 많은 요청을 병렬로 실행하고, Orca 대비 2–4배의 속도 향상을 얻는다. 실제로 Orca처럼 요청을 세밀하게 스케줄링하고 끼워 넣으면 메모리 관리가 더 어려워지므로, vLLM이 제안한 기법이 더욱 중요해진다.

**Memory optimizations.** 가속기의 연산 능력과 메모리 용량 사이의 격차가 벌어지면서 메모리는 학습과 추론 모두의 병목이 되었다. 스와핑 [23, 42, 55], 재계산 [7, 24], 그리고 둘의 결합 [40]은 학습의 최대(peak) 메모리를 줄이는 데 활용되어 왔다. 특히 FlexGen [46]은 제한된 GPU 메모리로 LLM 추론을 하기 위해 가중치와 토큰 상태를 스왑하는 방법을 연구하지만, 온라인 서빙 환경을 대상으로 하지는 않는다. OLLA [48]는 텐서의 수명과 위치를 최적화해 단편화를 줄이지만, 세밀한 블록 단위 관리나 온라인 서빙은 다루지 않는다. FlashAttention [13]은 타일링(tiling)과 커널 최적화를 적용해 어텐션 계산의 최대 메모리를 줄이고 I/O 비용을 줄인다. 본 논문은 온라인 서빙의 맥락에서 블록 단위 메모리 관리라는 새로운 아이디어를 도입한다.

## 10 Conclusion

본 논문은 어텐션의 키와 값을 비연속 페이지 메모리에 저장할 수 있게 하는 새 어텐션 알고리즘 PagedAttention을 제안하고, PagedAttention으로 가능해진 효율적 메모리 관리를 갖춘 고처리량 LLM 서빙 시스템 vLLM을 제시한다. 운영체제에서 착안해, 가상 메모리와 쓰기 시 복사 같은 검증된 기법을 KV 캐시 관리와 LLM 서빙의 다양한 디코딩 알고리즘 처리에 효율적으로 적용하는 방법을 보였다. 실험 결과 vLLM은 당시 최고 수준의 시스템보다 2–4배 높은 처리량을 달성한다.
